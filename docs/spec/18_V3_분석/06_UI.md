## 리소스 구조와 native 실행

SPC 안 `flash.sfl`은 `LLFS`, 버전 7.11이다. 헤더는 매직 뒤 `u16 patch, u16 minor, u32 major, u32 tableCount`이다. 각 테이블은 16바이트 헤더, 각 entry도 16바이트 헤더를 갖는다. entry에는 id, payload 길이, event 번호, data 개수, 시퀀스 관련 값이 있다. 모든 필드의 원본 오프셋을 JSON에 남겼다.

테이블 1은 이미지 참조 정수, 2는 이미지 해상도, 3은 이미지/네 정수로 구성된 사각형 레코드를 가진다. 4는 텍스트 계열, 5는 sprite timeline, 6은 main timeline으로 native 사용처와 연결된다. 사각형의 네 정수는 원문 그대로 보존하며, 최종 화면상의 글자 bounding box와 혼동하지 않는다.

UI 명령 번호는 SWF의 번호와 겹치지만 **payload는 SWF 그대로가 아니다.** 공개 SWF 파서를 적용하던 가설은 전체 corpus에서 실패했고, native 코드를 확인한 뒤 아래 형식으로 교체했다.

| 명령 | 확인한 실행 | native 근거 |
|---|---|---|
| 26 | PlaceObject2. shape/text/sprite 생성 또는 기존 layer 행렬·색 갱신 | `0x1404b7010`, `ev_0ac38ffd3dccdf71d279e5d5c4bfb7f17b73f007ffc71e70efcb0f1348268580` |
| 28 | RemoveObject2 계열, 원문 depth 보존 | RTTI `GameFlashTagRemoveObject2` 및 corpus |

배치 참조는 **table 종류 u8 + entry 번호 u16**이다. 실제 native는 종류 3·4·5를 각각 다른 생성 함수로 보낸다. 원문 depth에서 1을 뺀 값을 내부 layer에 전달한다. 52,236개 배치 참조가 전부 실제 테이블 entry로 연결됐다. 동일 layer의 기존 객체에는 `0x1404a9320`이 행렬 9개 float와 색 변환 8개 float를 갱신한다. 근거 `ev_c23fe9934634603cbc022dcf34e8af10ce697811467ca1db10785752572026c8`.

### 실제 행렬 형식

`0x1404b7710`의 component mask는 다음과 같다. 근거 `ev_9727aa40a4dd39983bcac9e37dfdd2fcbb72fba69b0c159f3e46e1df86fe3f97`.

| mask | 값 | 변환 |
|---|---|---|
| `0x01`, `0x10` | X/Y 배율 | signed 정수 ÷ 65,536 |
| `0x02`, `0x08` | 두 skew 성분 | signed 정수 ÷ 65,536 |
| `0x04`, `0x20` | X/Y 이동 | signed 정수 × 0.05 |

배율·skew·이동의 각 그룹은 존재하는 경우 **5비트의 공통 비트폭**을 먼저 읽고, mask가 켜진 성분만 signed bitfield로 읽는다. 기본은 단위행렬이다. signed bitfield 독해는 `0x1404b79b0`, 근거 `ev_840b27fa3fda2497bd8b355d2aa94e8afc5e3cfa9313f4fc00d6d8a096518268`와 일치한다. corpus에서 행렬 1,121,392개를 해독했다.

색 변환은 첫 1바이트의 하위 4비트가 RGBA multiply, 상위 4비트가 RGBA add의 존재 mask다. 이어지는 4비트가 공통 비트폭이며 각 signed 값에 `1/256`을 곱한다. 기본 multiply는 1, add는 0이다. `0x1404b74c0`, 근거 `ev_281438cc2ac8158986ff07dd7b5267901d5e759d25511a208a1dc980cc222d8d`.

PlaceObject2는 SWF의 Ratio flag `0x10`에 해당하는 값을 소비하지 않는다. `0x40`의 u16은 instance name보다 먼저 소비한다. 액션은 짧은 opcode도 모두 `u8 opcode, u8 opaque, u16 payloadLength`의 4바이트 헤더를 갖는다. 이 차이를 없애고 SWF로 뭉뚱그리면 좌표·알파·이름이 전부 뒤틀린다.

## 실행 시간: clip 정지와 UI 전체 정지는 다르다

`0x1404ab510`에 전달한 16/32 같은 float를 글자 크기로 해석하면 안 된다. 실제 원시 명령의 연결은 UI 보조객체 +0x10 저장(`0x1404ba190`) → `0x1404bc1d0`의 작업 enqueue → callback `0x1404bd230` → UI 항목 +0x150에 더하기(`0x1404a9690`)다. 공통 update `0x1404aad00`은 400개 UI slot에서 이 누적값을 player에 전달하고 0으로 비운다. player `0x1404a8170`은 main timeline +0x144에 값을 저장한다. raw 코드 구간·SHA는 외부 `native/ui_stage2_raw.json`에 보존했다.

main timeline의 실제 시간 소비 `0x1404afd60`은 이 delta를 최대 1씩 나눠 논리 frame cursor +0x13c에 더하면서 해당 frame tag를 실행한다. Play는 자기 clip의 진행 flag를 켜고, Stop은 그 flag를 끈다. frame/label 이동은 이전 frame들을 다시 적용하는 별도 seek 분기를 갖는다. 따라서 frame 차이를 무조건 60으로 나누거나 source label 번호를 그대로 초로 바꿀 수 없다.

대표 실제 소비 `0x140354810`은 입력 predicate `0x1403c8740`과 진행 상태를 검사하여 정상값 1 또는 빠른 진행값 16을 `0x1404ab510`에 넘긴 뒤 label 재생을 요청한다. 이 분기는 글자 크기를 16배 키우는 동작이 아니다. 같은 label을 빠르게 기다림 상태로 진행시키는 정책이다. 근거 `ev_4d77b5a966e15f71fc7870685ec609f23832c4c13973538db3fe093b4cea1a9b`, 공통 UI update `ev_fe9fbdf41a4737fdc360e1994b465ee3c46d88375d1ce412040f5c8d35e64906`, 시간 소비 `ev_73b41903208c911269ce45d6bdd0194006307796442f588ac7e1db0b822497c2`.

중첩 sprite는 부모 frame cursor와 같은 값을 사용하는 것이 아니다. `0x1404ae850`은 player main timeline의 delta를 `0x1404a7990`으로 읽어 자기 +0x144에 복사하고, **자기 play/stop 상태와 자기 cursor**로 같은 시간 소비 함수를 실행한다. main tick `0x1404a94c0`은 자기 clip이 Stop 상태여도 그 뒤 child layer update `0x1404a9390`을 호출한다. 그러므로 부모가 대화 기다림 frame에서 멈춰도 자식의 대기 장식·루프가 계속될 수 있다. 근거 `ev_e558a1ae6019d239b45dbe71812ffc7fd0473a312ceecf516fe4b18e0f398a80`.

반면 player `0x1404a8460`의 전체 freeze +0x1e8, active +0xf8, pause +0xfc gate는 root update 자체를 제한한다. 이를 DoAction Stop 하나로 구현하면 중첩 장식과 전환이 잘못 멈춘다. 빠른 진행 중에도 Stop/seek 분기를 만나면 단순 delta만큼 끝까지 진행하지 않으므로, 화면의 특정 전환을 검증할 때 label·delta·stop 상태·자식 상태를 함께 기록해야 한다.

후속 실행 상태의 제한된 대조도 있다. black client 상태에서 읽은 title SFL slot12/13/14/15/19/20/21의 root cursor는 각각60/19/55/19/13/13/71이었다. 원본 SFL의 해당 table6 frame을 조회하자 **7개 전부 DoAction Stop7+End0에 정확히 일치**했다. 전체 slot의 flags가0이라는 이유만으로 UI 전체 update가 동결됐다고 설명하는 가설은 이 대조와 맞지 않는다. 이 결과는 논리 timeline 진행·정지의 근거이며, 최종 화면이 보였다는 증거는 아니다. 원장은 외부 `native/startup_sfl_cursor_comparison.json`과 `runtime_boot_snapshots.jsonl`이다.

### 패드 진입의 그룹 정지와 SFL 전체 player 갱신 gate

공통3bc0f0은 상태가 바뀔 때511c30에0..9의10slot을 전달한다. slot→실제group은0,1,2,10,11,12,20,21,22,−1이다. callback에는slot10→group−2도 있지만 이 진입에서는slot10을 호출하지 않는다. −1도 다음 소비자의 정확한 group 일치 비교를 거치며 모든 group이라는 wildcard로 쓰지 않는다.

511c30은manager+0x30d84의slot 상태를 갱신하고,8바이트(slot,flag)를495170으로 전달한다. 이 함수는 thread 조건에 따라 즉시 callback을 부르거나 payload를 복사해 ring queue에 넣는다. 항상 동기 호출이라고 정리하지 않는다. callback511d80은4개 실제 pool writer와1개 return-only stub을 부른다. pool 용량400/1000/200/100은 등록 slot 수이며 화면 객체 개수나 메뉴 개수가 아니다.

SFL의4ab060은group이 정확히 일치하는 기존player의+0xfc를 쓴다. 다른3개 pool도 별도 pause field를 쓰되 공통으로group30/31/32를 제외한다. 현재 패드의 모든 asset이 어느group인지까지 이 후속에서 확정한 것은 아니다. SFL 소비4a8460은+0xf8이켜지고+0xfc가0일 때만 root virtual update를 부른다. 따라서 이 그룹 정지는 parent clip의Stop 뒤 child tick이 계속되는 앞 절과 다른 층이다. 4aad00의slot 순회·delta 전달 자체와 실제root 갱신도 구분한다.

## 텍스트 크기·정렬과 계층 좌표

실제 text draw `0x1404b3d10`은 SFL type4 text payload의 색, bbox, 정렬과 높이를 읽는다. 앞 u32는 색, 다음 signed32 네 개는 x/y/width/height다. byte20 정렬 0/1/2는 각각 왼쪽/오른쪽/중앙 배치 경로로 간다. **byte22의 u16×0.05를 int로 바꾸어 `0x140554380`에 넘기는 것이 기초 글자 높이 경로**다. setter는 font backend의 thread-local context +0x98에 보존한다. `adv_kaiwa_window`의 실제 값 900은 이 경로에서 45가 된다. 최종 화면 글자 높이는 뒤의 계층 배율·font glyph metrics·viewport까지 적용해야 하며, 45를 항상 물리 화면 45px로 단정하지 않는다.

text bbox의 각 꼭짓점은 `0x1404b0da0`에서 먼저 object local affine에, 다음 parent renderstate affine에 적용된다. 예를 들어 1단계는 `x'=x*m00+y*m10+tx`, `y'=x*m01+y*m11+ty`다. parent flag에 따라 추가 배율·offset과 색 multiply/add가 결합된다. 단일 배치 translation만 읽어 최종 문자의 위치·줄바꿈을 결정하면 이 순서를 놓친다.

근거 text draw `ev_ee05dc8da27b4a06ef6697e62024459aa32e501e2916195a54d0933cef09823f`, 높이 setter `ev_39e36c8372b93619584472a77ecbcf8ce01809ece7fd7ad83d82cf1a7a8d1328`, affine 소비 `ev_0920c8a1559f245effeea15a3ab9a53d56fb29e91fb823c6ef55ef734fcdb27c`. 아래에서 glyph·개행·최종 2D 정규화까지 별도 연결했다.

### 중첩 sprite의 행렬과 clipping

sprite draw `0x1404ad740`은 자기 renderstate를 `0x1404ad070`으로 조립한 뒤 child layer에 넘긴다. matrix는 row-vector 표기에서 **`point * local * parent`** 순서다. 부모 state flag에 따라 별도 X/Y 배율과 offset을 먼저 반영하고 color multiply/add를 합성한다. 예를 들어 자식 translation (10,20), 부모 scale (2,2)와 translation (100,50)이면 합성 translation은 (120,90)이다. (110,70)처럼 translation끼리만 더하면 틀린다. `sfl.compose_native_affine`과 회귀 사례는 이 기본 행렬 순서만 검증하며 viewport·추가 flag를 자동 적용하지 않는다. 근거 `ev_8cb4b12bedf18615b388ba01ef141dbc134b318bd76e28f736a538fb74511e5a`.

layer draw `0x1404a8d70`은 depth 순서로 각 slot의 shape/text/sprite 세 포인터를 처리한다. clip-depth 값과 이전 clip 범위에 따라 renderstate의 0x1000 flag를 달리 전달한다. 즉 PNG들을 단순히 instance 이름 순서로 쌓는 방식과 다르다. 이 경로에서 확인한 depth clipping과 텍스트 bbox의 scissor/줄맞춤은 구별해야 한다. clipping flag를 실제 최종 GPU stencil 정책까지 전부 해독한 것은 아니다. 근거 `ev_50939110d5677de28a4bbc28b973846e5cce19b57847a3f318f40b0c99401d81`.

### 글리프 위치·줄간격의 실제 식

`0x140556780`은 요청 높이 H와 선택 font descriptor의 기준 높이 B를 사용한다. H가 양수면 `ratio=H/B`, 아니면 1이다. 전체 배율 S와 X/Y 개별 배율을 곱해 `scaleX=ratio*S*scaleXInput`, `scaleY=ratio*S*scaleYInput`을 만든다. 줄 높이 기초값은 `B*ratio*S*scaleYInput`이다. 다음 줄 advance는 이 기초값에 조건부 추가 높이와 별도 line-gap 필드(+0x70)를 더한다. 추가 높이의 style flag가 어떤 외형 이름인지 확인 없이 outline/ruby라고 부르지 않는다. 근거 `ev_2e337c8ebf2d494cfd92c9822c0402dff058a3af9f0e93ad3225dd2c7a9ae809`.

폭 계산 `0x14055a890`은 실제 SpFt bitmap/index로 글리프를 찾고 `(glyph.width+signedLeft+signedRight)*scaleX+letterSpacing`을 더한다. 끝에서는 마지막 letterSpacing을 뺀다. LF(UTF16 10)를 만나면 다음 줄의 pointer를 반환하므로 `0x140555400`은 각 줄 폭의 최대값을 얻는다. 수평 정렬 `0x14055ada0`은 중앙이면 측정 폭의 반, 오른쪽이면 전체를 기준 X에서 뺀다. 원본 glyph 폭만 글자 advance로 쓰면 좌우 signed 간격과 최종 spacing 차이가 사라진다. 근거 `ev_34f58b85643ffc36307ed39d38df344c4044047a8fd11936e7b64d1d58721432`, `ev_58074863fdc7b8387b85718d2e0c49e02f190bd1e8ddc312ad0dfd9f96cb2667`, `ev_a439f323d5e81eaf6d18c13305ed834b419c538770f51ac781c5ce0d9ea8fe9c`.

glyph 배치의 raw 명령은 `left=inputX+signedLeft*scaleX`, `top=inputY+signedVertical*scaleY`, `right=left+glyph.width*scaleX`, `bottom=top+glyph.height*scaleY`다. 반대 방향 배치는 signedRight와 width를 inputX에서 뺀다. `0x140558944`의 signed byte7 읽기와 scaleY 곱·Y 더하기를 직접 확인했다. 이 값은 glyph placement origin에 대한 실제 vertical bearing이며 OTF의 이름 붙은 baseline 값을 임의로 대입한 것이 아니다. REA의 `0x1405588d0` query는 unwind fragment를 포함하는 `FUN_140558870`으로 정규화됐으므로 상세 수식은 원시 명령과 함께 보존한다(`ev_eb45394ed5e35e8ed73770234c03a48bd8dcbbed9e9d45ad7a07c46e04459bc3`).

줄간격의 원본 소비도 확인했다. `0x1404b40a6`은 text payload byte30의 **unsigned u16**을 읽어 float 0.4와 곱하고, letter spacing 0과 함께 `0x1405544a0`에 전달한다. setter는 TLS +0x8c/+0x90에 두 값을 저장하고, `0x14055b410`이 draw job의 +0x6c/+0x70으로 복사한다. 일반 대화의 실제 높이 900과 gap 40은 각각 45와 16 design unit이므로, 배율 1·조건부 추가 높이 0인 경우 줄 advance는 **61**이다. 이 16은 빠른 timeline delta 16과 다른 필드다. `0x140559900`은 LF에서 X를 정렬 기준으로 되돌리고 Y에 계산된 줄 advance를 더한다(`ev_6d33d2296befaf1c012ca675c694c5e4ed18bce9ad87c22528ed8da3fefdfee6`).

726개 header 중 gap 16은 662개, 8은 35개다. 나머지는 72·120·160·26174.4이며, 마지막 8개는 원본 u16 65436의 unsigned 소비 결과다. 이를 signed -100으로 바꾸거나 임의 보정하지 않았다. 해당 text가 실제로 표시되는 조건과 별도 override는 아직 실행 확인이 필요하다. 원시 값 전체와 예외를 `native/sfl_text_headers.json`에 남겼다.

추가 전수 검증은 외부 `scan_sfl_stage2/summary.json`이다. SFL **1,987 carrier / 1,609 본문 전체**가 새 text header까지 오류 0으로 통과했다. text를 가진 고유 SFL 215개 안의 text header 726개를 모두 해독했다. 기초 높이는 20..50 범위이며 45가 309개, 42가 136개다. 정렬은 왼쪽 459·중앙 146·오른쪽 121개다. 전체 원장은 `native/sfl_text_headers.json`이고 carrier 중복은 별도 ledger로 보존한다. `sfl.py`의 새 text/행렬순서/명시적 viewport 회귀를 포함해 담당 자원 검사 16개를 통과했다.

## 1920 설계 좌표에서 최종 2D projection까지

실제 `GameFlash::Draw` 함수 `0x1404a7560`은 2D player branch에서 `0x1400f1e00`에 **1920.0, 1080.0**을 전달한다. 이 함수는 width/height와 절반값을 camera 설정에 저장하고 `0x1400f1a80`을 호출한다. 후자는 `[W,H,1/W,1/H]`를 render parameter에 넘긴다. native 등록 `0x1400df810`은 그 ID global `0x140d21430`을 정확한 이름 **`_sp_system_virtual_screen_param`**에 연결한다. 이름이 비슷하다는 추측이 아니라 ID 저장과 소비를 연결한 근거다. 근거 root `ev_eb8d27f1f2af3ffdd89d8cdd7812a23bef64cdcedca5ad379e8b42ce0e83a8fd`, camera 설정 `ev_c1b209d3d052783ca87d6f3d4d5e628299aa780648ee1296cf6d0e53dd6e389e`, parameter 소비 `ev_ccd9fc60e5295207bcfe9a0c0e16ace90ac86ccd1a21c347a6177d7e9c676d05`, 등록 `ev_f775d978727deae35de60f3a6e92adab765213839e62a8276b0cc7560bc5e304`.

REA가 제공하는 shader 전용 기능이 없어 Windows `D3DDisassemble`을 읽기 전용으로 사용했다. 복원 EXE에 내장된 유효 DXBC **477 carrier / 440 고유 본문**을 오류 0으로 disassemble했다. 그중 위 이름을 reflection에 가진 vertex shader **21개 전부**는 동일한 XY 식을 사용한다. `div position.xy, screen.xy` → `mad *2-1` → Y 부호 반전이므로 **`clipX=2*x/1920-1`, `clipY=1-2*y/1080`**이다. 각 variant의 UV·색·Z 처리는 다를 수 있으며 화면별 실제 shader binding을 실행 추적한 것은 아니다.

따라서 affine 적용 뒤 design 좌표 `(x,y)`와 viewport `(Vx,Vy,Vw,Vh)`가 주어지면, 일반 w=1 경로에서 **`screenX=Vx+x*Vw/1920`, `screenY=Vy+y*Vh/1080`**이다. 예를 들어 viewport (100,50,1280,720)의 design (396,873)은 (364,632)가 된다. 이 식의 해상도 적용은 회귀로 검증했지만 실제 창의 viewport가 항상 client 전체라는 추가 가정은 넣지 않았다. `GameFlash::Draw3D`인 `0x1404a6af0`은 별도 world camera와 0.01/-0.01 scale을 쓰므로 이 2D 공식을 모든 UI에 적용하지 않는다.

재현 script·reflection·assembly는 저장소 밖 `native/disassemble_embedded_ui_shaders.py`, `native/embedded_shaders/inventory.json`, `native/embedded_shaders/virtual_screen_shaders.json`에 있다. 대표 VS SHA256은 `0ab153ef1683f36173d40ca8c34767a54b398c8715d9d3400b6e14e3c445484e`다. 원본 shader bytecode를 프로젝트에 편입하지 않았다. native 연결·수치·검증 결과는 `native/ui_runtime_findings.json`에 묶었다.

## 남은 불확실성

SFL payload 디코드는 corpus 전체에서 검증했고, 논리 delta·중첩 cursor·Stop과 전체 pause의 차이, 계층 affine, glyph bearing·개행 advance, 1920×1080의 shader 정규화를 연결했다. 아직 실제 실행 화면과 wall-clock UI 속도, 창 크기별 letterbox/viewport 정책, 모든 외부 label·callback·폰트/style 선택, GPU clip/stencil 전환 전체를 검증한 것은 아니다. 검은 client 화면은 이전 실행의 관찰 이력이다. 후속 [14_플레이경험과설계학습.md](14_플레이경험과설계학습.md)에서 원본 타이틀·Load·본편 대화의 일부 화면을 실제 관찰했지만, 이 문서의 모든 SFL·변환식·재생 속도를 실행 검증한 결과로 확대하지 않는다.

반증 기준도 분리한다. 부모 Stop 후 자식 루프가 계속되는 것은 현재 코드와 일치한다. 전체 player pause에도 계속된다면 다른 player·별도 update 경로를 조사해야 한다. 동일한 최종 design 좌표가 viewport 식과 다르면 먼저 3D branch, hierarchy 추가 flag, 실제 viewport와 w를 확인한다. 정상 글자 높이가 fast delta에 따라 16배 커지는 구현은 확인한 native 소비와 맞지 않는다. 원본 gap 65436의 표시 결과는 정상 대화 gap 40과 분리해 관찰해야 한다.

SRD 텍스처는 원본에서 분석용으로만 해독했다. 우리 게임에 원본 이미지나 폰트를 편입하지 않았다. 알려진 PC layout flag `{1,3,65,67,71}`에서 linear BC7/DXT 계열을 디코드했고, 실제 텍스처 atlas를 열어 확인한 대표 사례가 있다. 모든 그림을 육안 검수한 것은 아니다.

1. `Game/tools/create-project.mjs`의 `W_Yumeno`·`W_Flow` 생성에서 `DialogFrame`, `Nameplate`, `Name`, `NameHead`, `Body`, `Next`를 위 실제 레이어 구성과 대조한다. 메시지 바탕·이름 바탕·이름 글자·메시지·장식은 개별 애니메이션을 갖는다. 원작 이미지는 사용하지 않는다.

4. 확인한 계층 affine→1920×1080 정규화→명시적 viewport를 한 곳에서 변환한다. `2/3`을 UI 곳곳에 복사하지 않고 2D/3D branch와 실제 viewport를 구분한다.
5. 새 상태에 `Stats()`·자동 입력 정보를 함께 추가하고, 구현 뒤 `node tools/verify-flow.mjs 0 6`과 화면 캡처 비교로 검증한다. 이번 작업은 분석 도구·문서 변경이므로 게임 빌드나 게임 자산 변경을 수행하지 않았다.

## 폰트 STX는 문자열 표와 다른 형식이다

전체 STX11,479 carrier 중 STXT 문자열 표는11,444개이고, 나머지35개는 `$CFH/$TXR/$RSI`를 가진 SRD 계열의 폰트 STX다. 확장자만으로 문자열 표 파서를 적용하지 않는다. `tools/re/font.py`가35개 전부를 별도로 해독했으며, 비트맵·인덱스·글리프 수와 atlas 사각형 범위는 모두 일치했다.35개 고유 본문에 글리프 레코드는 총11,110개다.

`$RSI`의 `font_table` 로컬 리소스는 `SpFt` 헤더를 가진다. 각8바이트 글리프 레코드는3바이트의 packed atlas좌표, 폭·높이1바이트씩, signed 간격값3개다. 문자 존재 비트맵과32문자 그룹의 인덱스를 연결해 실제 글리프를 찾는다. 0xD800 이상을 무조건 자르는 공개 파서의 제한을 그대로 가져오지 않고 원본 비트 수 전체를 검사했다.

폰트 이름은 실제 metadata에서 읽었다. 일반 US 대화 폰트 사례는 `FOT-HummingStd-D.otf`, 다른 자료에는 `FOT-NewRodinPro-DB.otf`, `FOT-RodinPro-EB.otf`, `FOT-SeuratPro-DB.otf`, `FOT-ReggaeStd-B.otf`, `DFGB_Y7.TTC`, `DFT_R7.ttc` 등이 있다. 원본 metadata의 이름이며 대체 폰트 추천이나 모든 최종 화면의 폰트 선택 확정값이 아니다. glyph·배율·줄간격의 소비 식은 위에서 연결했지만 모든 라벨의 font/style 선택과 외곽선 정책은 남아 있다.

전체 원본 경로·본문 해시·글꼴 이름·atlas 크기는 저장소 밖 `font_metadata/summary.json`, 글리프 수치와 물리 오프셋은 `font_metadata/<SHA>.json`에 있다. 원본 font atlas·글리프 그림·TTF/OTF를 우리 게임에 편입하지 않았다.

## 입력 좌표와 표시 좌표를 연결할 때

[13_입력.md의 마우스 좌표 절](13_입력.md#마우스-좌표--display-target--상대-조준--실제-hit)은 client 좌표가 `5af060/5b0dc0`에서 swap-chain back buffer→display-color target의 중앙 aspect-fit 보정을 거치는 실제 입력 경로다. 목적지는 graphics+0x68이며, 별도 내부 render-color target+0x78과 혼동하지 않는다. 함수 자체가 destination1920×1080을 강제하지는 않는다.

이 문서의1920×1080 design→NDC→viewport와 입력의 client→display 변환은 반대 방향의 서로 다른 계약이다. 팬게임에서1920×1080을 입력·표시 정본으로 사용할 경우 실제 content rectangle과 display 크기를 명시하고 sprite·hit를 같은 변환 결과로 연결해야 한다. 대표 `3913e0`은 처리된 상대 입력으로 만든 같은 커서 좌표를 SFL 배치 `4ab240`과 hover `38f530`에 넘긴다. 이 사례의 상대 조준 gain·±40 제한을 모든 메뉴·미니게임에 공통 적용하지 않는다. 수평 FOV는3D 투영 계약이며2D mouse 배율로 곧바로 곱하지 않는다. 외부 원장은 `native/mouse_coordinate_findings.json`이다.

## UI 시간의 생산과 소비 — 속도 설정은 지속되고 정지 중 진행량은 조건부로 비워진다

4ab510은4ba190을 통해 helper+0x10에 재생 증분을 저장한다. 이 setter 호출 자체가 진행량 command를 즉시 보내는 것은 아니다. 공통 시간 문턱49d550은 게임 갱신3bc280 뒤511d10을 호출하고,511d10→4abe80은400개 slot을 돌며 player와 helper가 있고 전체 freeze(+0x1e8)가0인 대상에4bc180을 호출한다. helper는 저장된 증분으로4bc1d0 command를 계속 생성한다. 따라서 같은 설정을 매 프레임 다시 지정해야만 재생되는 계약이 아니다. 단, 모든 helper 생성자의 기본값1을 이번에 확인한 것은 아니다.

4bc1d0은 slot 포인터·설정값의 float32 비트·marker12345678을32바이트 payload로 묶어495170에 전달한다. 즉시 실행 또는 복사 queue 조건은 기존 분석과 같다. callback4bd230은 marker와 slot ID를 확인한 뒤 payload+0x18의 **float를 XMM2**로4a9690에 전달한다. 의사코드에 보이는 `(int)param_1[3]`을 실제 정수 변환으로 읽으면 안 된다. raw MOVSS를 대조했다. 4a9690은 값을 slot+0x150에 더하므로 소비 전에 여러 command가 도착하면 합산된다.

511bb0→4aad00은 누적값을 player에 전달하고 slot+0x150을0으로 만든 뒤4a8460을 호출한다. 그룹 pause(+0xfc) 또는 비활성(+0xf8) 때문에 root 갱신이 거절되더라도 이 소비·초기화가 앞선다. 생산자4abe80은 전체 freeze는 검사하지만 그룹 pause/active는 검사하지 않는다. 따라서 **queue와 소비가 정지 중에도 계속 처리되는 조건에서는** 정지 중 진행량을 매번 버리고, 해제 시 그 양을 한꺼번에 따라잡지 않는다. 소비 자체가 멈춰 command가 보존되는 경우까지 이 결론으로 덮지 않는다. 전체 freeze는 새 생산도 막지만 이미 도착한 payload의 처리 여부는 별도다.

511bb0의 직접 call 참조는 없고 함수 포인터 자료 참조와.pdata 참조가 있다. 모든 가상 호출·render thread의 실행 순서와 소비 빈도는 아직 닫지 않았다. 공통 게임 틱이 명목60Hz라는 사실과 UI 소비가 정확히 같은 주기라는 주장을 합치지 않는다. 알려진 증분1·매 틱1회 소비·Stop/seek/pause 없음이라는 조건이면 label 차이19는19 논리 틱으로 계산할 수 있지만, 실제 대화 전환이 항상19/60초라고 실측한 것은 아니다.

외부 `native/close_ui_delta_clock.py`, `ui_delta_clock_findings.json`에14개 함수·참조·raw float callback과 조건부 정지 소비 사례를 보존한다. 생성자별 기본값·최종 가상 dispatch·실제 속도가 남아 있으므로 진척표의 화면·소리 항목은 올리지 않는다. 게임 코드는 변경하지 않았다.
