# 00 — 게임 전체 흐름과 대본 실행

## 범위와 증거 수준

주인님의 요청은 재판만이 아니라 **설치본에 포함된 게임 전체**다. 본편의 타이틀·장 선택·일상·탐색·자유행동·수사·재판·처형·장 종료, 저장·설정·갤러리와 해금, 카지노와 별도 보너스 게임도 범위에 포함한다. 파일을 목록에 올린 것, 내용을 해독한 것, native 처리기와 연결한 것, 실행 화면을 관찰한 것은 서로 다른 완료 조건이다. 현재 결과는 정적 분석이며 전체 플레이·화면 재현 검증 완료가 아니다.

원본 설치 경로는 `C:/Program Files (x86)/Steam/steamapps/common/Danganronpa V3 Killing Harmony`다. 상세 근거의 루트는 `C:/Users/kirby/Downloads/v3_re/`다. 이 문서에서 이하 경로는 해당 루트 기준이다. 실행 파일 SHA와 정적 복원 사본의 차이는 README와 `native/derived/*.provenance.json`을 따른다. 패킹된 코드의 잘못된 디컴파일은 동작 증거에서 제외한다.

## 전체 자산의 연결

설치 파일 7개 중 CPK 3개의 모든 8,116멤버를 읽어 범위·압축 여부·해시를 확인했다. 이 설치본의 CPK payload는 압축되지 않았고, 실제 압축은 SPC 내부에 있다. 따라서 사양서17의 'CPK는 CRILAYLA 해제가 필요'라는 가정은 이 설치본에는 적용하지 않는다. 직접 작성한 파서는 CRILAYLA도 지원한다.

7,959개 바깥 SPC의 60,538항목과, 그 안 445개 추가 SPC의 915항목을 합쳐 내부 기록은 61,453개다. 이 합계에는 다시 다른 항목을 담는 SPC carrier 자체도 들어 있다. 본문 수나 고유 콘텐츠 수와 같지 않다. 근거는 `inventory/nested-summary.json`, `nested-deeper-summary.json`, 각 CPK JSON 및 SPC JSONL이다.

WRD는 명령열, STX는 문자열, typed DAT는 라벨→숫자·리소스·조건 표, SRD 계열은 장면/그림/메시, SFL은 UI 타임라인이다. 파일명만으로 화면 동작을 결론내리지 않고 다음 연결을 보존한다.

`CPK 멤버 → SPC 항목/압축 → WRD 명령 바이트 오프셋 → 참조 라벨/숫자 → native 처리기 → DAT/SFL/SRD → 화면 상태`

## WRD 로드와 실제 실행 루프

`0x14047b0e0`은 `wrd_script/`의 대본 묶음과 언어별 텍스트 묶음을 선택하고 WRD/STX 파일을 준비한다. `0x14047bac0`은 기존 묶음 재사용/교체와 호출 깊이를 처리한다. `0x14047dfb0`의 상태0/1/2/3/4/6은 리소스 준비 상태로 나타나며 이것을 일상/수사/재판 enum으로 바꿔 읽으면 안 된다. WRD 객체 생성은 `0x140475720`이다.

실제 명령 실행은 `0x14045b310`, 근거 `ev_80ecfb61b6347b0d1922b13763ea7b6250c2a72e2501dd9965a4c61caf0f5db0`다. 두 바이트를 big endian 명령값으로 읽어 `0x7000 + opcode`로 분기한다. 인자 디코드 뒤 처리기를 호출하고 인자 바이트 수를 명령 위치에 더한다. 처리기 반환이0이면 현재 위치를 저장하고 호출자에게 돌아가며,1이면 다음 명령을 같은 호출 안에서 계속 처리한다. 따라서 화면별 기다림은 단순한 고정 지연이 아니라 처리기의 진행/중단 정책과 연결된다.

| 흐름 명령 | 확인한 처리 | native 주소 |
|---|---|---|
| SUB | 현재 호출 깊이+1로 다른 묶음/대본 로드 | `0x140471e00` |
| RTN | 호출 깊이 감소와 복귀 후 정리 요청 | `0x1404719b0` |
| JMP | 라벨 resolver로 명령 위치 변경 | `0x1404679d0` |
| END | 종료 요청 필드 설정, 실행 루프에 반환 | `0x140464530` |
| FLG/IFF/WAK/IFW/SWI/CAS | 플래그·변수·조건·선택 분기 | `native/wrd_dispatch.json`에 전체 주소 |
| LOC/CHN/BTN | 문자열 표시·화자·진행 대기 연결 | `02_일상.md` |

`LAB`는 명령표와 라벨표를 함께 사용한다. `lab_Top`은 resolver에서0으로 처리하며, 나머지는 라벨명과 오프셋을 조회한다(`0x1404758f0`). 발견하지 못했을 때도0으로 돌아가는 분기가 있어, 외부 분석기는 '연결됨'과 'fallback0'을 구분해야 한다.

공개 opcode명76개 중 native switch에서 67·68·69는 독립 처리기로 분기하지 않는다. 보너스 RSC 대본에는 실제 command_label.dat의 별도104개 명령 이름을 적용했다. 메인 WRD23,215개/6,443,020명령과 RSC442개/89,391명령을 모두 경계까지 해독했다. RSC 확장 명령30,453회의 인자 종류는 아직 미확정으로 남긴다. 최신 재현 분모는 `repro_script_scan_v3/summary.json`이다.

## '007 전체'와 실제 도달 순서는 다르다

`wrd_script/007`의 코어 WRD2,714개에는734,183명령이 있다. 기본 대본에 US overlay를 적용하면2,716개 WRD와2,166개 STX,73,000개 LOC가 연결된다. LOC의 누락 ID는0이다. WRD 헤더 문자열 개수와 STX 행 수가 다른10건은 별도 기록했다. 중복 ID·테스트 대본을 포함하므로 이를 실행 오류10개로 해석하지 않는다.

003~007은 일부 묶음만 동일하다. 실제로 다른 대본도 있으므로003 수치734,288과007 수치를 합치거나 복사하지 않는다. 추가 확인한 상태 초기화 함수 `0x14053cf60`은 묶음 버전 필드+0x9790/+0x9794에7을 기록한다. 저장 스냅샷 `0x140477a17`에도 해당 필드 갱신이 있다. 따라서 새 상태의 정적 기준을007로 삼을 직접 근거가 생겼다(`ev_7ee5c0bb7314474499e9b97c8d154134bb9fe2b4906ce6001b5828ea12d31390`). 설치 language.txt의 실제 값은US다. 기존 저장 자료의 구버전 전환과 각 로드 분기는 별도 확인한다. `core003_control_flow.json`은003의 정적 분기 후보 그래프이며, 전체 실행 순서의 증명이 아니다.

## 진행 구간 개방에서 실제 선택 조건까지

ModeChapter403·EventGallery300·nightevent15·secretevent6·ModeCasino1곳이다. 모두 작성 위치이며 실제 해금 횟수가 아니다.

## 남은 검증

하루 흐름은 구체적인 표본도 연결했다. 첫 장의scene19와20은 각각 활동 완료 `flg220`을 확인하는 호출자 분기에서 다음scene으로 넘어간다.21 초기화는 `wkDayTimes=Night`,22 초기화는 `DayTime`을 기록하며21의 방 대본에서22로 가는FIL도 확인했다. 즉 이 표본에는 두 활동 문맥→밤의 이야기·선택→다음 낮이라는 작성된 연결이 있다. 관련10개 script의 SHA·offset·완료 분기 인접 명령은 외부 `native/day_sample_19_22.json`에 보존했다. 휴식·거절·취소의 별도 분기까지 하나로 합친 것은 아니며, 이를 모든 날의 고정2회 규칙으로 일반화하지 않는다. 특히02의 같은scene 복귀 예외는 그대로 남는다.

자유행동은 초대 wrapper240개와 호출 scene군23개를 효과 US007 대본까지 대조했다. 초대·수락·선물 소모·SSB/SIN·스킬 보상·완료 플래그와 다음 진입점의 연결 및 같은 scene으로 복귀하는 예외는 [02_일상.md](02_일상.md)를 따른다. 씬 수를 날짜 수로 바꾸거나 완료 플래그만으로 고정 활동 횟수를 추정하지 않는다. 실제 플레이 관점의 이해·적용 판단과 초기 실행 관찰 제한은 [14_플레이경험과설계학습.md](14_플레이경험과설계학습.md)에 유지한다.

아침·밤 방송의 모든 진입 조건, 하루별 자유행동 횟수, 문/구역 해금의 모든 식, 수사 순서, 각 저장 지점의 일대일 목록은 전체 도달성 그래프로 검증하지 않았다. 이 전수 범위를 주요 정상 명세의 필수 공백과 혼동하지 않는다. 일반 수사 gate·재판 요청/복귀·장끝 저장/FIL·정상 Continue는 각각03/04/16/09의 후속 근거로 연결됐다. 모든 예외와 최종 화면은 한계로 유지하고, 런처/초기 창 관찰을 본편 전체 플레이 검증으로 표시하지 않는다.

## 유메노쿠니에서 바꿀 것

1. `Game/Source/Flow.hpp`의 `enterBeat()/nextBeat()/eventsDone()`는 비트를 선형으로 넘긴다. 조건·호출·복귀·대기·비동기 리소스 완료를 각각 재개 가능한 상태로 표현하고 자체 대본 이벤트와 연결한다.
2. 같은 파일 `openChapter()/newGame()/loadFlow()`는 장 시작/수사/재판/자유행동 재개 진입점을 구분할 수 있도록 고친다. 원작 대본 경로를 우리 대본에 그대로 삽입하지 않는다.
3. `saveFlow()/loadFlow()`는 beat/event 외에 진행 중인 UI/모드/호출 문맥의 복원 규칙을 정의해야 한다. 원작 세이브 바이트를 흉내 내기보다 실제 재개 동작을 기준으로 한다.
4. `tools/build_flow.py`의 생성 이벤트에 명시적인 전환 조건·해금·연출 기다림을 넣고, 검증기 `Game/tools/verify-flow.mjs`에서 입력 없이 건너뛰는 전환도 관찰한다.
5. 이번 변경은 분석 도구·문서다. 기존 게임 파일 수정사항은 작업 시작 전 변경이며 이번 분석이 구현 완료를 의미하지 않는다.
