# 공통 업데이트 시간과 하위 재생 속도

## 확인 범위

Steam PC 설치본에서 코드 영역만 복원한 정적 분석용 실행 파일을 사용했다. 원본 SHA256은 `503073a67a2cc0056b7d11d400fb9736c65eec46ec6877478e6ff1ccb6526438`, 분석본은 `1a012357f54076ef7fbe6a63f19f055bbe1ce71792b8c0719e7dc51d2a5affeb`이다. 실제 게임의 프레임 시간을 측정한 결과는 아니다.

공통 업데이트 루프에는 약 60Hz의 시간 문턱이 있다. 이것은 모든 자료의 `Frame` 열이나 모든 애니메이션 클립이 60fps라는 뜻은 아니다. 하위 객체의 정지 조건·업데이트 횟수·독립 재생 배율은 따로 확인해야 한다.

## 시계 단위는 마이크로초

초기화 `FUN_14061b140`은 Windows `QueryPerformanceFrequency` 값에 `1e-6`을 곱하여 전역 분모에 기록한다. 시계 getter `FUN_14061b0d0`은 `QueryPerformanceCounter`를 그 분모로 나누고 정수화한다.

```text
clock_us = integer(QPC / (QPF × 0.000001))
```

따라서 이 getter의 경과 차이는 마이크로초다. 외부 분석 `native/timing_disassembly.json`에는 실제 명령 바이트와 주소도 남겼다. 상수 `1e-6`의 원본 VA는 `0x14078d470`, 파일 오프셋은 `0x78ba70`이다.

근거: `ev_6a4eaaae1f51951d164840e561eba87c59573505e8a96606f0e0e6682c2bd0ed`, `ev_c36614d3b9c64ce910132a9de0444ae1a445f7556e28c2b4d69c8348fbd64489`.

## 공통 루프의 약 60Hz 문턱

`FUN_14049d550`은 경과 마이크로초를 `16666.666015625`로 나누고 이전 소수 누적값을 더한다. 합이 1 미만이면 `SwitchToThread`를 호출하여 다시 기다린다. 1 이상이면 `fmodf(sum,1)`을 다음 소수 누적값으로 저장하고 시계 기준을 현재 시각으로 갱신한다. 이 상수는 약 `1,000,000/60`마이크로초다.

문턱을 넘은 분기에서 전역 tick `0x140ce80a8`을 1 올리고 공통 입력·작업·게임 업데이트 `FUN_1403bc280`, 메시지 화면, 영화 계층 등을 갱신한 뒤 반환한다. `FUN_1403bc280`의 직접 호출은 복원 코드의 E8 호출 조사에서 이 루프 내부 `0x14049d7fc` 한 곳이었다.

```text
sum = elapsed_us / 16666.666015625 + previous_fraction
if sum >= 1:
    previous_fraction = fmodf(sum, 1)
    time_origin = clock_us()
    global_tick += 1
    update_common_game_services()
    return
else:
    yield_thread_and_retry()
```

이 함수는 지연된 정수 tick 수만큼 게임 업데이트를 여러 번 돌리는 catch-up 루프가 아니다. 여러 문턱을 넘었더라도 여기서 한 번만 갱신하고 현재 시각으로 기준을 다시 잡는다. 따라서 부하가 있어도 정확한 실제 60fps가 유지된다고 단정하지 않는다. 시계 모드 0/1/2와 외부 작업 대기·정지 상태도 있으므로 실시간과 게임 진행 시간이 항상 동일하다고 보고하지 않는다.

근거: `ev_7893bfe3fdbee7442a02aa26af49c7373a021075b91b367a5f3eca94b85a153c`. 나머지 함수의 실제 이름 `fmodf`는 예외 경로 문자열까지 확인했다: `ev_d5dae20c37363c7590f831ed4af5d536a10bed05b906ce31efda1f6ef0fdcb76`.

## 타이틀·갤러리·게임 상태와의 관계

타이틀 작업 `FUN_140456970`은 반복마다 `FUN_14049d550`을 지난 후 타이틀 상태 `FUN_1403b63b0`을 갱신한다. 따라서 이 경로의 상태 폴링은 공통 시간 문턱을 사용한다. 갤러리도 같은 공통 영화·메시지 완료 getter를 기다리는 구조다. 실제 UI 클립의 키프레임 재생 속도와 이 상태 폴링 빈도는 별개다.

게임 업데이트 `FUN_1403bc280`은 전역 상태 +0xd2c가 3인지 검사하고, 추가 정지 플래그 `0x140c24ff0`이 0일 때 탐색·오브젝트·카메라 등 관리자를 호출한다. 탐색 관리자 `FUN_140406860`과 카메라 관리자 `FUN_14037d050`이 같은 공통 문턱 아래에 있다. 단순히 모든 객체가 무조건 한 tick씩 진행하는 구조로 옮기면 정지 중에도 시간이 흐르는 오류가 생길 수 있다.

근거: 타이틀 `ev_538a78cd63af185344bb4b3eb071d4d7e981f85406b69c7bef6283f237dda684`, 공통 게임 업데이트 `ev_e96a98b5b65b3e34b197b62173646a04f7ea57c9647ef75e0d57eebbde271514`.

재판 프리셋 경과값의 호출 빈도도 연결된다. 공통 게임 업데이트는 `FUN_1403f8b70`을 호출하고, 이 함수는 해당 관리자가 있으면 `FUN_1403e02e0`을 호출한다. 후자는 활성 상태에서 세 카메라 객체 각각에 `FUN_1403dd070`을 한 번 호출하며, 그 함수가 프리셋 경과값 처리 `FUN_1403de930`을 호출한다. 따라서 활성 상태의 이 경로에서는 공통 게임 tick마다 카메라 경과 업데이트를 한 번씩 요청한다. 각 객체 내부 배율·대기 조건까지 1로 확정한 것은 아니다.

근거: `ev_04952f94866794da3c7ccfcb0af2141fa4cf079faa6bc42aa14199654ff8786b`, `ev_bf60ee744e84651ca938bbfa12780a6b53da95f241d264bc8edabe5db9384084`, `ev_c6f19f0d65b30f7f98e71db39a96c9c017cf6965db375b06c56f28313c270687`.

## 아직 개별 연결이 필요한 값

- 카메라 `Frame/(호출속도×Speed)`와 경과 인자 `+0x18c×+0x190`은 공통 tick에 연결되는 배율까지 확인해야 초로 환산할 수 있다. `08_카메라.md`의 미확정 경계를 유지한다.
- 일반 대화의 Auto 입력·저장 bit와 빠른 재생 조건은 [02](02_일상.md), 음성 상태 조회와 대기 카운터는 [07](07_소리.md), 글자 표시 속도의 실제 reveal 소비는 [09](09_시스템.md)에 후속 연결했다. 이는 모든 모드의 pause·wall-clock 진행 속도 검증이 아니며 문자열 길이만으로 초당 글자 수를 만들지 않는다.
- `UIShowFrame`과 미니게임의 `×60` 상수는 각 소비자가 tick마다 무엇을 증가시키는지 확인한 다음 해석한다.
- SFL의 독립 delta·cursor 소비는 [06](06_UI.md), SAN935개의 핵심 키 구간·선형/SLERP·레이어 재생 모드·로컬 행렬·계층 job은 [12](12_애니메이션과후처리.md)와 외부 `native/animation_playback_findings.json`에 후속 연결했다. 실제 호출 증분의 초 단위·사용자 pause·모든 채널 대상·최종 스키닝은 남아 있다. PPP219개의 명령 경계와 일부 전달 경로를 확인해도 효과별 의미 전체가 닫힌 것은 아니며 공통60Hz로 일괄 환산하지 않는다.
- MP4는 자체 트랙 시간과 재생 완료 상태를 사용한다. 프레임 문턱을 영화 파일 길이 계산에 대신 적용하지 않는다.

기계 판독 근거는 저장소 밖 `native/timing_seeds.json`, `native/timing_calls.json`, `native/timing_disassembly.json`과 `native/rea-restored-evidence.json`이다. 정적 디스어셈블 호출 조사는 직접 E8/E9 대상 범위이며 가상 호출·함수 포인터 호출의 부재 증거는 아니다.


UI 증분 생산은49d550→511d10→4abe80→helper의 지속 설정에서 이어지며, 소비는511bb0→4aad00의 별도 경로다. 그룹 pause 중 소비가 계속되면 진행량은 root gate 앞에서 비워진다. 생산 주기와 소비 주기·벽시계 시간을 합치지 않는 후속 근거는06의 「UI 시간의 생산과 소비」 및 외부 ui_delta_clock_findings.json을 따른다.
