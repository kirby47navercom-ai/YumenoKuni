# 15 — 패드 지도에서 선택하고 이동하는 흐름

## 확인 범위

실행 파일의 패드 지도 controller와 typed `TechouMap.dat`를 연결했다. 화면을 직접 관찰한 결과가 아니며, 지도 전체를 3D 조감이라고 확정하지 않는다. 원작 화면의 외형·표시 타이밍·물리 입력의 전 과정은 계속 확인해야 한다.

## 장소 선택과 인물 선택

`0x140414040`은 준비 → UI 로딩 대기 → 진입 연출 → 선택 → 퇴장 → 결과 반환을 분리한다. 선택 상태6은 `0x140417730`, 상태7은 `0x140417120`을 호출한다. 두 상태 모두 취소로 퇴장 상태10에 들어가며, 확정은 선택 행의 +8/+0xc 두 조건이 모두 참일 때만 허용된다. 보인다는 사실과 이동을 확정할 수 있다는 사실을 구분해야 한다.

장소 선택은 구역당 최대6개 행을 한 번에 다룬다. 선택 위치 +0x36c와 스크롤 시작 +0x370의 합이 실제 행 번호다. 한 칸 이동과6칸 단위 이동이 구분되며 끝에서는 래핑하거나 마지막 유효 창 범위로 제한한다. 장소 수가6보다 작으면 페이지 이동 경로가 빠진다. 이 숫자는 전체 지도 장소 수가 아니다.

`0x140417510`은8개 구역을 순환하되 해당 구역의 유효 표시값이0이면 건너뛴다. 변경 직후 상태8로 옮겨 UI 준비를 기다리고, 선택·스크롤을 초기화하고 지도 표시를 갱신한다. 잠긴 구역을 단순히 모든 장소 목록에 섞는 구현과 다르다.

다른 선택 상태는 가로·세로 각각0..3의 좌표를 쓰고 `y*4+x`를 인물 인덱스에 대응시킨다. 방향 이동은 각 축에서 순환한다. `0x140418560`은 진행 조건과 현재 구역의 인물 bit를 확인하고 해당 인물이 존재하는 장소 행을 선택한다. 인물을 선택하면 바로 순간 이동하는 것이 아니라 장소 선택을 갱신하고, 다시 공통 확정 조건을 거친다. 특수 장면과 주인공 구성에 따른 별도 매핑도 존재하므로 고정된 인물 순서로 일반화하지 않는다.

근거: `ev_0d89896bed51721dfb6baba6903863e25d103d2495bf565dc954e3b7a919ed5e`, `ev_ea07798c9b715c85a9f4a071ccc78e724d1e97a752e9813b1069b641cb71cfc9`, `ev_c4241756058e62ef0735a528e532abba83d4f536ac6afc2983a3b3c51ad401d5`, `ev_d132c9ee3b7e8a624d2f0d58627efe243b2a5219c1888e8b7aeaca6b4c6ee556`.

## 지도 자료와 실제 이동 목적지

`TechouMap.dat`는500행·12열이다. 열4/5는 지도 좌표X/Y이고, 열9/10은 signed16 이동 맵/이동 위치다. native getter `0x140530ba0`/`0x140530bd0`가 각각9/10열을 읽는다. 확정 성공 시 그 값을 controller +0x3cc/+0x3d0에 기록하고 퇴장한다. 따라서 그림상의 위치와 이동할 맵·시작 위치는 서로 다른 자료다. 실제 월드 전환과 `mapjump_data.dat`의 조건·재매핑은01의 `0x140478c90` 경로를 함께 따른다.

`0x140416cd0`은 현재 위치를 읽어 초기 구역·선택·스크롤을 정한다. 현재 위치를 항상 목록의 첫 행으로 두는 구현과 다르다. `0x1404180d0`은 선택 장소의 최대16개 인물 bit를 세어 UI 연출을 고른다. 이때 인물 bit 수에 따른 연출 분기는 확인했지만 화면 없이 각 연출의 시각적 의미를 명명하지 않는다.

## 목록에 포함되는 조건과 이동 허용 조건의 생성

`414690`은 `TechouMap.dat`의 표시 타입(열7), 구역(열2), save No(열1), 표시 순서(열8)를 각각 `530b70/530b10/530d10/530b40`으로 읽는다. 이 **표시 타입0/1/2는 Map.dat의3D/2.5D나 place의操作0/1과 다른 계약**이다. 지도 타입1을 보행 모드1로 해석하지 않는다.

유효 구역의 장소 목록에는 표시 타입2/−1을 제외하고 `working+0x700+saveNo*4`의 bit29가 켜진 행만 넣는다. 저장된 행의 +8은 타입1일 때만1이다. +0xc는 같은 word의 bit30에서 시작하지만, 탐색 manager의 `+0x10!=0 && +0x224==1` 준비 조건과 공통 flag0x8f가 모두 참이어야 유지된다. `478300(0x8f)`의 실제 위치는 **working+0x6d0 bit15**다. 두 선택 상태의 확정 입력은 +8과 +0xc가 모두 참일 때만 목적지를 쓴다. 즉 목록 포함 bit29, 이동 허용 bit30, 탐색 준비, 별도 공통 허용 flag를 구분한다. flag의 진행상 이름과 각 장면에서 이를 쓰는 모든 명령은 이번 범위에서 확정하지 않았다.

구역 머리 항목은 타입2 행에서 별도로 만든다. `flag(구역+0x60)`과 유효 구역 조건을 확인하며 구역7은 save No249 조건도 있다. 같은 구역의 첫 적격 행을 보존한다. 장소 행은 signed 표시 순서의 오름차순으로 정렬하며 같은 순서 값은 이 비교에서 교환하지 않는다. 500행 중 타입 분모는 −1:329, 0:92, 1:44, 2:35다. 그중 타입1이며 구역0..7인17행의 이동 map/position 쌍은 아래 재매핑 표의17개 선택 쌍과 정확히 일치한다. 이는 정적 연결 전수 대조이며 현재 진행에서17개가 모두 개방된다는 뜻이 아니다.

근거: `ev_1258ab5b1293026cd3b084bb8b7e61966f7f58e4b92daff65f30c97e7fe4bfd1`, `ev_9b48e7147b002602b51fb9a9774cc7130522e30f3443a25449d00e35d7900507`, `ev_bafe286d80cca9c7cc0df7031841d87b01d95bfd21bfcd9e23eaeb07bfcbcb71`. 열 getter 근거와 전체 행 연결은 외부 `native/map_travel_gate_findings.json`에 있다.

## 빠른 이동 재매핑의 두 검색 순서

`478c90`의 첫 검색은54행 전체를 순회한다. 두 signed 최소 상태가 현재 값 이하이고 **원래 선택 map/position**이 같으면 목적 map과 위치를 덮어쓰며, 중간에 멈추지 않는다. 따라서 **마지막 조건 일치 행**이 이긴다. 출력 목적지를 다시 검색 키에 넣는 재귀 재매핑도 아니다. 일치 행이 없으면 map은 원래 선택값, 목적 위치는−1이다.

현재 요청 map과 이 결과 map이 같으면 남은 목적 위치를 `407a80/406490`에 전달한다. 다르면 별도 검색에서 **최소 상태16a0가0인 첫 행**을 찾아 그 목적 map을 요청+0x5e28에 쓰고 +0x5e2a를0으로 한다. 이 두 번째 검색은 최소 상태1704를 검사하지 않으며 처음 일치하면 멈춘다. 첫 검색의 목적 위치+0x5e2c는 이 분기에서도 남는다. 그러므로 논리적 최종 목적 map과 다른 맵 전환의 기본 요청 map을 같은 숫자로 일반화하면 안 된다. 이후 wrapper와 MAP 로딩 경로까지 거쳐야 실제 로드 자원을 결정할 수 있다.

54행은17선택 쌍이고 각 쌍에는 최소16a0=0인 행이 정확히1개다. 최소1704는54행 모두0이다. 예를 들어 선택(0,0)은 최소16a0의0/4/6 행이 차례로 map4/74/50을 낸다. 상태6이면 첫 검색 결과는50이지만 다른 맵 분기의 기본 요청은4다. 이 예제는 상태 번호의 줄거리 의미를 명명하지 않은 기술 대조다. 경계 상태153개와 확정 gate 조합64개를 정적 계약으로 계산·검사했으며 native 실행이나 실제 경로 도달 검증으로 세지 않는다.

근거: `ev_1e2569f99e90edbee790599afc84e8e6de22010a350f79d0c1963cc3cd1d09ea`. 전체 offset·선택 쌍·경계값·계산 한계는 외부 `native/map_travel_gate_findings.json`에 보존했다. 이 후속 분석에서는 원본 실행·UI 조작·프로세스 읽기·신규 자산 추출·렌더를 하지 않았다.

## 공통 이동 허용 flag의 실제 이름·초기화·대본 작성부

앞 절의 numeric flag0x8f는 본편 `game_resident/game_resident.spc/flg_label.dat`의507행 중 `flgMapExitCross → FLG_NAME →143`과 일치한다. main FLG464b60의 category8 이름 해석과 `working+0x6c0+4*(143>>5)` 쓰기가 getter478300의 `+0x6d0 bit15` 읽기에 연결된다. 일반 bit 저장 후 이 이름의 특수 가지는 추가 동작 없이0을 반환한다. 이름에 Cross가 있다는 이유로 금지 비트라고 뒤집지 않는다. 지도 목록 생성414690은 이 비트가 켜져야 이동 허용을 유지한다.

초기화53cf60의 mode0/1은0x97a0바이트 채움 경로 뒤 `+0x6d0 |=0x80008000`으로 이 비트와 다른 비트159를 켠다. 신규 context47a150은 실제 working 포인터+0x8f8을 context+0x970으로 정하고 mode0 초기화한다. 저장 상태 복원482190은 저장 블록을 복사한 뒤 원래 인수mode를 전달한다. 의사코드가 이 호출의 두 번째 인수를 생략했지만, raw의 MOV EDI,EDX와 호출 직전 MOV EDX,EDI로 전달을 확인했다. mode2/음수 등의 다른 동작까지 항상 기본값으로 초기화한다고 해석하지 않는다. 기본 비트가 켜져도 장소bit30·탐색 준비·표시 타입 조건은 여전히 필요하다.

## 진행표가 지도 상태를 만드는 순서와 중복 행 반례

native472650을 기준으로 캐시 MPF 3표를 함께 계산했다. 설정294행은 고유 상태288개이고, 동일3키가6쌍이다. 그중5쌍은 내용도 같지만 상태(1,31,0)의 행56/57은 다르다. native는 첫 일치에서 중단한다. 뒤 행으로 덮어쓰는 계산을 대조하면 word100은0x30000000 대신0x20000001, word154는0x20000000 대신0x30000000이 된다. 표시bit29가 같아도 인물bit와bit28이 달라지므로 중복을 병합하거나 마지막 행 우선으로 읽지 않는다. 기술 상태 숫자의 줄거리 의미는 여기서 명명하지 않는다.

함수는 먼저1000개 word의 낮은31bit를 지우고bit31만 보존한다. 단 chapter1·scene20..102에서는 기존 word4의bit17과word26의bit29를 따로 남긴다. 따라서 같은 진행3키라도 이전 상태에 따라 결과가 달라질 수 있다. 이후 첫 일치 설정행으로 인물16lane·bit28 세 lane·빠른 이동17slot을 세우고, 정렬된 cursol표는 현재키 이하 행을 순서대로 누적한다. code−1에서 해당 행의 목록을 끝내고,1000미만은 표시bit29를 켜고1000이상은1000을 빼서 끈다. 단일 최근 행만 선택하는 방식과 다르다.

mpf_map의 앞43행은 누적 상태bit와5개 충돌bit 해제 규칙을 처리한다. 마지막8행은 지도word와 별개로 공통 flag96..103을 조건에 따라 켜거나 끈다. 설정의17개 hardcoded 빠른 이동 slot은 TechouMap의유효 구역·type1 17행saveNo와 정확히 같다. WAK474af0의 진행 상태 변경에서 이 갱신을 부르지만 모든 파일 진입이 곧 갱신이라는 뜻은 아니다.

저작된288상태의 기본 계산과 해당 조건의이전값3조합 추가108개를 외부 `native/map_progression_table_findings.json`에 보존했다. 기본 계산은 기존bit31·특수 보존bit가0인 가정이며 실제 저장 상태·날짜별 도달성·현재 UI를 관찰한 결과가 아니다. 최종 이동은 여전히 탐색 준비와 flgMapExitCross를 거친다. `close_map_progression_tables.py`는 원본 payload SHA·폭·행수·cursol 정렬·17slot 연결과 중복 반례를 대조한다. 근거는472650과474af0 및414690의 기존 Evidence이며 신규 원본 실행·추출·Game 변경은 없다.

### 갱신을 요청하는 대본 명령과 이전 모드 의존

WAK474af0은 wak050_scene 또는 wak051_detail이라는 이름에 대한 대입 뒤, 현재wkMode가1일 때472650을 부른다. scene 대입은 먼저detail을0으로 만들고, detail 대입은scene을 지우지 않는다. 이 이름별 분기는 이전값과 새값이 다른지 비교해서 막지 않으므로 같은 값을 다시 써도 갱신을 요청한다. wkChapter 대입 자체에는 이 호출이 없다.

실효 기술 대본의 해당 명령은 scene205/detail107, 총312곳이며 모두 숫자 literal을 `=`로 쓴다. 선택한 자유행동 시작23개는 첫 명시적 제어 분기 전에 chapter·scene을 대입하고 대응 MPF행이 있다. 이 중16개만 앞서wkModeTansaku를 직접 대입하며7개는 이전mode1을 필요로 한다. 이 연결은 정상 본편 base mode라는 가정에서의 상태키이며, 갤러리/장 선택의 chapter override나 앞선MOD의 scheduler까지 재현했다는 뜻이 아니다. 따라서 파일 진입이 곧 동일한 지도 상태나 초대 가용성이라는 결론을 내리지 않는다. 외부 원장에23prefix의 SHA·명령offset·첫MPF행·mode상속 여부와312명령 위치를 보존했다.

## 유메노쿠니에서 바꿀 것

- `Game/Source/Explore.hpp`의 `showMap()`, `mapAt()`, `mapPreview()`는 표시 좌표·선택 위치·이동 목적지를 구분한다. 현재 방과 개방 상태를 반영해 진입 시 선택을 정한다.
- `Game/Source/Pad.hpp`의 지도는 장소 선택과 인물 찾기를 같은 장소 자료에 연결한다. 인물 선택에서 취소·확정·불가 조건이 유지되어야 한다.
- `Game/tools/create-project.mjs`의 지도 위젯은 구역 전환, 선택, 페이지 이동, 전환 중 입력 대기를 따로 표현한다. 최대6개 표시라는 수치를 전체 장소 제한으로 옮기지 않는다.
- 공간 지도를 임의의 원형 점이나 목록만으로 대체하기 전에 원작 UI 자산의 좌표 변환·실제 합성 화면을 확인한다. 이 문서는 분석 결과이며 해당 게임 코드를 수정했다는 뜻이 아니다.


## 대표 지도 표현과 이동 왕복의 정적 재구성 계약

기존 지도 입력·허용·재매핑 자료에 SFL 표현과 좌표 소비를 연결했다. 외부 `native/pad_presentation_contract.py`는 본 절과21의 통합 범위에서 REA28건·정적 범위10개·기존 SFL63개 carrier를 검증한다. `pad_presentation_findings.json`, `pad_presentation_raw.json`, `pad_presentation_sfl_contract.json`은 근거 ID·바이트 해시·라벨/배치/변환·색 정보를 보존한다. 원작 실행·신규 추출·렌더를 수행하지 않았다. 동일 모델의 코드가 아니라 retained 대상의 정적 소비 근거이며 최종 물리 픽셀/실청취는 주장하지 않는다.

`414040`의 상태1은 현재 위치로 구역·장소를 맞추고 해당 `techou_map_000..007` 자원을 요청한다. 준비 뒤 본체·구역·장소목록·인물목록·지도 자원의 입장 라벨을 요청하고, 본체 완료 후 현재 행 강조와 인물 수 표현을 적용한다. 구역 전환 상태8은 새 지도 자원의 준비가 끝난 뒤에만 선택 상태6/7을 다시 연다. `417de0`은 icon handle의 준비·layer 설정을 담당하며 마커 좌표 계산 본체가 아니다.

실제 재배치 `418ac0`은 현재 구역의 각 장소에서 `530c80/530cb0`으로 TechouMap X/Y를 읽는다. 장소 표시·빠른 이동 point·인물·그룹 좌표 배열을 서로 구분하며, 이동 허용값에 따라 point의 `fl_wait_off_on` 또는 `fl_wait_off_n`을 선택한다. 인물 bit에서1명이면(x,y),2명이면(x−30,y)/(x+30,y),3명이면(x,y+30)/(x−30,y)/(x+30,y)에 인물 표시를 놓는다.4명 이상은 개별3개 규칙을 반복하지 않고 그룹 마커로 표시한다. 인물 원본 그림은 현재 구성에 맞게 선택해 `p_dot_chara`와 `p_dot_chara_shadow`에 바인딩하며, 이 위치를 게임 월드 좌표로 혼동하지 않는다.
