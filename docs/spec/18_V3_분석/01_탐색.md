# 01 — V3 탐색 공간·배치·충돌 분석

## 확인한 것과 아직 확인하지 않은 것

설치본의 실제 공간 리소스는 3D 메시, 노드 트리, 행렬 배열, 충돌 기하, `place.dat`의 시작 위치·카메라·인물·물체·구역 값으로 구성된다. 유메노쿠니의 현재 배경 이미지 패닝과는 자료 구조부터 다르다. 이번 분석은 이 데이터를 원본 바이트까지 추적했다.

반면, 이 문서는 실제 실행 화면을 관찰해서 이동 조작·카메라 추종·가속·계단·충돌 반응을 측정한 완결된 플레이 규격은 아니다. 특히 작업지시서 17에 적힌 **캠퍼스 3인칭**이라는 목표 표현을 이번에 확인한 관찰 결과로 다시 인용하지 않는다. 아래 native 연결로 위치 기반 이동 시점과 고정 중심 시점의 차이까지 확인했지만, 최종 보이는 외형은 실제 플레이 화면과 구분한다.

## 공간 자료의 실제 연결

`partition_data_win.cpk`의 `model/bg/<공간>.SPC`를 기준으로 `model.srd`/`model.srdi`, shader SRD, texture SRD/SRDV, `place.dat`, `text.stx`, SAN 등이 묶인다. 가변 물체는 `obj000_model.srd`, 별도 shader/texture/animation처럼 분리된 실제 사례가 있다.

확인용 대표 파일은 저장소 밖 다음 위치다.

| 공간 | 파일 | 확인 내용 |
|---|---|---|
| 학교 복도 | `C:/Users/kirby/Downloads/v3_re/resources/ID001_sch_1F/` | 본체 VTX 381, MSH 381, TRE 2, COL 3. 별도 가변 물체 2개도 해독 |

전체 SRD carrier 10,937개는 SHA가 다른 본문 8,553개로 연결된다. 블록의 헤더·범위·알려진 payload를 모두 읽었다. SRDI/SRDV 참조 범위 425,451개와 inline shader payload 범위 32,464개, 합계 **457,915개가 모두 경계 안에 있다.** 원작 shader의 의미나 모든 스켈레톤·애니메이션을 이해했다는 뜻은 아니다.

## place.dat: 화면 위의 점이 아닌 공간 데이터

`model/bg/` 안의 `place.dat`는 **236 carrier, 서로 다른 본문 138개, carrier 기준 총 16,430행**이다. 같은 내용의 지역화/중복 carrier도 경로를 유지했다. 전체 값은 `resource_catalog/all_place_tables.json`에 있다.

대표 형식은 `種類`, `No.`, `float1`부터 `float8`, `ascii`, `int1` 열이다. 종류 문자열은 제작자가 붙인 데이터다. 종류가 알려져도 `float1..8` 전체의 의미를 추측해 이름을 바꾸지 않았다.

| 종류 | 해독해서 보존한 내용 | 해석의 한계 |
|---|---|---|
| `操作`, `キャラ表現` | 모드 관련 `int1` 값 | 모드 0/1이 어떤 입력·렌더링을 뜻하는지 전체 소비 경로 필요 |
| `カメラ上下角度制限` | 카메라 수직각 제한 두 값 | 원문 라벨·숫자는 확정. 엔진 축 부호·도 변환 경로와 결합해야 함 |
| `画角` | 화면각 값 | 공통 투영의 가로 전체각은 [08](08_카메라.md)에서 확인. 장면별 aspect override·최종 표시는 별도 |

| `開始位置`, `注視点座標` | 시작 배치·시선 관련 번호와 값들 | 뒤 native 절에서 XYZ·시작 yaw/pitch·FOV·제한을 연결함. view 축은 [08](08_카메라.md), 실제 최종 화면은 별도 |

| `オブジェクト`, `背景オブジェクト` | 물체 번호·값·노드 이름 | 원형/사각형/메시 판정 방식은 int1과 native 소비 함수를 함께 확인 |

| `影`, `環境光`, `平行光源` | 조명 관련 값 | 모든 float를 색/위치로 단정하지 않음 |

인물 `place.dat` 위치는 native에서 X에 -0.01, Y/Z에 +0.01을 곱하고 각도 부호를 바꾼다. 아래 실행 코드 절에 원시 명령 근거를 적었다. **세계 단위를 미터로 확정하지 않았고**, raw mesh·모든 place 행에 같은 변환을 무조건 적용하지 않는다.

## 노드·공유 행렬

공개 SRD parser는 TRE의 행렬 한 개만 읽는다. 설치본을 추가 조사해 각 TRE의 matrix pointer부터 첫 node name pointer까지 **64바이트 단위의 공유 4×4 행렬 배열**이 존재함을 확인했다. branch의 기존 `unknown0c` 값은 이 배열의 index 범위 안에 있다.

- TRE를 가진 서로 다른 SRD 1,431개.
- TRE 블록 1,670개, 공유 행렬 19,870개.
- 배열 경계의 64바이트 정렬·모든 branch index 검증 오류 0개.
- 복도는 공유 행렬 3개와 23개의 TRE 두 개, 교실은 90개의 TRE 한 개.

행렬·node 이름·부모 depth·leaf 연결·절대 바이트 오프셋은 `resource_catalog/trees/<SHA>.json`에 있다. `tree_summary.json`이 공간 carrier로 연결한다. 초기 구조 조사에서 보존했던12~14번 float는 뒤의「TRE 행렬의 순서와 실제 검증 경계」절에서 local translation으로 연결했고, native 소비도 row-vector `local @ parent_world` 순서로 확인했다. **실행 중 외부 root/SAN·일부 pointer-sharing flag·원작 최종 visibility는 미재현**이다. 상속 곱 자체의 확인과 scene 전체 runtime 복원을 구별한다.

메시의 정점·인덱스는 실제 SRDI 범위를 읽어 OBJ로 내보냈다. 대표 공간들과 공통 소품에서 621개, 재판장 비교 공간에서 799개를 내보내 정점 범위·삼각형 index·유한 float를 확인했다. 결과는 **원본 local geometry**이며 rig·material·scene transform을 적용한 완성 scene이 아니다.

## 충돌 기하

공개 SRD parser가 opaque로 남긴 `$COL`을 원본 바이트로 독립 조사했다. 아래는 설치본 전체 505개 COL에서 일치한 구조 추론이다.

1. 24바이트 헤더: `u16 version, u16 unknown, u32 nodeOffset, u16 nodeCount, u16 leafCount, 3×u32 unknown`.
2. 32바이트 node 배열: `6×f32`의 min/max bound와 아직 의미가 확정되지 않은 `2×u32` tree link 값.
3. leaf마다 `u32 vertexOffset, u32 indexOffset, u16 vertexCount, u16 indexCount`; 정점 데이터는 16바이트 정렬.
4. 정점은 `4×f32`의 XYZW, index는 u16. `0xffff`가 strip을 나눈다.

**서로 다른 SRD 81개 안 COL 505개, 정점 37,590개**에서 모든 정점·인덱스 경계와 payload 끝까지 검증했고 오류가 없다. `resource_catalog/collision_summary.json`과 `collision/<SHA>.json`에 근거 오프셋·전체 수치가 있다.

복도의 세 COL을 collision OBJ로 따로 내보냈다.

| COL | 정점 | strip에서 구성한 삼각형 |
|---|---:|---:|
| 바닥 계열 node | 48 | 40 |
| 벽 계열 node | 378 | 282 |
| 닫힌 문 계열 node | 16 | 8 |

node 이름에 연결된 RSI local property는 `Op2MapCollisionParameter`이고 대표 값은 4바이트 정수 7이다. 이 값을 float로 재해석하면 극소수가 되므로 물리 계수로 사용하면 안 된다. 이 자산 속성만으로 tree link bitfield, front/back 판정, 마찰·계단 정책을 해독한 것은 아니다. 수동 이동의 기본 형상·sweep·법선 속도 보정은 뒤의 native 절에서 별도로 확인했다. 충돌 메시의 존재·일반 solver 기능·실제로 실행하는 수동 응답을 구별한다.

## 실행 코드에서 확인한 조사·치기·빠른 이동

전체 게임 sequence `0x140456d80`은 탐색 모드의 `HelpTansaku3D/25D`를 선택하고, 탐색 manager `0x140405dd0`의 결과를 조사 script 실행 `0x14047b060`으로 넘긴다. 클래스에 붙은 TitleSequenceTask라는 이름만 보고 제목 화면 전용으로 제외하면 안 된다. 이 연결은 파일 분류가 아니라 실제 게임 진행 분기의 정적 근거다(`ev_23d247969dbd7a0b9da1eb6889fecf67cdc863969eaa28a85aa9331c16020782`).

`0x14040c470`은 물체 reaction 상태 기계다. 상태1에서 효과음 `V3_SE_075`와 `0x14040c680` 연출을 시작한다. 상태2에서는 대화 UI의 준비 조건을 기다리고, 탐색 manager +0x240의 target ID로 물체를 조회한 다음 `0x1403bdf30` 자격 조건을 검사한다. 이어 `0x14040c6f0`, `V3_SE_076`을 호출한다. reaction 적용 분기에서는 물체 +0x94가 양수이면 줄이고 별도 UI 통지를 하며, +0x88 내구도를 1 줄여 0 아래로 내려가지 않게 한다. 남은 내구도가 양수이면 중간 reaction, 0이면 종료 reaction과 `ObjectReaction` 경험치/진행 통지 및 저장 변경 경로로 간다. +0x94는 지급 요청 stock이며, 영속 stock 검사·코인 지급과 상한 999·소진 물체의 재선택 차단은 [19_본편성장.md](19_본편성장.md)의 「물체 타격의 메달·반응 완료·경험치」를 따른다(`ev_e50288ab79428ff50867232b08fafad5b819ca4545cf8ffaddd0a2faf947c187`).

치기 UI의 `0x14040c680`은 UI 함수 `0x14035f060`의 kind4와 speed2.0을, `0x14040c6f0`은 kind5와 speed1.0을 넘긴다. 이 두 float는 캐릭터의 이동 속도가 아니라 해당 연출 소비값이다. 대표 조사·치기·대시의 물리 입력과 허용 조건은 후속 [13_입력.md](13_입력.md)에 연결했다. 모든 버튼 반복 상황·하위 hit/ray geometry·실제 거리 판정의 전 과정까지 검증한 것은 아니다.

빠른 이동 `mapjump_data.dat`는 54행×12바이트다. `0x140478c90`은 행의 첫 두 signed16 값이 현재 상태 +0x16a0/+0x1704 이하인지, 다음 두 값이 선택 map/position과 같은지 검사하여 마지막 두 값을 목적 map/position으로 쓴다. 이 첫 검색은 **마지막 조건 일치 행**을 쓰며, 다른 맵 분기의 선두 상태0 fallback은 **첫 일치 행**에서 멈춘다. 같은 장소로 이동하는 경로와 다른 맵을 로드하는 경로를 구별하고 전환 중 입력을 제한한다. 목록 포함·이동 허용 bit와17개 선택 쌍의 전수 연결, 두 검색 순서의 차이는 [15_패드지도.md](15_패드지도.md)의 후속 절을 따른다. 입력 상태 enum의 전체 이름이나 실제 지도 클릭 key를 추측하지 않는다(`ev_1e2569f99e90edbee790599afc84e8e6de22010a350f79d0c1963cc3cd1d09ea`).

`0x140414690`은 지도 자료와 MPF 진행 bit를 8개 UI 그룹으로 정리·정렬한다. 현재 방의 그림 UV를 임의 원형 점으로 바꾸는 현재 구현과 다르다. MPF 전체 3종·보너스 stage 105종·탈출 15종의 실행 소비 근거와 parse 범위는 [10_보너스와_비정형_DAT.md](10_보너스와_비정형_DAT.md)에 따로 기록했다.

위 근거는 복원 실행 파일의 정적 분석이다. 실행 캡처에서 조작·프레임 시간·충돌 응답을 직접 측정했다는 뜻이 아니다. renderer tick에서 모델 위치/회전/scale를 갱신하는 경로까지 보았지만, draw-call 수·culling 효과·프레임 성능은 아직 측정하지 않았다.

### 조사 마커의 투영·선택 가능 조건

`0x140404440`은 object +0x2c/+0x30/+0x34의 위치를 homogeneous 좌표로 만들어 `0x1404a04d0`에 넘긴다. `0x140404390`은 투영 결과에 대해 `0<x<=1920`, `0<y<=1080`, `depth>0`을 검사한다. 또한 depth가 manager +0x330이 가리키는 객체의 +0xc0 이하인지 검사하며, 이미 marker ID를 가진 항목에는 깊이 한계에 1을 더한다. 이어 object +0xf0이 1이 아니고 +0xf4와 +0x58이 0이 아닌 경우만 허용한다. 허용 항목은 `0x140403fa0`으로 marker를 만들고, 조건에서 벗어나면 UI와 manager에서 기존 marker를 없앤다.

따라서 실제 조사 표시에는 화면 범위·깊이·object flag가 관여한다. 1920×1080은 **이 native 조건의 논리 화면 범위**로 확인한 값이며, 모든 SFL 좌표를 이 viewport로 변환하는 전체 식을 확정한 것은 아니다. 이 함수를 실제 raycast·클릭 반경 그 자체라고 부르지 않는다. 근거는 `ev_76bf88f1f3960a29181a2c2f6e08c4ab343f73bd6da06032652e40c7d98eb46d`, `ev_d49ddc2f840625e424f6ef7de6a76c27a60ec0b454e4de0aeae5de40f7162262`다.

치기 자격 `0x1403bdf30`은 object +0x84가 0이면 즉시 거부하고, +0x19c의 연결 대상이 유효하면 해당 entity +0x60이 0인지 확인한다. 연결이 없으면 이 추가 제한을 통과시킨다. flag의 외형상 의미를 임의 명칭으로 고정하지 않는다(`ev_fddc04c0d77fcbd08aaffae1e40e139531ab03056ab2cb6d4ffd5f3c31351aee`).

마커 allocator `0x140403fa0`은 manager +0xa8부터 **6개 signed32 slot**을 검사한다. 같은 target ID가 있으면 그 slot을 재사용하고, 없으면 값이 -1인 첫 slot에 넣는다. 모두 차 있으면 -1을 돌려준다. 이것은 화면 조사 마커의 pool 수이며 현재 유메노쿠니의「방 인물 최대 6명」과 같은 규칙이라고 간주하지 않는다(`ev_7bc6d691c7980ae1491649c8f5b25519318ec74ea6571cbefb9527cdbdfdf98a`).

### 일반 탐색 tick과 이동 종류

전체 게임 update `0x1403bc280`은 input/model/camera manager와 함께 탐색 tick `0x140406860`을 호출한다. 탐색 active +0x21c가 0이면 tick을 건너뛴다. +0x220 mode가 0이면 일반 상태 기계 `0x140409240`, 3이면 자동 연출 `0x140408c00`, 5이면 경로 이동 `0x1404082b0`으로 간다. 일반 탐색에서 별도 +0x90 값 1/0에 따라 입력·위치 적용 함수가 갈라진다. 두 state 필드를 혼동하면 안 된다.

일반 상태 기계는 인물 target +0x238을 먼저 보고 `TalkCharacter`를, 없으면 물체 target +0x240으로 `CheckObject`를 기록한다. 조사 시작·종료를 구별해 결과 state를 만들어 상위 sequence에 넘긴다. 물체 reaction 가능 여부 +0x84 때문에 일반 조사와 치기가 다른 입력 경로로 갈라진다. 대화·연출이 완료되기 전에는 다음 조사 state로 진행하지 않는다.

mode5는 선택 경로의 지점들을 순서 또는 역순으로 읽어 XZ를 한 step씩 이동하고, 도착 거리가 step 이하이면 정확한 지점으로 맞춘다. 지점 사이 Y를 거리 비율로 보간한다. +0x25c가 켜지면 step을 0.5배, +0x28c가 켜지면 +0xec 배율을 적용한다. yaw는 ±180도 범위에서 최단 방향을 택하고 차이가 0.1도 이상일 때 차이×0.1, 또는 +0x25c 조건에서는 ×0.05로 접근한다. pitch는 매 tick 0.9배, 절댓값 0.1 미만이면 0이다. 이 수치는 **자동 경로 소비 함수의 native 상수**이며 일반 수동 걷기 전체의 속도라고 부르지 않는다.

`0x14040ba70`은 탐색 위치·각도·mode 관련 값을 상태 +0x8920..+0x895c에 복사한다. `0x14040c2a0`은 yaw를 0..360도로 정규화하고 pitch/180 등을 shader 상태에 전달한다. 두 함수는 입력 읽기가 아니라 진행 상태 보존과 화면 효과 적용이다.

근거: tick `ev_8bf2a42215ca22dbdcead84542b5429338719a54f7931c2d922f19aad79a237a`, 일반 탐색 `ev_99e55cd0271aea076b0ec4578b58d79fdd906d1d2b9797cec5d88abb4af177f3`, 경로 이동 `ev_c50022d4a7ae5eea3ec2bc32f1b6b9989506651befb341219e89e78fa073eff0`.

### 수동 이동·시점 보간의 실제 수치

`0x14040a120`은 +0x90=1 경로의 수동 입력을 소비한다. 매번 cursor 상태를 (960,540)으로 놓고 다음 공식을 적용한다. 아래는 **tick당 계산**이다. 전역 scheduler `0x14049d550`의 QPC/QPF 기반 임계는 16,666.666015625µs로 nominal 60Hz이며 여기서 전체 update `0x1403bc280`이 호출된다. frame drop 시 실제 진행이나 UI 독립 속도까지 실행 측정한 것은 아니며, 물리 단위와 solver 시간 변환을 확인하기 전 meter/s 수치로 바꾸지 않는다(`ev_7893bfe3fdbee7442a02aa26af49c7373a021075b91b367a5f3eca94b85a153c`).

| 대상 | native 계산 |
|---|---|
| yaw 입력 | input `0x1403c2de0` 값×2. target을 향해 `v+=(target-v)*0.5`; 입력 0이면 `v*=0.6`, `abs(v)<0.001`이면 0 |
| yaw 각도 | `yaw+=v`, 0 이상 360 미만으로 wrap. +0xf8 제한이 있으면 이 입력 건너뜀 |
| 이동 속도 target | 입력 벡터 길이×필드 +0xe8. run predicate `0x1403c9260` 또는 +0x378 조건이면 ×필드 +0xec |
| 이동 속도 보간 | `speed+=(target-speed)*0.5`; 입력 0이면 `speed*=0.5`, `abs(speed)<0.001`이면 0 |
| 이동 방향 | 입력 벡터 각도+yaw를 0..360으로 wrap하여 +0x80에 보존 |
| 걷기 phase | `phaseRate=(speed/baseSpeed)*field_f4`. +0x25c 조건이면 0.75배 |
| pitch 입력 | input `0x1403c3080`을 0.5 보간. 입력 0이면 0.5 감쇠, `abs(v)<0.05`이면 0 |
| pitch 복귀 | 시점 유지 조건이 없으면 `pitch*=0.9`, `abs(pitch)<0.1`이면 0 |
| pitch 제한 | 필드 +0xb8/+0xbc 순서를 맞춘 뒤 범위 안으로 clamp |

이동 상태가 참일 때 실제 좌표·충돌 경로 `0x14040c180`을 호출한다. baseSpeed의 place→runtime 필드 연결은 아래 「place 설정의 기본값과 수치 해석」에서, 실제 키/축 변환은 [13_입력.md](13_입력.md)에서 확인했다. 물리적 meter 단위와 실제 보행 시간의 대응은 별도 미확정이다. 여러 입력 fallback에 5/10/30 tick 상태도 있으므로 단순 키가 눌렸다는 사실만으로 속도 배율을 전부 설명할 수 없다.

+0x90=0 경로 `0x140409c50`은 별도의 시점 입력을 읽고 `0x140408ad0`으로 look-at 중심(+0x94/+0x98/+0x9c)과 반경 +0xa0에서 카메라 위치를 계산한다. 자유 걷기와 같은 식으로 취급하지 않는다. +0x90=1의 `0x140409010`은 현재 world position과 높이 +0xe4, 설정 predicate에 따른 phase 기반 흔들림을 적용한다. 흔들림 phase는 180도 주기로 wrap하며 멈출 때 최소 8도씩 중립에 복귀한다.

입력·보간 근거 `ev_e4d8a295a929f4f0d0b96ea8d09d9074b338d41ac85067dd6cef9c5e1a4fdfa9`, 고정 중심 카메라 `ev_9ecbfcf48b39e668751bf8bd0848e2a00cd8d491a16f50f4827690a1e4e279d3`, 위치 기반 카메라 `ev_4c6c1d37c86a8fe9a9a309ab320e83cb8f540760f06aac30dbff9c832a5d56e3`.

### 커서 속도·흡착과 충돌 bridge

고정 중심 탐색의 cursor `0x14040ac40`은 입력 벡터의 방향과 길이를 읽고 `aimSpeed(0x140407c80)*magnitude*10`만큼 이동한다. target 후보가 있고 magnitude가 0.7 미만이면 magnitude를 6으로 나눠 정밀 조작한다. X는 0..1920, Y는 0..1080으로 clamp한다. 입력을 멈춘 뒤에는 target ID·유지 시간·이전 cursor 위치 조건을 확인하고, 목표점까지 거리가 10보다 크면 한 tick에 10씩 접근하고 작으면 정확한 목표점으로 맞춘다. 이 조건은 아무 대상에나 무조건 10px 보정을 거는 규칙이 아니다. target 이력 counter는 100을 넘지 않으며, 일부 흡착 경로는 counter가 12 이하일 때만 진행한다(`ev_534f3b0bb83e8e917d095f2926e7af5bb8992b61c24728eefdb9f8db24d1aeb5`).

`0x14040aac0`은 cursor로부터 `0x1404ff3b0`의 두 벡터를 만든 뒤 `0x14040bb50`에 넘겨 인물·물체 target을 갱신한다. 새 target의 전환 효과음은 별도 8-tick 조건을 갖는다. 이 점까지는 screen cursor와 공간 선택 소비가 연결된다. 최종 hit geometry는 아래 함수 내부의 추가 근거가 필요하다(`ev_85790c58034b52ed1e8f273b4edfd3be8787ef7520986e1af2f78283b859478b`).

이동 `0x14040c180`은 `velocityX=sin(direction)*speed*60`, `velocityZ=cos(direction)*speed*60`, vertical 값 +0x2bc를 만든다. 현재 position vec4와 필드 +0xfc/+0x100을 `0x140405090`에 넘긴 뒤 수정된 position과 vertical 값을 반영한다. 따라서 ×60 상수는 이 bridge에서 실제 존재하지만, 그 사실만으로 mesh 단위를 meter로 확정하지 않는다. 충돌 소비 내부의 시간·공간 변환을 함께 확인해야 한다(`ev_b9ca36c7e852cc78052775be730b26f0ac59597b0c8128a56ee7f9650a78489d`).

### 공간 선택과 충돌 응답의 native 연결

`0x14040bb50`은 먼저 캐릭터 hit manager `0x140383dd0`를 조회하고, 실패하면 물체 hit manager `0x1403bfc40`를 조회한다. 자유위치 모드에서는 캐릭터의 추가 조건과 물체 거리(+0x128 한계)를 검사한다. reaction 가능 flag +0x84가 켜져 있는데 내구도 +0x88이 1 미만인 물체는 선택에서 제외한다. hover 표시용 target과 실제 target은 별도 필드다. 따라서 조사 표시·ray hit·내구도·script 결과를 하나의「클릭 원」으로 합칠 수 없다(`ev_8004a03ef19bcdf471e6afe2147193bee9980fb0c2e3f521565ad18475cf429d`).

`0x140405090`은 두 중심점과 radius를 가진 충돌 shape를 만든다. 입력 position의 Y에서 한 중심은 `Y+height-radius`, 다른 중심은 `Y+radius`로 잡고, +0xfc 인자를 radius 위치에 넣는다. map collision object를 조회하고 `0x1406250d0`/`0x140625c60`을 반복 호출한다. 충돌 normal과 velocity의 내적 성분을 velocity에서 빼는 slide 계열 응답을 확인했다. 수직 가속 성분에는 -9.8과 1.1111112 상수가 있다. 이것만으로 meters 단위를 선언하지 않는다.

같은 함수 뒤쪽에는 접촉 목록의 map 속성 +0x108 bit들을 0/1/2/3 등으로 분류하는 코드가 있다. 그러나 아래 후속 분석에서 **이 수동 경로는 목록 수집을 끈 채 호출하므로 해당 분류 목록이0개로 남는 것**을 확인했다. 이 분류 코드를 이 경로의 실제 발자국·지면 종류 소비로 확정하면 안 된다. 그 안의 조건도 `-0.707 <= abs(normalY)`여서 45도 경사 제한이 아니다(`ev_9ca469c6302308a4d96bbae9b24d74200eb682475a15657cfb4c3678480a64fa`). 수정 position·velocity를 반환하는 경로와 실행되지 않는 목록 분류를 구별한다.

### place 설정의 기본값과 수치 해석

place 소비 함수 `0x140371ef0`은 「操作」를 기본 0, 「キャラ表現」을 기본 1, 「画角」을 기본 45로 초기화한 뒤 해당 행이 있으면 덮어쓴다. 「移動速度」 두 float는 기본 0.1과 2.0이다. 두 번째 값은 양수일 때만 기본값을 덮어쓴다. 수동 이동에서 base speed와 run 배율이 별도 필드이므로 복도의 `[0.1,2.25]`를「최소 0.1, 최대 2.25」로 해석하면 안 된다. 이 helper의 반환 필드가 manager +0xe8/+0xec로 옮겨지는 연결도 아래 실제 명령으로 확인했다(`ev_14668c2d0870b3b61da3926e7a9c8cc581880253d93b042add0a00ffc468d8ef`).

인물 place 소비 `0x140371140`은 위치 세 값, 각도, scale와 표현 설정을 별도로 읽는다. 좌표 helper `0x1403719a0..0x1403719d0`의 변환은 다음 절처럼 확인했다. table와 raw model을 변환 없이 같은 단위라고 가정하지 않는다(`ev_64a4b0e35b8ea117828b3c132816c6782d469fc4cc0fa1e639426f5f6306de6d`).

### place → runtime 좌표 변환 확정

복원 PE의 실제 명령은 위치 helper 세 개가 모두 `mulss xmm0,[constant]; ret`인 것을 보여 준다. `0x1403719a0`은 -0.01, `0x1403719b0`과 `0x1403719c0`은 +0.01을 곱한다. 각도 helper `0x1403719d0`은 -1을 곱한다. 인물 place를 읽는 `0x140371140`의 X/Y/Z/각도 호출과 연결하면 **runtime X=-placeX/100, Y=placeY/100, Z=placeZ/100, angle=-placeAngle**이다. 단순 100배 scale뿐 아니라 X와 각도의 부호가 바뀐다.

constant VA/원시 바이트는 각각 `0x140750934:0ad723bc`, `0x140714314:0ad7233c`, `0x1407118e4:000080bf`다. 외부 `native/place_scalar_conversions.json`에 복원 binary SHA-256, 명령 file offset·hex, constant VA·hex와 float32 값을 보관했다. 이 단위 변환으로 place의 180은 runtime 1.8에 대응하지만 단위 이름을 meter라고 자동 확정하지 않는다. raw OBJ에 이 변환을 무조건 한 번 더 적용하면 안 되며, mesh 자체와 TRE 부모 변환은 별도다.

설정의 runtime 연결도 실제 명령으로 확인했다. `0x140372df0`은 20바이트를 할당해 `0x140371ef0`으로 채운 뒤 설정 객체의 첫 포인터에 보관한다. `0x14040b720`은 `0x1403734d0`이 돌려준 객체의 첫 포인터에서 +0/+8/+12/+16을 각각 탐색 manager +0x90/+0xdc/+0xe8/+0xec로 복사한다. 따라서 「操作」→모드, 「画角」→FOV, 「移動速度」첫 값→base speed, 둘째 값→run 배율이 연결된다. **복도 2.25는 run 배율**이다.

manager 초기화 `0x140407ce0`의 기본값은 base speed 0.1, run 배율 2, 흔들림 크기 +0xf0=0.06, phase rate +0xf4=6, 충돌 radius +0xfc=0.5, capsule 높이 인자 +0x100=1이다. 실제 맵·상태가 이를 덮어쓸 수 있으므로 모든 방의 값으로 고정하지 않는다. 외부 `native/exploration_field_connections.json`에 세 코드 구간의 원시 바이트·Capstone 명령·offset과 SHA를 저장했다.

일반 solver `0x140623a00`에는 counter +0x200을 float로 바꾸어 `1/16384`와 `1/64`를 곱하고, `d=v*h+0.5*a*h²`에 따라 normal 조합·velocity 투영을 선택하는 코드가 있다. **수동 탐색은 solver+0x34=1이어서 이 함수의 제약 선택 본문을 실행하지 않는다.** 이 함수 자체도 position을 전진시키는 적분 함수가 아니다. 실제 수동 경로의 별도 `0x1406248b0`이 같은 h로 적용할 변위를 만들고, 무접촉 분기의 `0x140627fb0 → 0x14062ec80`이 capsule 양 끝 XYZ에 이를 더하며, `0x1406249d0`이 `v+=a*h`를 적용한다. 따라서 **full counter인 무접촉 수치 적분의 h=1/64**는 확정했다. 접촉 분할·다른 CAM 모드·물리적 실초는 별도이며, 이 결과를 전체「physics 64Hz」로 번역하지 않는다. 전역 nominal 60Hz와 내부 적분 구간을 구별하고 `base speed*60`도 최종 초당 이동 거리라고 확정하지 않는다. 실제 Y 갱신 guard와 조건부 수치 예시는 아래 추가 분석 절, 원시 명령·상수와 제한은 외부 `native/physics_time_conversion.json`에 있다.

일반 solver의 `0x140623650`은 접촉 목록에서 침투 보정 벡터를 구한다. 초기 threshold는0.01171875와0.00390625지만, 이 수동 경로는 목록이0개이므로 그 보정이 적용된다고 말할 수 없다. 이 값을 플레이어의 단차·경사 한계로 사용하지 않는다. 최종 REA 근거는 설정 생성 `ev_f41f9548cc391fc75f791299e7b11473389209e1368f32c1501f0ea635119e3e`, 설정 복사 `ev_9f5f68a86f19cb4a3ec30cf486bc4c877e43ac2f6206edadf4c249cbbc623c35`, manager 기본값 `ev_853665bc1376aa14a04c84ecd822d50733a9eabe524b542ab9d12fb5bf49650f`, 일반 침투 보정 `ev_f99e23a00e4908bc2f9887e1d1cfbad8a0573c280f558b8569e125c4f71ed0bc`, 일반 제약 예측 `ev_faa273b4a640b925a38498e96cccfead4745f5ebb500919f66d15b463b2e9af8`다.

## 물리 입력에서 이동·조사까지의 추가 연결

키보드 compiled 기본 배치 35행을 실제 프로그램이 생성한 config와 비교하여 모두 일치했다. `40a120 → 3c3260 → 3c32c0/3c33f0`의 수동 이동은 행동 19/20(A/D)과 17/18(W/S)을 읽는다. 대시 판단 `3c9260`은 왼쪽 Shift의 `move_dash` 및 조작 종류(+0x6a)에 따른 패드 버튼 조합을 사용한다. 시점 입력 `3c2de0/3c3080`은 조작 종류별 키·패드와 허용된 마우스 변화량을 선택한 뒤 X(+0x42f08)/Y(+0x6c) 반전값이 1이면 최종 축을 −1배 한다.

조사는 +0x90 모드 0의 `3c71c0`, 모드 1의 `3c9140`에서 새 클릭 또는 결정 비트를 받는다. 후자는 조작 종류 1에서 R1(기본 E/Space, XInput 오른쪽 Shoulder)도 허용한다. 입력 뒤 target +0x238/+0x240과 진행 상태를 통과해야 `TalkCharacter`/`CheckObject` 결과로 이어진다. 실제 입력·허용 조건·동작 결과를 연결한 표와 근거는 [13_입력.md](13_입력.md)에 정리했다. Enter/마우스 버튼 1로 +0x258이 토글되는 사실은 확인했지만 이 필드의 외형상 의미를 조사 모드라고 단정하지 않는다.

## 공간을 어떻게 플레이하는가: 복도·실내·야외 비교

이 절은 공간 기능을 설명하는 좌표 분석이다. 원작 화면을 보았다는 기록이 아니며, 원본 모델·텍스처를 렌더해 복제한 그림도 아니다. 원본 CPK에서 세 대표 `model.srd`를 다시 읽고 SHA를 확인한 뒤 COL·TRE·place를 비교했다. 수치와 plot은 저장소 밖 `map_experience/`에, 종합 결과는 `native/map_experience_findings.json`에 있다.

### 모드 이름과 실제 조작은 별도 필드다

`Map.dat` 164행은 `2.5D` 99개와 `3D` 65개다. native MAP handler는 이 문자열로 help/state 분기를 선택한다. 반면 실제 탐색 manager의 +0x90은 place의 「操作」에서 온다. base CPK의 place carrier 142개를 Map label과 연결하면 `2.5D/操作0` 83개, `3D/操作1` 52개지만 **서로 다른 조합도 있다**. `2.5D/操作1` 1개, `3D/操作0` 2개, 操作 행이 없는 3D 자료 4개다. 따라서 Map type 하나만 보고 걷기·고정 시점을 결정하지 않는다. 전체 비교는 `map_experience/map_type_operation_comparison.json`이다. 142는 base carrier 수이고, 앞 절의 138은 전체 place 본문의 SHA 중복 제거 수이므로 분모가 다르다.

Map label 나머지22개는 base place와 직접 매칭되지 않는다. 일부는 `test/maptest2/3`에서만 참조되지만 일반 chapter script의 참조도 있어 전부 테스트 잔재로 제외하지 않았다. 다른 모델 재사용·alias·미사용 분기 여부가 남아 있다. 동일 원장에22개 전부와 scope007 Load/Preload 참조를 보존했다. Map164를 설치된 독립 탐색 scene164개로 바꿔 세지 않는다.

대표 복도와 야외는 操作1이라 `0x14040a120`의 수동 이동→capsule 충돌→`0x140409010`의 위치 기반 시점으로 간다. 대표 교실은 操作0이라 `0x140409c50`의 시점 입력→`0x140408ad0`의 look-at 중심·반경 카메라를 사용한다. 교실의 「걸어가서 책상 사이를 통과한다」는 동선을 만들어 넣을 근거는 없다. player는 고정 중심에서 방향을 바꾸고 공간 target을 조사하는 경로로 해석해야 한다. 인물·물체 target은 공통 ray 선택 경로를 사용하지만 조작 조건과 거리 제약은 모드별로 다르다.

입구 적용 `0x140407a80`도 확인했다. 입구번호가0이상이면 settings를 갱신하고 `0x14040b7f0`으로 시작 배치, `0x14040b8c0`으로 look-at 배치를 따로 적용한 뒤 操作별 카메라 함수로 간다. 두 lookup의 실패 정책은 다르다. **시작 배치가 없으면 position과 yaw/pitch를0으로 만들지만, look-at은 요청번호가 없을 때 번호0으로 다시 찾는다.** look-at도 없으면 중심 X/Z=0, Y=추가 높이 필드, 반경=-5를 쓰고 각도 제한 flag를 끈다. 따라서 모든 누락 입구를 「0번 시작점으로 fallback」한다고 구현하면 틀린다.

look-at record의 중심은 manager+0x94/+0x98/+0x9c, 반경은+0xa0, 각도 두 끝은+0xb0/+0xb4로 간다. Y에는 manager+0xd8의 높이를 더한다. 각도 끝값을 정렬한 뒤 span이360 미만인지로+0xac 제한 flag를 정한다. 여기서 확인한 것은 **가공된 배치 record→camera field**의 연결이며, place의 모든 raw float가 record로 변환되는 전체 파서를 완료했다는 뜻은 아니다. 근거 입구 적용 `ev_0da66d21877c61d0922360a62565b67cd907c809d9f8204b5c9a8ee94c1aadf8`, 시작 적용 `ev_4e975862b067f6da24b0929b30f8b2e999dfc63f25da84dbb67b58e19ad72f39`, look-at 적용 `ev_a02ec25de62caf02d36f0600e1a82a310fc5da66caa48529d796e0772247e360`.

### 복도: 분기하는 이동 공간과 상태로 닫히는 통로

`ID001`의 바닥 계열 COL은 40삼각형, 벽 계열은 282삼각형, 별도 `door1_close_col`은 8삼각형이다. XZ 투영은 길게 뻗는 횡단 구간, 넓어진 중심, 꺾여 내려가는 가지로 구성된다. 단일 배경을 좌우로 패닝하는 것과 달리, 이동 방향을 바꿔 가지로 진입하고 해당 위치에서 물체·구역을 조사하는 공간 구조다. 바닥의 Y는 대체로 0이지만 양 끝 일부에 -1.2/+1.2까지의 높이 변화가 있다. 별도 닫힌 문 COL을 무시하면 실제 script가 통로를 닫는 상태를 재현할 수 없다.

0.5 단위 격자에 바닥 투영만 합치면 한 연결 성분이다. 좌표 상관 가정 아래 시작0→시작5의 투영 경로는 약46.14, 직선은43.25다. 반면 시작1과11은 현재 바닥 투영에서 각각 약34.00,27.08 떨어져 있다. 이 둘을 가장 가까운 바닥으로 강제 이동해「검증된 동선」으로 만들지 않았다. 미사용/상태별 시작점, scene 변환, 다른 공간 기하 중 어느 설명인지 추가 소비 확인이 필요하다. 모든 place 행을 현재 한 가지 충돌 상태에 맞는 입구로 취급하지 않는다.

### 실내: 노드에 묶인 조사 대상과 시점 전환

`ID017` model에는 COL이 없고, 고정 중심 카메라용 「注視点座標」가 두 행 있다. 물체 39행의 node 문자열은 **39개 모두 TRE branch와 연결**된다. 칠판·문·교탁, 책상16개와 의자16개가 따로 target 식별자를 갖는다. 같은 책상으로 묶어서 하나의 클릭 영역으로 만드는 구조가 아니다.

특히 node형 물체의 place XYZ가 모두0이어도 같은 원점에 겹쳐 놓인다는 뜻이 아니다. `desk_00`은 TRE matrix index58, `chair_00`은59를 참조하며 local translation이 각각 `(3.2484,0.5845,-6.0033)`, `(3.5764,0.6015,-5.6611)`이다. 뒤 절에서 상속 곱을 확인했어도 외부 root·실행 상태·camera ray까지 검증한 것은 아니므로 이 값으로 최종 screen hotspot을 선언하지 않는다. 대표 공간의 분석 plot에서는 node형 zero XYZ 물체를 원점의 점으로 그리지 않았다. 후속 전체 좌표 연락판은 원시 object 행 좌표를 표시하므로 node 참조·zero XYZ 주의사항을 함께 남겼다.

### 야외: 넓은 외형과 충돌 바닥 투영은 다르다

`ID249`의 COL은 ground4개와 wall3개다. ground0a는 중심 연결부, ground0b/0c는 길게 휘어 이어지는 양쪽 경로, ground0d는 좁은 이어짐을 가진다. 이 이름은 원본 node 이름이며, 재질·장식·분위기의 관찰을 뜻하지 않는다. 바닥 XZ 범위가 크다고 그 사각형 전체를 걸을 수 있다는 근거는 되지 않는다. 투영에는 넓은 빈 부분과 이를 돌아 연결하는 띠 모양의 바닥 기하가 있다. **그 투영 내부만 이동을 허용하는 nav mask라는 뜻도 아니다.** 아래 native 검증처럼 실제 충돌 shape·수직 적분·이동 중 갱신 조건을 함께 봐야 한다.

### VTX의 8바이트 선언과 UV 연결

native `0x1405bc160`은 VTX payload+4의 u16을 선언 배열의 시작 offset으로, +6의 u8을 선언 개수로 읽는다. 과거 `mesh_type`이라고 보존한 s16은 실제로 **개수 byte와 buffer flags byte**의 조합이다. 호환성을 위해 기존 출력은 남기고 새 필드를 추가했다. 각 선언은 다음 8바이트다.

| 상대 offset | 실제 읽기 | 의미 |
|---|---|---|
| 0 | u16 | attribute 이름의 payload 내 문자열 pointer, 0이면 빈 이름 |
| 2 | u8 | stream 안의 byte offset |
| 3 | u8 | stream 번호 |
| 4 | u8 | semantic ID: 관측한 position1/normal2/color3/UV4 |
| 5 | u8 | semantic index, UV0/UV1 등 |
| 6 | u8 | raw format ID, 관측한 float2=2/float3=3 및 packed color58 등 |
| 7 | u8 | flags, native는 bit0을 별도 보존 |

format ID 전체를 단순한 성분 개수로 취급하지 않는다. 특히58은 float58개가 아니다. byte offset과 stream을 합친 u16로 읽는 것도 잘못이다. `tools/re/srd.py`의 `attributes`는 각 byte를 분리하고 원시 ID를 보존한다. pointer 범위·stream·semantic index를 독립적인 합성 fixture로 검사했다.

`0x1405b7270`은 material의 map 이름을 MSH의 child/parent 이름 쌍과 비교하고, 그 parent 이름을 VTX attribute 이름과 다시 비교해 GPU 선언을 구성한다. 따라서 **첫 material texture를 첫 UV에 붙이는 규칙은 성립하지 않는다.** 이 교실의 `D2_desk_00`은 다음 연결이다.

- `COLORMAP1 → map1 → UV0 → id_017_cr1_desk_00.bmp`

### 시작점의 좌표 연결과 바닥 밖 점의 의미

`0x1403745a0`은 실제 「開始位置」 행에서 float0/1/2에 X -0.01, Y/Z +0.01 helper를 호출하고 processed+0x10/+0x14/+0x18에 저장한다. float3의 yaw에는 -1을 곱하지만 float4의 pitch는 그대로다. `0x14040b7f0`이 그 위치를 manager+0x40/+0x44/+0x48에 복사한다. 따라서 기존 변환은 시작점에도 연결됐지만, **모든 각도를 무조건 음수로 바꾸는 규칙은 아니다.** look-at `0x140374a40`도 같은 위치 변환을 쓰고, radius·yaw 제한을 별도로 읽는다.

COL은 `0x1405c0400`의 실제 node/leaf pointer로 정점과 index를 연결한다. 초기 물리 world 등록의 `0x14036d4b0 → 0x14036d790`은 이 raw pointer를 그대로 받아 `vertices[index*16]`에서 bounds를 만든다. 이 경로에는 TRE나 model root 행렬을 곱하는 단계가 없다.0xffff는 bounds 계산에서 건너뛰고 폭이 너무 작은 축은 약`1.5258789e-5`까지 넓힌다. 이 작은 수치에 임의의 meter 단위를 붙이지 않는다. 후속 상태별 collider 활성·수정까지 모두 해석한 것은 아니다.

기본판과 US판은 두 맵 모두 model 본체 SHA가 다르지만, **place SHA와 COL 좌표·배열은 같다.** 따라서 이번 시작점 불일치를 언어판 geometry 차이로 해소할 수는 없다. 기본·US 비교는 외부 `base_US_map_comparison.json`에 있다.

복도17개 시작점 중13개는 raw floor의 XZ 투영 안에 있다. 나머지의 정확한 point-to-triangle-union 거리는 시작1=33.75,9≈13.72953,10=8.37,11≈26.89693이다. 과거0.5격자에서 계산한 근사 거리와 구별한다. X/Z 반전·교환, COL에만 scale을 주는 대안도 계산했지만 내부 점 수가10/6/6/10/2/2로 줄었다. 오차가 작아 보이는 변환을 정본으로 골라 맞추지 않았다. place와 COL 양쪽에 동일한 rigid root 변환을 적용해도 상대적인 포함 관계와 거리는 바뀌지 않는다.

여기서「바닥 밖 = 잘못된 시작점」은 반증됐다. **`0x140408c00`의 자동 intro는 카메라 경로 자료가 없는 경우 시작점10과 look-at10을 직접 적용한 뒤 yaw sweep을 수행한다.** 적어도 이 소비는 일반 보행 입구가 아니라 자동 시점 연출이다. test script의 MAP literal만 보면9/10/11은 각각 시험용 Load1회지만, native의 직접 시작점10 사용은 그 literal 목록 밖에 있다.

시작1은 scope007의 non-test Preload27회와 test Load1회가 있으므로 모두 미사용이라고도 볼 수 없다. 반대로 Preload27회가 모두 실제 보행 시작1을 쓴다는 뜻도 아니다. 예컨대 `chap0/c00_000_007`의 Preload1@312 → wrapper FIL@350 뒤 wrapper의 한 분기는 explicit Load0@112로 덮어쓴다. 다른 phase redirect와 MOD는 별도로 남아 있다. `MOD` native는 `mapStartPosNon`일 때 저장된 입구를 `0x140406490`에 넘기고, 이 함수는 명시 입구면 위치를 다시 적용한다.「Non이면 언제나0으로 바뀜」이라는 반대 단순화도 하지 않는다.

야외는21개 시작점 중20개가 바닥 투영 안이며 시작19만 약52.70665 떨어져 있다. 시작19의 MAP literal은 이번 실효 US007 범위에서 없지만, 다른 방언·native 카메라·직접 배치를 배제한 전체 미사용 증명은 아니다. 모든 점을 바닥에 강제 snap하지 않았다. exact 거리와 대안별 오차·script offset은 `ID001_sch_1F_start_alignment.json`, `ID249_sch_side_0_start_alignment.json`에 보존했다.

### 정지·이동 중의 Y 정책과 무접촉 적분

수동 자유위치 경로 `0x14040a120`은 양수인 filtered speed가0.001 이상일 때 moving flag(+0x84)를 세우고, 그때만 `0x14040c180`을 호출한다. 입력을 놓아도 speed의 감쇠가 남아 있는 동안에는 갱신할 수 있다. 정지 중에는 이 capsule 적분 호출이 없다. `40c180` 자체의 speed0 분기는 vertical velocity를0으로 만들지만, ordinary idle guard가 이 함수를 호출하지 않는다는 점과 구별한다. **idle마다 vertical velocity도 자동으로0으로 지운다고 일반화하지 않는다.**

이동 중에는 위치 Y가 항상 고정되는 것도 아니다. `40c180`은 저장된 vertical velocity(+0x2bc)를 `405090`에 넘기고 반환된 Y·vertical velocity를 manager에 다시 복사한다. 기본 가속은 수평 velocity의 크기 `q`에 대해 `aY=min(-9.8, -9.8*q/1.1111112)`다. native acceleration getter `0x140623970`은 solver+0x1f0을 읽고 접촉 제약이 있으면 추가 보정을 수행한다.

무접촉 분기에서 확인한 실제 식은 다음과 같다.

```text
h = float(counter200) / 16384 / 64
deltaXYZ = velocityXYZ*h + 0.5*accelerationXYZ*h*h   (6248b0)
capsule 양 끝 XYZ += deltaXYZ                       (627fb0 → 62ec80 case2)
velocityXYZ += accelerationXYZ*h                    (6249d0)
```

초기 counter16384가 전부 남아 있다면 h=1/64다. 예를 들어 이미 speed field가0.1에 도달했고, 접촉·추가 constraint·초기 vertical velocity가 없는 조건에서 입력 velocity의 수평 크기는6, 한 호출의 수평 변위는0.09375, 수직 가속은 약-52.92, 수직 변위는 약-0.00645996이다. **원작을 걸어서 측정한 수치나 meter/초 단위의 속도가 아니다.** 접촉 시의 분할 counter·보정, 다른 CAM/자동 이동 모드까지 이 예제로 덮지 않는다.

그러므로 floor 투영은 충돌 표면 분석의 한 층이다. 그 안/밖만으로 시작점의 유효성·보행 허용·즉시 추락 여부를 단정할 수 없다. 여기서는 초기 world의 raw 좌표, 일반 수동 경로의 실제 Y 소비와 수치 적분을 닫았으며, 상태별 collider·입구·시점과 실제 조작 관찰은 남아 있다. native 적분 근거는 `6248b0 ev_8c2503ceae890abfcf81c72d458ef87f663246599f595786f132335337e823f9`, `6249d0 ev_38199a4e489da49b4a11ebc6fb1ee74045b200f0de21586f8b430b92d7cca6f4`, `62ec80 ev_b0e100b374d69fcdee842e778e0655ff1c693a0ae023cc837f0225a09017531c`다. 전체19개 관련 native 근거와 조건부 계산 검사는 외부 `native/map_visual_additional_findings.json`에 있다.

### 수동 이동의 실제 접촉 분기: 일반 solver와 다른 부분

`405090 → 62e2f0`의 실제 명령은 solver+0x34를1로 초기화한다. `6250d0`은 `628250 → 623650 → 623a00`을 호출하지만, `628250`은 먼저 접촉 수 +0x204를0으로 만든 뒤 **+0x34==0일 때만** 접촉을 수집한다. `623a00`도 같은 조건 아래에서만 제약을 고른다. 따라서 이 경로에서는 접촉 목록·추가 가속 제약 수가0이고, 일반 solver의 다중 법선 분해·침투 보정이 수동 플레이어에 적용되는 것은 아니다. 함수 이름이나 호출 존재만 보고 실행 본문을 추정했던 해석을 이 조건으로 정정한다.

실제 접촉 응답은 `625c60`의 이동 검사에서 온다. 먼저 `6248b0`이 현재 잔여 counter의 변위 `d`를 만든다. `624be0 → 625d70 → 62efb0`이 전체 이동을 검사하고, 충돌하면 counter를 이분 탐색하여 충돌하지 않은 지점(+0x7d4)과 충돌한 지점(+0x7d8)을 좁힌다. 구간은 정수 counter이므로 간격이2 미만이면 끝내며, 안전 구간이 양수이고 `(hit-safe)*length(d)/counter < 0.001953125`이면 일찍 멈춘다. 이0.001953125와 검사 형상에 더하는0.015625는 **보수 오차·여유 값**이다. 캐릭터 반경이나 물리 초 단위와 동일한 개념이 아니다.

후보 선택도 바닥 XZ 안/밖 검사로 끝나지 않는다. capsule 분기의 `61b530 → 61cfb0`은 활성·비활성 조건과 bounds를 검사하고 하위 형상, triangle index strip/mesh를 순회한다. `625150 → 62da00 → 6298b0 → 630a30`은 충돌한 쪽의 이동 위치에서 capsule과 상대 형상의 근접점을 구한다. `6283d0`은 두 점의 차이를 정규화한 법선 n을 만들고, 상대 예측 변위와 `dot(d,n)>0`인 후보 중 분리 벡터 길이 제곱이 가장 작은 것을 +0x820에 남긴다. 일반 수동 경로의 world pair는 동적 상대 solver 포인터를0으로 넣으므로, 상대 물체의 이동을 빼는 추가 분기까지 실제 정적 지도와 혼동하지 않는다.

`627e70`은 안전 counter 비율만큼 실제 형상을 옮기고 counter에서 이를 뺀다. `625c60`은 이어 hit와 safe 사이의 counter 간격도 소비한다. 호출자 `405090`은 선택한 법선이 있으면 **XYZ 전체에 `v'=v-n*dot(v,n)`**을 적용하고 남은 counter로 다시 검사한다. 이 조건부 수식은 벽을 향한 성분을 없애면서 접선 성분을 남길 수 있다. 한 축 벽 법선 n=(1,0,0), v=(2,0,3)이라는 계산 예에서는 v'=(0,0,3)이다. 원작에서 해당 벽을 걸어서 실측했다는 뜻은 아니다. 바닥·비스듬한 면은 Y가 포함된 법선이어서 Y 성분도 바뀔 수 있다. 단, 충돌한 분기에는 무접촉 분기의 `6249d0: v+=a*h` 호출이 없으므로 전체 구간에 가속을 한 번 적용한 뒤 마지막에 clamp하는 구현으로 단순화하지 않는다.

기본 radius0.5·높이 인자1을 형상 식에 넣으면 두 중심이 모두 Y+0.5가 된다. 즉 **이 기본값에서 capsule은 반경0.5인 구형으로 퇴화**한다. 설정이 바뀌면 두 중심이 갈라질 수 있다. 눈높이1.5는 별도 카메라 필드이며,0.015625 검사 여유는 원래 형상의 반경을 영구적으로 바꾸는 값이 아니다. sphere/면 접촉의 법선 투영이 낮은 모서리에서 위쪽 이동 성분을 만들 수 있다는 기하적 가능성과, 원작이 특정 단차를 실제 넘는다는 검증은 구별한다.

#### TXR flags7의 실제 해독 조건과 GPU 업로드

공개 parser가 `swizzle`이라는 ushort로 묶었던 TXR payload+4는 native `5977d0`에서 **flags:u8와 첫 external resource index:u8**로 따로 읽힌다. +0xd는 mip count다. `srd.py`는 기존 `swizzle`/`unknown0d` 키를 보존하면서 `flags_byte`, `first_external_index`, `mip_count`, `is_cubemap`을 추가했다. `54f200`은 선택한 RSI descriptor에서 source 상위3비트·offset 하위29비트를 읽어 원래 payload 포인터를 돌려준다. export도 이 index를 사용한다. 기존 offset bit28을 잘라 버리던 mask는 native의 `0x1fffffff`로 바로잡고 경계 회귀로 확인했다.

일반2D의 `597b40 → 5c0e50`은 원래 mip 포인터를 `D3D11_SUBRESOURCE_DATA.pSysMem`에 넣는다. native format15의 실제 DXGI table 값은71/72(BC1_UNORM/BC1_UNORM_SRGB), row pitch는 `ceil(width/4)*8`이다. `5a77a0`은16바이트 subresource 구조 배열만 복사하고, `5a7d30`은 그 포인터·descriptor로 `ID3D11Device::CreateTexture2D`를 호출한다. 이 경로에는 low flags0..2를 이유로 texel을 재배열하는 처리가 없다. DXGI 상수·구조와 vtable 위치는 로컬 Windows SDK10.0.22621.0 header의 SHA/행으로 대조했고, [Microsoft DXGI enum](https://learn.microsoft.com/en-us/windows/win32/api/dxgiformat/ne-dxgiformat-dxgi_format), [subresource data](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/ns-d3d11-d3d11_subresource_data), [CreateTexture2D](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11device-createtexture2d)의 계약과 일치한다.

native `5a0d00`은 MAT의 bitmap 수를 runtime+0xd8에 보존하고 각 resource를+0x68 배열에, slot 이름 hash를+0xa8 배열에 저장한다. bitmap 수가0이면 이 반복을 생략하지만 이후 shader/default 초기화는 계속한다. 따라서 **bitmap0→자동 비표시**라는 가정은 이 소비 경로와 맞지 않는다. `5bfc40`은 MSH의 mapped-node 두 이름을 runtime+0x68의16바이트 쌍으로 복원한다. `4ee110`은 별도의 shader property에서 PCG/VCG 쌍을 읽어 shader cache/hash를 유지하므로 MAT bitmap 목록만으로 최종 표면 식을 알 수 없다. 명명 UV 선택은 아래 후속 native 연결에서 확인했고, 다중 texture 합성·alpha/outline/shadow의 실제 선택 pass는 미확정으로 남겼다. 이 분류 단계에서는 전체 renderer나 기본 profile을 확대하지 않았고 최종 draw/exclusion 분모55,007/1,022도 유지했다.

이름에 따른 실제 resource 선택도 확인했다. `5a12b0`/`5a11d0`은 요청 slot 이름을 seed1/base0x89로 hash하고 선언된 slot hash와 대조해 해당 resource·texture를 돌려준다. **없으면0이며 첫 texture로 대체하지 않는다.** `5a1560`은 두 shader variant에 대해 선언된 slot hash를 `5b1df0`으로 보내 반환 byte를 variant별 binding 배열에 기록하고 실패하면0xff를 넣는다. `5b1df0`은 stride0x38인 shader reflection record의+0x28 hash를 비교해+0x30 byte를 반환한다. `5a0b10`은 그 byte가0xff이면 건너뛰고, 아니면 해당 index에 texture resource와16바이트 sampler/state payload를 context 상태 함수 `0e4f10`/`0f1b90`으로 넘긴다. bitmap0은 이 texture 반복을 생략한다. 이로써 반환값이 shader별 texture/state binding index로 소비되는 것까지 연결했지만 최종 GPU submit·정확한 D3D register 번호와 동일시하지 않는다.

UV 선택은 별도 native `5b7270`에서 확인했다. semantic4 입력의 index와 shader reflection record+0x31을 대조한 뒤, record+0x20의 slot 이름을 MSH mapped-node 첫 이름과 비교한다. 일치 쌍의 두 번째 이름을 VTX의 **semantic4·명명 attribute**와 정확히 비교해 정점 입력 선언에 넣는다. 즉 shader slot→MSH 매핑→이름 있는 VTX UV의 연결이며 `map1` 문자열만을 유일한 UV 계약으로 사용하지 않는다. 명명 경로가 없으면 semantic·index를 대조하는 별도 fallback으로 가며 무조건 첫 UV를 고르지 않는다. `56c4b0`/`56c250`의 선언 항목·stream flag·hash 작성까지 대조했으나 최종 D3D input-layout submit을 이번에 새로 검증한 것으로 세지는 않는다.174 carrier의 명시 링크가 실제 native 선택 체계와 부합한다는 점과 어느 shader variant가 실제 활성인지는 별개다.

외부 `native/material_native_selection.json`에14개 REA 근거·reader·이름 조회·binding consumer·명명 UV 경로를 묶었다. `4ee9e0`은 REA procedure가 잡히지 않았으나 `.pdata` 없는 raw leaf `4ee9e0..4eea5a`를 확인했으며, 파라미터 복사·배율 reset뿐이어서 texture 선택 함수 후보에서 제외했다.

### 시점·표시에서 남은 경계

`0x140409010`은 eyeY를 managerY+기본 eye-height(+0xe4, 초기1.5)+추가 높이로 만들고 FOV를 place에서 받는다. `0x14040b110`은 position/yaw/pitch/FOV를 camera setter `37be00/37bec0/37bdb0/37bd70`으로 전달한다. 후속 [카메라 분석](08_카메라.md)의 실제 view 행렬 연결로 world yaw0→+Z, yaw180→−Z와 기본 FOV가 수평 전체각인 점까지 확인했다. 이것을 기존 참고뷰에 소급 적용했다고 말하지 않는다. 참고뷰의 `fov_y=80`은 분석자가 고른 수직각이고4:3 프레임이다. 모두 기록된 **분석자 카메라**이며 원작 입구 시야가 아니다.

최초 CPU 참고뷰에서 큰 floor triangle의 near-plane 교차를 버려 바닥이 빠져 보이는 분석기 오류도 확인했다. world triangle과 UV를 함께 clip하도록 고친 뒤 참고 형상이 돌아왔다. 이를 원작의 누락 geometry로 잘못 보고하지 않았다. 검은 큰 면·강한 색면도 원작 shader/blend·visibility·variant를 재생하지 않은 상태라 최종 장식·조명으로 해석하지 않는다. 별도 sky/obj 인스턴스·SAN·runtime root를 합성하지 않은 한계는 각 manifest에 유지했다.

## 이동 위상과 실제 발걸음 SE 요청

일반 수동 자유 이동 `40a120`은 입력 크기×기본 속도(+0xe8), 달리기 predicate `3c9260` 또는 강제 상태+0x378에 따른 배율(+0xec)을 목표 속도로 삼는다. 현재 속도+0x7c는 목표와의 차이에0.5를 곱해 접근하고, 무입력일 때0.5 감쇠하며0.001 부근에서0으로 정리한다. 이동 flag+0x84가 켜져 있으면 발걸음/흔들림 위상 증가량+0x8c를 `(현재속도/기본속도)×+0xf4`로 둔다. 초기 +0xf4는6이며 별도 +0x25c 분기는 증가량에0.75를 곱한다. **실제 새 좌표−이전 좌표의 길이를 다시 재서 누적하는 식이 아니다.** 충돌 처리 `40c180→405090`이 실제 변위를 줄이더라도 이 경로는 그 차이로 보행 위상을 줄이지 않는다. 막힌 상태에서 소리가 무조건 없다고 가정할 수 없다. 근거 `ev_e4d8a295a929f4f0d0b96ea8d09d9074b338d41ac85067dd6cef9c5e1a4fdfa9`, `ev_b9ca36c7e852cc78052775be730b26f0ac59597b0c8128a56ee7f9650a78489d`.

## 탐색에서 일상·수사·이동·저장으로 돌아오는 정상 연결

탐색 manager의 같은 입력/결과 구조가 일상과 수사의 대본을 연결한다. MAP/입구·모델·인물·hit/표시 요청을 준비하고 modTansakuWait에서 조작을 받는다. 인물 선택은 HUM 번호, 물체·구역 선택은 결과 target+100의 CHK로 대본에 들어간다. 일반 HUM 복귀는 탐색 준비를 확인한 뒤 저장된 탐색 진입 IP/문맥을 복원한다. 따라서 조사 대화를 닫을 때마다 새 맵·새 scene을 만드는 구조가 아니다. 일상 초대의 수락/거절·완료220→다음 초기화는 [02_일상.md](02_일상.md), 조사 결과·언령·지역 완료 gate는 [03_수사.md](03_수사.md)로 이어진다.

실제 물체 전환 한 예는 scene19의 `c01_019_001 CHK100@964→ID249 Preload/start0@968→ID001 Delete@998→FIL c01_000_250@1006`이다. wrapper의 scene19 branch는 `c01_019_250`을 고르고 그 파일 `@42`가 ID249를 `mapStartPosNon`으로 Load하므로 이 경로에서는 앞의 입구0을 유지한다. Preload·이전 맵 삭제·파일 교체·목적 MAP Load·준비 완료를 각각 보존한다. 이 지역 body가 존재한다는 것과 모든 저장 상태에서 그 대상이 선택 가능하다는 것은 다르다. 실제 맵 리소스와 파일명 끝자리250도 같은 ID가 아니다.

패드 지도 왕복은 별도 gate를 가진다. MPF 갱신으로 장소/인물 마커가 표시돼도 빠른 이동 확정에는 TechouMap type1·bit30·탐색 manager 준비·flag143 등이 추가된다. 유효한 확정만 mapjump의 논리 목적지→같은 맵 재배치 또는 다른 맵 정리→장별 wrapper→scene 분기→실제 MAP/입구로 이어진다. 강조만 옮기거나 취소한 경우를 실제 이동으로 만들지 않는다. [15_패드지도.md](15_패드지도.md)의 목록 SE005·확정 SE001·취소 SE004·퇴장 클립/manager 복귀, `map_wrapper_load_findings.json`의 리소스 준비 계약을 함께 따른다.

일상·수사 모두 본편 탐색 mode1을 쓸 수 있으며 SaveScene·지역 조사 플래그·재판 mode2 진입은 다른 축이다. 패드/F1과 SystemSave의 허용 조건을 충족하면 확인 UI→snapshot→비동기 파일 쓰기 완료/성공→퇴장으로 연결한다. Continue는 저장된 맵/인물/UI를 다시 준비하고 위치·시점·탐색 mode와 대본 호출 문맥/커서를 복원한 뒤 복원 잠금을 해제한다([09_시스템.md](09_시스템.md)). 맵 Load 성공·HUM 반환·활동220·패드 닫기를 각각 디스크 저장 성공이나 모든 입력 허용으로 합치지 않는다.

시간제 수사 중 목적지를 고르지 않은 패드 열람은 정상 HUD/탐색 준비가 유지돼 타이머가 감소할 수 있다. 반면 이동 확정으로 탐색을 정리하면 준비 predicate가 꺼지고 공통 HUD 전에 반환할 수 있다. 같은 탐색/패드 연결이라도 이 두 분배는03의 타이머 정상 계약으로 구분한다. ‘패드를 열면 언제나 게임 전체가 정지한다’는 공통 규칙을 만들지 않는다.

이로써 **준비된 공간/인물/선택→일상·수사 대본→조건/보상/증거→같은 탐색 복귀 또는 목적 맵·다음 모드→저장·Continue**의 주요 정상 시스템 연결을 재구성할 근거가 있다. 모든 portal 후보의 전역 도달성·누락 WRD 후보 하나의 해명·모든 카메라 override·실제 픽셀은 별도 한계다. 외부 `exploration_investigation_normal_findings.json`과 `exploration_investigation_normal_contract.py`가 기존18원장·REA21함수·raw getter2개·대본 연결17곳을 대조하며 원작 실행·신규 추출·공용 진척 수정은 없다.


## 조사·말걸기·물체 반응의 정상 표현 소비

이 절은 기존 target/ray·카메라·자격 판정·보상 규칙에 **커서/이름→수락→표현 완료→대본 문맥 복귀**, 그리고 **타격 준비→적중→물체 노드 반응**을 결합한다. 외부 `native/interaction_presentation_contract.py`는 REA24건·정적 범위6개·기존 SFL9개 carrier를 검증한다. `interaction_presentation_findings.json`, `_raw.json`, `_sfl_contract.json`에 Evidence·바이트 SHA·라벨/Stop·이름 있는 배치의 depth/행렬/색 정보를 남겼다. 원작 실행·신규 추출·렌더·청취 검증을 한 결과가 아니다. 언령 획득 KTD 표현은 별도 담당 계약이며 여기서 중복 해석하지 않는다.

### target 선택과 이름·강조의 작성/소비
