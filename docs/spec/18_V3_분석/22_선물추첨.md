# 22. 본편 선물 추첨: 모노모노머신

이 문서는 원작의 선물 획득 머신에서 입력→투입량 선택→차감→추첨·보유 등록→추가 추첨→결과·퇴장→저장 경계를 분석한다. 선물 취향·자유행동 중 선물 소모는 [02](02_일상.md), 카지노와 보너스 Carddess는 [10](10_보너스와_비정형_DAT.md), 공통 패드는 [21](21_패드정보.md)로 구분한다. 원작 대사·이름 목록·그림·전체 디컴파일은 저장소에 넣지 않았다.

근거는 설치본007·US007을 합친 실효 WRD2,716개와 복원 정적 실행 파일 SHA256 `1a012357f54076ef7fbe6a63f19f055bbe1ce71792b8c0719e7dc51d2a5affeb`다. 실제 머신 화면이나 난수 빈도를 측정한 결과는 아니다. 기존02의 식·후보 표 분석을 재사용하고, 남은 상태 소비와 복귀 경계를 추가 대조했다.

## 진입은 본편 요청과 독립 UI 루프를 연결한다

`mode_label.dat`의 MODE6=modMonomonoMachine을46cd40이 처리한다. 본편 모드값1에서는 탐색 controller+4=5, 모드값3에서는 별도 일상 controller+4=10을 요청한다. 458f00/45a5b0은 문자열을 보관하는 setter이며 추첨 함수가 아니다.

실효007의 literal MOD 호출은7개다. 본편6개는 장1/2/3/4/5에 각각1/2/1/1/1개, 나머지1개는 test/다. 장6·별도 일상의 literal 호출이 없다는 사실을 동적 호출이나 해금 후 메뉴 진입까지 불가능하다는 증명으로 사용하지 않는다. 모든 호출의 세 후속 인자는 non이며, 스크립트 SHA·offset·인접 명령은 외부 `native/monomono_script_calls007.json`에 있다.

456d80/4598f0은 주변 장면을 정리하고15f700을 호출한다. 15f700은 stack에 머신 context·도움말·공통 패드 manager를 만들고 매 반복에49d550과15eb30을 호출한다. UI가 끝나야 상위 controller로 돌아간다. 이 진입을 단순히 MOD 다음 줄이 곧바로 계속 실행되는 동작으로 구현하지 않는다.

상위 복귀 후에는 ModeMonomonoMachine flag를1로 쓰고 배경·탐색 UI·대본 대기를 복구한다. 이 flag 쓰기는 추첨 성공 분기에만 있는 것이 아니라 머신 UI 반환 뒤에 있다. 코인을 쓰지 않고 취소하는 경우와 실제 선물 획득을 같은 조건으로 보지 않는다.

## 표시 중복률과 실제 정수 추첨을 구별한다

N=83개 후보, U=그중 기획득 수, C=선택 투입량으로 두면160160의 표시 백분율은 다음과 같다. 연산은 float32의 순차 연산이다.

```text
U == N      → 100
그 외 C <=1 → 100*U/N
그 외 C==100→ 0
그 외       → max(0, 100*U/N - 100*C/N)
```

15f390은 기획득 목록 A와 미획득 목록 B를 만든다. p=표시 백분율/100으로 두고 A가 비면0, B가 비면1로 보정한다. `float32(p*32768) >= 난수의 하위15비트`이면 A, 반대면 B를 선택하고 다음 난수 `%선택 목록 수`로 아이템을 고른다.

이 비교는 등호를 포함한다. 기획득 목록이 존재할 때 표시0이어도 하위15비트가0이면 A 쪽이다. C=100을 신규 아이템의 수학적 절대 보장이라고 부르지 않는다. 모든 후보를 이미 획득했다면 첫 분기부터100이며 신규 후보는 없다. 정수 나머지 선택과 PRNG의 실제 시드·분포를 조사하지 않고 표시값을 실측 확률이라고 쓰지 않는다.

5d7ba0은 CRT rand가 아니라 전역 u32 네 상태와 xor·shift11/11/8을 쓰고 최상위 비트를 지운31비트 값을 반환한다. 후속09에서 정수·실수 난수 함수와의 전역 상태 공유 및 직접 시드 호출 두 곳의 GetTickCount 사용을 확인했다. 시드 보존·재개 경계와 편향의 실제 빈도는 미확정이다.

160160 의사코드는 산술 뒷부분을 누락하므로 전체 raw0x140160160..0x140160295를 함께 보았다. 근거: `ev_374df80db2aff57b13cdbc8ed8920153f720955acf8cd1f9a3f21387ec857fb6`,최초 선택15f390 `ev_e050f9f670490da1682a08cbdcd883e81def2c934a8b896e6dff6b73282aef0d`. 기존 `native/machine_static_findings.json`의 원시 SHA·범위와 신규 원장을 대조했다.

## 추가 추첨: 무료 재진입과 카운터 재설정

추가 판정용 확률은15e590의 SSE 반환값이다. C=100이면1, 그 외에는 `clamp(float32(0.1+0.009*C),0,1)`이다. 의사코드는 float 반환을 누락하므로 raw0x14015e590..0x14015e5d3을 사용했다. 15e5e0은 이 값×32768과 하위15비트 난수를 등호 포함으로 비교한다.

이 로컬 상태 순환은 다음과 같다.

```text
0xc 차감·추첨 준비(counter=0)
 →0xd 선물 선택·획득(C=0)
 →0xe 결과 표시 완료 대기
 →0xf 새 입력 대기
 →0x10 다음 입력 또는 퇴장 애니메이션 완료 뒤 추가 판정
 →성공:0x11 추가 표시 완료 대기, counter+=1, 확률*=0.5
 →0xc로 재진입(counter가 다시0)
```

첫 선물을 선택한 뒤 C를0으로 만들므로 추가 성공으로0xc에 재진입할 때의 코인 차감은0이다. 처음 투입한 비용을 매 추가 회차마다 다시 내는 구조가 아니다. 결과 이후 잔액이0이어도 이미 시작한 결과 표시와 이 무료 추가 경로는 계속될 수 있다.

중요한 정정은 **‘최대4회 추가’가 이 순환에서 성립하지 않는다는 점**이다. 15e5e0의 counter≥4 거부 조건은 존재하지만0xc가 counter를0으로 지운다. 정상 로컬 순환에서0x11이 만든1은 다음 추첨 전에 다시0이다. 15f700의 외부 루프도 해당 필드를 바꾸지 않는다. 강제로 추가 성공 분기를 연속 택한 최소 상태 추적에서 첫 차감100 뒤 후속 차감은 모두0, 각0xd의 counter는 계속0임을 확인했다. 이 추적은 조건부 상태식 검사이며 실제 플레이나 RNG 시드 실행 기록이 아니다.

또한0xd의 `counter≠0이면 전체 N에서 직접 선택` 분기는 코드에 있지만 위 순환은 그 값을0xd까지 유지하지 않는다. 따라서 확인한 로컬 순환의 추가 회차는 다시15f390을 사용한다. 그때 C=0이므로 처음 투입량의 중복률 감소를 그대로 유지하지 않고, **갱신된 기획득 집합과 C=0의 기본 비율**로 재평가한다. 반면 추가 판정 확률+0x710은 성공마다 절반이 되어 유지된다.

C=100의 첫 추가 판정은 임계값32768로 모든 하위15비트 값 이상이다. 이후0.5의 임계값도16384를 포함한다. 값이0이어도 난수0은 통과할 수 있으므로 이를 이상적인 연속 확률의0%/50%와 동일시하지 않는다. 외부 callback의 모든 교차 실행까지 배제한 증명이나 실제 최대 연속 획득 횟수 측정은 아니다.

## 결과 입력과 취소·복귀

상태0xf는3c34a0의 새 입력을 기다린다. 이는 고정 결정 버튼 하나가 아니라 허용된 마우스·패드·키보드 새 누름을 받는 공통 경로다.0x10에서는 추가 입력으로 퇴장 표시를 넘기거나 표시가 끝나기를 기다린 뒤 추가 판정을 한다. 추가 실패는 입력 상태0xb로 돌아간다. 화면의 모양·표시 시간은 실제 관찰하지 않았다.

결제·결과 처리 상태0xc..0x11에는0xb의 구매 전 취소 분기가 없다. 결과에서 Escape가 공통 새 입력으로 수용될 수 있다는 사실은 구매 취소나 환불이라는 뜻이 아니다.
