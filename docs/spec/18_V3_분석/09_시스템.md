## 타이틀은 리소스·입력·전환 상태를 분리한다

실제 타이틀 메뉴 업데이트는 `FUN_1403b63b0`이다. 리소스·글자 관련 준비 완료를 확인한 뒤 타이틀 BGM 큐 `V3_BGM_002`를 시작한다. 시작 입력을 기다리는 단계는 입력 함수 `FUN_1403c34a0`을 확인하고, 입력되면 결정 효과음 `V3_SE_001`과 UI 전환을 시작한다. 이후 각 화면 애니메이션의 완료 여부를 확인한 다음 메뉴 입력 단계로 넘어간다.

이어하기·장 선택·옵션 등의 세부 화면은 각각 자체 상태 객체를 갱신한다. 타이틀은 그 반환값을 기다리고 메뉴 또는 다음 모드로 진행한다. 따라서 시작 입력 즉시 장면 하나를 바꾸는 구현은 대기 중인 UI·소리·저장 목록 처리 순서를 생략하게 된다.

타이틀 진입 작업 `FUN_140456970`은 메뉴 객체를 생성하고 업데이트 반환 상태에 따라 다음 작업 번호를 선택한다. 이 작업과 전체 시퀀스 상태 처리기 `FUN_140456d80`도 별개다. Task 생성 함수만 확인하고 타이틀 동작을 분석했다고 할 수 없다.

## 타이틀 8개 모드의 활성 조건과 해금 쓰기

`Mode.dat`의 16행 중 앞 8행은 위 메뉴 순서와 일치하며, `セーブNo`는 0~7이다. SHA256은 `c8e07e88f00f1feaf806e500cdac6dfffe66c36582cf3d36aa4998aed6f1b732`다. `52ec20`은 기술 이름으로 행을 찾고 `52ed10`은 열 1의 번호를 읽는다. `53a0a0`의 조회와 `53de00`의 쓰기는 영속 상태 `+0x80 + (번호>>5)×4`의 `번호&31` bit를 사용한다. 따라서 이 8개는 `+0x80` 첫 워드의 bit 0~7이다. 이름이나 행 순서만 보고 추정한 활성 상태가 아니다.

초기 상태 생성 `53b790`은 payload 범위를 0으로 만든 뒤 새 게임·옵션·Extra bit를 명시적으로 켠다. 기존 저장 자료의 복원과 초기값 생성을 구분한다. 초기화 함수가 있다는 이유로 실행할 때마다 사용자의 진행이 초기화된다고 해석하지 않는다.

| 인덱스 / 기술 모드 | 초기 bit | 실제 활성 조건·쓰기 |
|---|---:|---|
| 0 `ModeFirstGame` | 1 | bit 0. 새 게임 경로는 난이도 등 하위 창을 거쳐 진입 |
| 1 `ModeContinue` | 0 | bit 1 조회 뒤 별도 저장 스크립트 검사로 덮어씀. 메뉴 bit만으로 결정되지 않음 |
| 2 `ModeChapterSelect` | 0 | bit 2. `wkChapter` 특수 대입 경로에서 아래 조건으로 켬 |
| 3 `ModeSuccess` | 0 | bit 3. 본편 장 6의 `CapterEndSave` 분기에서 켬 |
| 4 `ModeRpg` | 0 | bit 4. 첫 육성 결과 이벤트의 별도 RSC 명령이 켬 |
| 5 `ModeAinori` | 0 | bit 5. 본편 장 6의 `CapterEndSave` 분기에서 켬 |
| 6 `ModeOption` | 1 | bit 6. 초기화 때 켬 |
| 7 `ModeExtra` | 1 | bit 7. 초기화 때 켬. 하위 부가 항목 전체가 해금됐다는 뜻은 아님 |

이어하기의 `53c2a0`은 영속 상태 `+0x30104`의 문자열에 `.wrd`가 들어 있는지를 검사한다. 현재 경로에서 저장 파일의 존재를 직접 조사하는 함수가 아니다. 결정 뒤에는 `53aed0(0)`이 읽는 저장측 `+0x39750` 필드와 `53ae30`의 상수 7도 비교하여 전자가 크면 거부 메시지 경로로 간다. 이 비교 필드의 전체 형식 의미까지 새로 확정하지 않았으며, 메뉴 활성과 실제 재개 허용을 같은 한 비트로 줄이지 않는다.

장 선택 활성 bit는 WRD의 일반 변수 처리기 `474af0`이 `wkChapter`를 특수 처리할 때 설정한다. 모드 1/2의 분기는 각각 장 값을 8/10으로 바꾸고 먼저 돌아간다. 나머지 분기는 `53d4e0` 처리 뒤 현재 장 `+0x16a0`이 0이면 `53de00("ModeChapterSelect",1)`을 호출한다. 이 조건을 근거 없이 ‘프롤로그 클리어 이후’라는 조건으로 바꾸지 않는다. 각 장·구간의 진행 비트는 메뉴 자체의 활성 bit와 또 별개다.

본편 끝의 실제 쓰기는 `46cd40`의 MOD save case 0에서 첫 인자가 1일 때 발생한다. 현재 장이 6이면 `462800`이 `ModeSuccess`와 `ModeAinori`를 켜고 `53d6d0(1)`로 영속 상태 `+0x7a`의 클리어 표시를 쓴다. 이 클리어 표시를 `539a00`이 읽으며 타이틀의 장 진행 수가 6이 된다. 같은 분기에 RPG bit를 켜는 쓰기는 없다. 해금 bit는 이 시점의 메모리 상태에 먼저 반영되며, 뒤의 저장 UI·실제 disk writer·성공/실패 결과는 기존 저장 절과 같이 분리한다.

RPG의 별도 쓰기 `27bfe0`은 육성 진행 객체 `+0xc`를 1로 만들고 `ModeRpg`를 켠다. 네이티브 등록 구간 `27a228..27a257`이 이 함수 주소를 command `0x7067`에 등록하며, `rsc_command_label.dat`의 `UNLOCK_RPG_MODE` 번호 103에 `0x7000`을 더한 값과 일치한다. 실효 RSC 조사 442개 WRD에서 해당 명령은 한 번이다. 호출 파일·SHA·오프셋 956과 전후 명령은 외부 `native/title_mode_rpg_unlock_rsc.json`에 두었다.

실제 상류 `261030`의 육성 결과 이벤트는 하위 순번 0의 스크립트를 끝낸 뒤, `2b7cc0 → 226080`이 읽는 진행 객체 `+0xc`가 0이면 순번 1을 추가로 실행한다. 이 추가 파일은 해당 해금 명령까지 직선으로 진행하며, 명령이 `2260d0(...,1)`로 같은 필드를 켜므로 다음 결과 처리에서 첫 회 분기가 반복되지 않는다. 따라서 확인한 시점은 **첫 육성 결과 이벤트 처리**이며 본편 클리어 시 일괄 RPG 해금이 아니다. 결과 이벤트에 도달하는 모든 진입·중도 종료 경로를 확인한 것은 아니므로 ‘반드시 36턴/졸업을 완료해야 한다’는 더 강한 조건은 주장하지 않는다. 해금 뒤의 결과 저장 요청과 저장 성공도 별도다.

표시 `3b7a90`은 이 활성 배열로 설명 인덱스와 여러 하위 UI의 가시성을 바꾼다. 선택한 비활성 칸은 별도 설명 인덱스 12를 쓰며, 입력 `3b7e80`도 활성값 0이면 거부 소리를 내고 그대로 돌아간다. 활성이어도 3/4/5/7번은 컨텍스트 `+0xcc0`을 추가 검사한다. 이 필드는 정상 시작 `49ec50 → 499fc0`에서 1로 설정되는 별도 진입 허용 필드다. 현재 근거로 이를 DLC·엔딩 해금 비트라고 이름 붙이지 않았다. 통과 뒤에만 타이틀의 하위 선택/모드 전환 상태로 간다.

### 구간별 잠금·선택·취소와 공통 스냅샷의 실제 재개

`3ac700`은 Chapter 표의 첫 7행을 사용한다. 각 장은 최대 5칸이며, `ModeChapter%d00/03/01/02`가 켜진 구간만 차례로 가변 배열에 추가한다. 따라서 표에 있는 모든 구간이 항상 선택되는 고정 목록이 아니다. 구간 type와 스크립트 열의 실제 대응은 다음과 같다.

`3ad0f0`에서 장 단계의 취소는 결과 `-3`을 기록하고 창을 닫아 타이틀 메뉴로 돌아간다. 장 확정은 구간 단계로 이동한다. `3ad310`에서 구간 단계의 취소는 장 단계로만 되돌아가며, 확정은 type 0~3의 해당 열 문자열을 `+0x1d0`에 기록해 결과 `-1`을 돌려준다. type 4는 결과 `-2`를 반환하여 `3b63b0`의 기록 화면 분기로 간다. 컨텍스트 `+0xcc0`이 0이면 장 인덱스 2 이상 또는 장 인덱스 1의 일부 구간은 안내 메시지로 막힌다. 이 추가 필드를 DLC 여부로 단정하지 않는다. 창 종료·입장 애니메이션의 준비 검사도 통과해야 부모 상태가 진행한다.

일반 구간 선택의 `-1`은 난이도 하위 선택을 거친 뒤 시작 문자열로 전달된다. `478780`은 이 문자열을 사용하는 시작과 `Continue`를 구분한다. 스냅샷 getter `53aef0(i)`는 영속 상태 `+0x2ffc0+i×0x97a0`을 가리킨다. **일반 장·구간 선택은 인덱스 0의 공통 스냅샷을 복사하고 선택한 시작 스크립트로 들어가는 경로**다. 각 구간마다 별도 저장본을 골라 복원하는 배열이라는 해석은 반증된다.

`482190`은 원본 포인터를 world `+0x8f0`에 보관하고 `0x97a0 = 38,816byte`를 world `+0x970`으로 복사하여 `+0x8f8`을 작업 상태 포인터로 둔다. 런타임 handle 영역은 별도로 world `+0xa110`을 가리키고 `482000`에서 `0x990byte`를 초기화하며 언어·옵션·무효 handle을 다시 설정한다. 즉 저장 바이트를 복사했다는 이유로 살아 있는 GPU/장면 객체까지 그대로 복원한 것은 아니다.

#### 타이틀 LOAD 목록의 입력과 마우스 취소 경계

초기 3항목 타이틀 `3b8190`은 결정 입력 `3c70f0(input,1)`을 받으면 **현재 선택값 `+0x58`**에 따라 실행한다. 이 함수에는 클릭 좌표로 항목을 새로 고르는 hit-test가 없다. 선택값 1은 `53c560 → 3fe950(mode=1)`로 공통 저장·불러오기 창을 연다. 따라서 화면의 NEW GAME 위치를 클릭했다는 사실만으로 그 항목이 선택됐다고 단정하지 않는다. 실제 커서의 이동 지연 원인은 이 함수만으로 확정하지 않았다.

공통 상태기 `3fe1e0`의 목록 상태 8은 `3ff430`을 호출한다. 이 함수는 먼저 목록 SFL `object+8`의 `4aa8c0` 준비 조건을 검사하며, 미완료이면 입력 검사 전에 돌아간다. 통과 뒤 순서는 취소 `3c3c80` → 결정 `3c70f0(input,1)` → 표시 전환·방향/페이지 입력이다. 취소가 성립하면 상태 `+0x1c=0x1a`로 가고 퇴장 연출 후 목록 처리를 종료한다. LOAD에서 빈 슬롯을 결정하면 거부 소리와 함께 목록에 남는다. 현재 선택 행 0~5와 스크롤 시작값 0~24를 합쳐 총 30슬롯을 가리킨다.

**확인한 LOAD 목록/확인창 소비 경로에는 별도의 마우스 취소나 화면 close 영역이 없다.** 취소 함수 `3c3c80`은 키보드·패드만 검사한다. 클릭을 허용하는 일반 결정 함수와 별개다. 슬롯 결정 후 확인창의 `3ff250`도 취소는 같은 함수이며, 취소하면 전체 LOAD를 닫는 대신 목록 상태 8로 돌아간다. 확인창의 좌우 선택과 결정도 현재 선택값에 작용한다. 이 결론은 `3ff430`, `3ff250`의 전체 분할 코드와 상시 표시 갱신 `3fef40`을 확인한 범위이며, 모든 게임 화면이나 운영체제의 창 닫기까지 마우스 경로가 없다는 뜻은 아니다.

`41b5e0`은 취소 입력을 먼저 처리해 미리듣기를 멈추고, UI out과 취소 효과음 callback을 요청한 뒤 상태 7→8로 진행한다. `419780`은 **취소 효과음 재생만** 하는 함수이며 저장 요청이 아니다. `41bf90`도 SFL 객체를 해제하는 정리 함수다. 조사한 종료 함수와 타이틀 `3b63b0`·패드 `410380` 복귀 분기에는 변경 전 값 snapshot을 복원하는 쓰기나 별도 저장 작업 요청이 없다. 따라서 여기의 취소는 화면 닫기이며, 값을 바꾸기 전으로 되돌리는 rollback이라고 구현하지 않는다. 반대로 RAM 값 변경만으로 disk 저장 성공을 선언하지도 않는다. 실제 영속 저장은 앞의 SaveJob 경계와 분리한다.

기본값 행에서 결정 입력을 받으면 `53c200`을 호출한다. 이 입력 분기에는 추가 확인 대화상자 대기가 없다. 뒤의 `4197e0` callback은 BGM·Jingle·SE·Voice 네 API에 복원된 음량/10을 다시 적용한다. 초기값 쓰기만 하고 audio manager의 현재 음량을 방치하는 구조가 아니다. 복원 대상은 위 11개 필드이며 음성 언어, 창·해상도·FXAA·마우스 배율·키 배치, 진행 상태 전체를 초기화하는 기능으로 확대하지 않는다.

수치 행별 범위·기본값·적용 경계는 외부 `native/options_numbers.json`, 사실·반증·잔여 경계는 `options_findings.json`이다. 원시 명령은 `.pdata/CHAININFO` 전체와 별도 leaf를 보존한 `options_disassembly.json`, 교차 검증은 `options_validation.json`에 있다. 주요 근거는 지도 `ev_69570d972631032231954cd67b83fe612bf8b870b88eb667e472a6213b22ba96`, 본문 속도 `ev_25bda95e42af5c626bdb509e0c7cccc7229fd7c483c11f86b0ba4e1587f2b96d`, 미리보기 `ev_c0ab3d1d9024fbdb5dc13e5dfcfe0ee508e65c76651a769a0f09c2ac06d61448`, 복원 audio `ev_a55772c35aa9e5e68143346c336882238b6204f93a13d377e3c1f32a862a0267`, 언어 로드 `ev_31495eb8197585a0d88ca967c5c63154ea8901badf160a0a11c600fb2ed90ff0`이다.

## 동영상·처형·장 끝

세 CPK의 실제 MP4 구성원은 59개다. 이를 추출하지 않고 MP4 atom을 읽어 트랙 시간·크기·코덱·샘플 시간을 검사했다. 구조 오류는 없었으며 58개는 1920×1080, 로고 1개는 1920×1088이다. 언어별 리소스가 있으므로 59개를 서로 다른 59편의 장면으로 해석하지 않는다. 갤러리 표 56행과도 별개의 집계다.

MP4 메타데이터는 영상 자체의 길이를 제공한다. 처형 진입 대사→영상→장 종료→다음 장의 실제 대기 조건은 WRD와 재생 완료 처리기를 연결해서 확인해야 한다. 현재 유메노쿠니의 키프레임 슬라이드 길이를 MP4 길이와 같다고 보고하지 않는다.

WRD `MOV`의 실제 함수 `FUN_14046fc00`은 `MoviePlay`, `MoviePlayStop`, `MoviePlayEnd`를 구분한다. 앞의 두 명령은 영화 준비를 요청하고 시나리오 대기 필드 +0x6b0을 켠 뒤 전역 재생 요청 (+0xab38,+0xab3c)에 각각 (1,0), (1,1)을 기록한다. `MoviePlayEnd`는 (4,1)을 기록한다. 이 setter `FUN_14047b0b0` 자체는 완료를 기다리지 않는다. 이름에 Stop이 있다는 이유만으로 그 명령이 바로 재생을 중지한다고 해석하면 실제 준비 요청을 놓친다.

공통 영화 준비 `FUN_1403bcba0`은 경로를 해석하고 재생 객체 생성을 요청한 뒤 영화 관련 진행 기록 `FUN_14053dee0`을 호출한다. 준비 상태 getter `FUN_1403bceb0`은 내부 상태 2인지 검사하고, 완료 getter `FUN_1403bcec0`은 상태 5 또는 0을 완료로 취급한다. 중지 요청 `FUN_1403bcf90`은 별도 작업을 요청한 뒤 상태를 4로 쓴다. MP4 끝 시간만으로 완료 플래그를 대신할 수 없다.

본편 소비자 `FUN_14047dad0`은 전역 요청 상태 1에서 준비 완료를 기다리고 `FUN_1403bcf60`을 호출하여 상태 2로 진행한다. 상태 2에서 두 명령의 처리가 갈린다. `MoviePlay`의 두 번째 값 0은 입력 함수 `FUN_1403c67b0`이 참이면 중지 요청을 낼 수 있고, 자연 완료 시에도 상태 4로 간다. 상태 4에서 완료를 확인한 뒤 영화 객체를 해제하고 시나리오 대기 +0x6b0을 해제한다. `MoviePlayStop`의 값 1은 이 입력 분기를 건너뛰며, 자연 완료 시 시나리오 대기만 해제하고 상태 3을 유지한다. 이후 `MoviePlayEnd`가 상태 4를 요청하여 해제 경로로 보낸다. 따라서 일반 재생, 마지막 상태를 유지하는 재생, 종료 명령이 구분되어 있다. 13의 후속 분석에서 이 입력은 기본 배치 F3/패드 Start의 새 누름으로 연결했다. 현재 재지정 상태·실제 중지 입력의 성공은 별도 실행 확인 대상이다. 근거: `ev_afc5449fcecb2fa8cacef6c14bf7ff2ba8e1790de772c96b99294be432819a42`.

## 공통 난수 상태와 끝값 — 정적 후속

공통 함수 `5d7910/5d7980/5d7a00/5d7a80/5d7b00/5d7ba0`은 네 개의 uint32 상태를 공유하고 호출마다 한 번 갱신한다. 시드 함수 `5d7bf0`은 이 상태를 함께 재설정한다. 확인된 직접 호출 두 곳 `3b63b0/672ef0`은 `GetTickCount`를 전달한다. 기존 타이틀 작업 `456970`과 연결하면 `3b63b0`의 상태1에서 재설정한 뒤 상태2로 넘어간다. 매 타이틀 프레임마다 재설정하는 것이 아니다. 정적 이미지의 네 상태는 `.data`의 파일 바깥 가상 꼬리 영역에서0으로 읽히며, 이것을 실행 중 시드로 해석하지 않는다. 따라서 모드마다 독립된 난수열이라고 가정하지 않는다. 다만 모든 초기화·재개 경로와 저장 파일의 상태 보존까지 닫은 것은 아니다.

단일 정수형 `5d7a80(n)`은 일반적인 비오버플로 입력에서 양수면 **0..n**, 음수면 **n..0**으로 양 끝을 포함한다. n=0도 상태를 소비한다. `5d7b00(a,b)`도 유효한 차이 범위에서 양 끝을 포함하는 방식이고, `5d7ba0`은 갱신 후 하위31비트를 반환한다. signed 극단값의 차이·절댓값·나눗수 오버플로까지 같은 범위 규칙으로 일반화하지 않는다.

`5d7a00`의 단위 실수형과 `5d7910`의 배율형, `5d7980`의 구간형은 uint32를 float32로 반올림한 뒤 계산한다. uint32 최대값은 float32에서 2^32로 반올림되므로 단위 결과가 정확히1이 되는 산술 경계가 있다. 상한이 항상 제외된다는 가정으로 구현하지 않는다. 이 값의 실제 플레이 도달 빈도는 측정하지 않았다. 정수형의 나머지 연산도 거부 추출 방식이 아니므로 이상적인 균등31비트 입력에서도 일부 폭에는 나머지 편향이 생긴다. 실제 시드 분포와 플레이 빈도는 별도다.

선택한 소비자도 구분한다. RSC `23f700`의 `wkRndMax`는 signed16 최댓값으로 추첨하고 `wkRnd`에 저장한다. `472130`은 허용값이0이면 먼저 제외하고, 나머지는 draw(99)의 결과를 허용값과 등호 포함으로 비교한 뒤 생존 목록에서 draw(개수−1)로 고른다. `1668e0`의 보상 등급은 draw(999), 후보 인덱스와 실수 혼합 추첨도 같은 전역 상태를 소비한다. 다른 소비자 `404ee0`은 draw(100)에 엄격한 `<` 비교를 쓰므로 동일 임계값의 draw(99)로 임의 교체하면 동작이 달라진다.

주 입력 `3affe0`은 상태 6에서만 작동한다. 허용 커서·페이지 변경은 `V3_SE_005`; 페이지는 최대 11행 단위다. 변경된 선택은 현재 항목의 미리보기 `3b2650` 및 해당 종류의 부가 표시 `3b2970`에 전달한다. 구매 가능 여부와 이미 구매한 열람 가능 상태는 구별한다.

상태 0 항목의 결정은 `V3_SE_000` 뒤 목록에 남는다. 상태 1 항목은 가격과 잔액을 비교한다. 충분하면 `V3_SE_001`, 본체/스크롤 `fl_ok`, 메시지 46에 가격을 넘겨 확인 상태 7로 간다. 부족하면 `V3_SE_000`, 같은 목록 잠금 표현과 메시지 47에 부족액을 넘겨 안내 상태 8로 간다. 메시지 완료 후 확인 결과가 1일 때만 `3b0c00`이 실제 구매 비트·차감·상태 2·변경 플래그를 갱신한다. 나머지 확인/안내는 구매 없이 상태 6으로 돌아온다. 상태 2의 결정은 `V3_SE_001` 뒤 viewer로 넘긴다.

취소는 `V3_SE_004` 뒤 상태 9→10에서 본체/스크롤 및 11개 행의 `fl_out`, 미리보기 닫힘, 클립 완료를 기다려 부모로 복귀한다. 구매 확인창을 띄운 순간과 실제 차감, viewer 시작과 해금 비트 쓰기를 혼동하지 않는다. 새 근거는 `3affe0`의 `ev_c0dd5c8909492b33f4f308ee830d564cf09a0061cfed110ef940cd71fe49e536`, `3b05d0`의 `ev_31ef99f20200f3f4e7ba4afac83286d67301eb01bb50de9df170068fa73c3c8e`다.

### 저장·불러오기 — 목록 강조·확인·작업 결과

공통 `3fe1e0`은 슬롯 30개의 메타데이터 준비 뒤 목록 입장 클립 완료를 기다려 상태 8로 간다. `st_save_load`는 화면 6행의 장/날짜/아이콘과 `fl_wait_0..5`, `fl_ok_0..5`, `fl_out_0..5`, 별도 스크롤을 갖는다. `3fec80` 원시는 handle와 `c255c0[index]`를 전달한다. 초기 강조는 현재 행+4로, 커서·페이지 이동 `3ff430`은 `V3_SE_005`와 새 선택 표시로 이어진다. 상시 표시 `3fef40`의 전체 분할 코드와 SFL의 `p_tx_chapter/date_000..005`·표시 부품을 같은 근거 원장에 남겼다.

목록이 준비되지 않으면 입력을 받지 않는다. LOAD의 빈 슬롯 결정은 `V3_SE_000`으로 거부하고 같은 목록에 남는다. 정상 슬롯 결정은 `V3_SE_001`·해당 행 확정 표현을 거쳐 확인 패널을 연다. 상태 9→10은 확인 `fl_in` 완료를 기다린 뒤 선택 1의 `fl_wait_on_01`을 기본으로 삼고 상태 11에서 입력을 받는다. `3ff250`의 좌/우는 `V3_SE_005`와 선택 0/1의 `fl_wait_on_00/01`, 결정은 `V3_SE_001`과 `fl_ok_on_00/01`로 연결된다. 선택 0에서만 SAVE/LOAD 작업으로 진행하며 선택 1은 목록으로 돌아온다. 취소는 `V3_SE_004`와 `fl_out_on_00/01` 뒤 목록 복귀다. 이 경로의 마우스 취소 부재는 앞의 입력 절 범위 그대로 유지한다.

SAVE 작업은 busy 해제와 최소 60 tick 뒤 결과 코드 2를 확인한다. 성공이면 해당 슬롯의 존재/메타데이터 표시를 갱신하고 목록 상태 8로 돌아간다. 다른 자동 저장 진입은 상태 0x10/0x11 뒤 종료 상태로 가므로 모든 저장을 목록 재표시로 강제하지 않는다. 실패는 별도 오류 메시지 상태이며 성공으로 표시하지 않는다. LOAD 성공은 종료 애니메이션을 거쳐 별도 재개 consumer로 전달한다. 목록을 닫을 때도 `fl_out`과 완료 대기가 있다. 이 정상 계약에 없는 저장 성공 축하 클립·추가 효과음을 만들어 붙이지 않는다.

이 자료로 대표 타이틀→옵션 또는 갤러리→저장/목록의 주요 정상 화면·소리 반응을 상태와 함께 재구성할 수 있다. 모든 갤러리 콘텐츠의 개별 viewer, 모든 설정 변형, 최종 합성 픽셀과 실제 청취는 별도 한계로 남긴다. 보너스 육성/던전의 표현 완료를 이 결과에 합산하지 않는다.
