# 물리 입력·논리 행동·설정 소비

## 조사 경계와 증거

원본 Steam PC 설치본과 코드 영역만 복원한 분석본을 읽었다. 원본/분석본 SHA256은 `08_카메라.md`와 동일하다. 설치 파일·저장 자료·키 배치를 수동으로 변경하지 않았다. 원작 프로그램 자체 실행으로 새 `config.txt`가 생성된 뒤 그 내용을 읽어 관찰했다. 실제 게임 화면에서 아래 모든 키를 눌러 검증했다는 뜻은 아니다.

입력은 물리 장치 상태 → 사용자 키 배치 → 논리 행동 → 모드·허용 조건 → 화면 상태의 순서로 해석해야 한다. 물리 키 이름 하나를 찾았다는 이유로 모든 화면의 기능을 동일하게 정하지 않는다.

## 키보드의 실제 장치 상태부터

`FUN_1405bec30`은 DirectInput 장치의 상태 조회에 256바이트 버퍼를 전달한다. 성공하면 원본 데이터 `0x14078b500`의 변환표를 사용하여 custom 키 인덱스 1~109 각각의 장치 바이트를 찾고, 해당 바이트의 `0x80` 비트를 검사하여 내부 키 bitset을 만든다. 실패하면 장치 재획득을 요청한다. 256바이트의 상위 비트가 키 누름 상태라는 해석은 [Microsoft의 DirectInput 키보드 문서](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee418261(v=vs.85))와도 일치한다.

내부 키 인덱스와 DirectInput 바이트 인덱스는 같은 번호가 아니다. 예를 들어 W는 custom 33 → 장치 바이트 17, A는 11 → 30, S는 29 → 31, D는 14 → 32, Enter는 41 → 28, Escape는 53 → 1, Space는 64 → 57이다. 전체 109개 변환은 외부 `native/input_keyboard_scancodes.json`이다.

등록된 키보드 객체의 `FUN_140579d10`은 이전 상태와 새 상태를 나누어 기록한다.

```text
현재 상태 +0x20 = 이번 장치 상태
이전 상태 +0x30 = 직전 현재 상태
새로 누름 +0x40 = 현재 & ~이전
해제 상태 +0x50 = 이전 & ~현재
```

따라서 매 tick의 누르고 있음, 새로 누른 순간, 뗀 순간을 하나의 bool로 합치면 화면에 따라 입력이 반복되거나 사라진다. 현재 상태 조회 `579bc0`과 새 누름 조회 `579c00`도 별도다.

근거: 장치 폴링 `ev_46b0f27bcc413bd1390f412d40b0ffa8f19a518bbe51397be0e4f1493634afdc`, 상태 전이 `ev_96bc38348cac6b6031b371b1c39169b80b0598b3328d476c96153181625466ba`. 해당 명령 바이트는 외부 `native/input_disassembly.json`에 기록한다.

## DirectInput 취득·폴링과 원작 타이틀 입력 미수신 조사

장치 생성 `5be950`은 시스템 키보드에 data format을 설정하고 `SetCooperativeLevel(HWND,6)`을 호출한다. 6은 `DISCL_NONEXCLUSIVE | DISCL_FOREGROUND`다. HWND는 전역 `0x140d22858`에서 가져온다. 이후 `Acquire`를 호출하지만 data format·cooperative level·Acquire의 HRESULT를 객체에 저장하거나 검사하는 분기는 없다. foreground 모드에서는 대상 창이 배경으로 가면 장치가 자동으로 취득 해제된다는 뜻이다([Microsoft cooperative-level 문서](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee417921(v=vs.85))). 현재 실행에서 실제로 취득이 실패했다는 관찰과는 구분한다.

업데이트 `670360`은 전역 `0x140d22660`의 키보드 서버로 `5bec30`을 한 번 호출한다. 이 폴링 함수는 서버 `+0x20..+0x2f`의 16바이트 bitset을 먼저 지운다. 이어 COM vtable `+0x48`의 `GetDeviceState(device,256,stackBuffer)`를 호출한다. 이 경로는 buffered event 목록이 아니라 현재 상태를 읽는 immediate 방식이다. 256바이트 키보드 자료 형식과 오류 반환 의미는 [Microsoft GetDeviceState 문서](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee417897(v=vs.85))와 대조했다.

조회 HRESULT가 음수이면 COM `+0x38`의 `Acquire`를 한 번 요청하고 **같은 tick에는 재조회하지 않는다**. 따라서 해당 tick에는 0 bitset이 등록된 키보드 객체로 전달된다. 성공했을 때만 109개 키 변환표로 누름 비트를 만든다. 실패한 키보드 상태를 직전 상태로 유지하는 구현이 아니다. 서버 등록 목록의 각 소비자에 `579d10`을 호출하면서 현재→이전, 새 조회→현재를 기록하고 새 누름·해제를 계산한다. 끝의 `579c70`은 `+0x60..+0x6f` 반복용 bitset과 `+0x70` 카운터를 갱신하며 `+0x40..+0x4f` 새 누름은 지우지 않는다. 따라서 반복 처리가 타이틀의 새 누름을 소거한다는 설명도 반증됐다. 공통 `49e920`은 context의 virtual `+0x178`을 호출한 뒤 렌더 준비를 진행한다. 부모가 원본 프로세스에서 제한된 포인터 읽기로 확인한 실제 slot은 RVA `49dad0`이다. 이 override의 원시 `49dadf`는 곧바로 `670360`을 호출한다. 따라서 실행 경로는 `49e920 → virtual+0x178 → 49dad0 → 670360 → 5bec30 → 579d10`이고, 실제 override가 base 함수와 다르다는 이유로 키보드 폴링이 생략된다는 가설도 반증됐다. `49dad0`은 폴링을 마친 뒤 입력 manager가 있으면 `+0xa4=1`을 기록하고 큐의 callback을 소비한다. 이 순서는 `.pdata/CHAININFO` 세 조각 `49dad0..49dc17` 전체와 대조했다. 이후 `49b910`은 렌더 pass 구성이다. 별도 `49d550` 게임 tick/타이틀 scan과 이 큐 사이의 전체 스레드 동기화는 아직 미확정이다.

원작 실행의 타이틀이 입력 대기 상태 8이고 입력 허용 전역이 `+0x1e2c=1`, `+0x1e30=0`인 부모의 읽기 관찰이 있다. 그러나 `3c34a0`의 키보드 전체 scan에는 입력 객체 `+0xa0` 가드가 없다. `+0xa0/+0x1c`는 마우스 분기에만 적용되므로 이 값으로 키보드 미수신을 설명하는 가설은 반증됐다. 허용 전역·UI 준비가 맞다는 사실도 DirectInput 키 누름을 받았다는 증거는 아니다.

추가 읽기는 서버 포인터·장치 포인터·등록 수와 작은 상태 배열만으로 제한할 수 있다. 서버는 전역 `0x140d22660`, 등록 수는 서버 `+0x18`의 4바이트, 장치는 `+0x30`의 8바이트, 변환 상태는 `+0x20`의 16바이트다. 이미 알려진 context `+0x1b8`의 키보드 객체에서는 `+0x20/+0x30/+0x40/+0x50` 각 16바이트가 현재·이전·새 누름·해제다. 서버와 키보드 객체를 혼동하지 않는다. HWND 전역을 읽어도 Sky의 opaque window ID와 같다고 단정할 수 없다.

부모의 후속 실행 관찰에서는 마우스 분기 조건 `manager+0xa0=1`, `+0x1c=1`, context `+0x270` nonnull을 확인한 뒤, Sky에 문서화된 drag를 빈 공간 `(220,800) → (520,800)`으로 한 번 수행했다. 그 뒤 원작 화면이 **PRESS ANY BUTTON에서 NEW GAME/LOAD GAME/QUIT 선택 화면으로 전환된 것을 실제로 관찰**했다. 이 결과는 타이틀의 입력 경로 전체가 막힌 상태라는 설명을 반증하며 해당 실행에서 마우스 입력이 전달됐음을 뒷받침한다. 도구 wall time 1.1초는 실제 hold 시간으로 환산하지 않았다. 앞선 키보드 press가 전환하지 못한 이유, 합성 키와 물리 키의 차이, 정확한 유지 시간은 여전히 미확정이다.

GetDeviceState HRESULT는 이 함수의 지역값이며 알려진 객체 필드에 마지막 오류가 남지 않는다. 따라서 입력이 끝난 뒤 배열이 모두 0이라는 snapshot 하나는 정상 무입력·조회 실패·폴링 사이의 짧은 누름을 구분하지 못한다. Sky 문서의 `press_key`에는 별도 hold duration/down/up 기능이 없다는 부모 확인이 있으며, 짧은 입력이 immediate poll 사이에서 사라졌을 가능성은 가설로만 남긴다. 이 조사를 위해 입력 주입·메모리 쓰기·디버거 부착·설정 변경을 수행하지 않았다.

근거: 생성 `ev_c071af3dec00c4c155e5e99b928dc2ecdadbd6dfc5ebde17ceffe70b3a8cd4c7`, 갱신 `ev_3d4bd9e7ef7af5a72af11a6097fb206f0b58ab935871c6b81755dcccc16ddb0d`, 폴링 `ev_46b0f27bcc413bd1390f412d40b0ffa8f19a518bbe51397be0e4f1493634afdc`, 상태 전이 `ev_96bc38348cac6b6031b371b1c39169b80b0598b3328d476c96153181625466ba`, 반복 처리 `ev_267543f056007c2f6f6e677d7f6b71896b274c43b0f2c24afc0067ddcebb8cb5`, scan `ev_78e190953fdbcdaf8f1bef787e5cd667df0dee4bd9ced40e4bebfb52b215c5a3`. 실행 override `49dad0`의 근거는 `ev_134dc5660840f38020b7b864eb03e0a45f9ffb086a1d682add4f4bc8a6ff12ac`다. 외부 `native/input_acquisition_findings.json`과 `native/input_acquisition_disassembly.json`에 수신 경로와 읽기 한계를 보존했다.

## 실제 키 배치는 행동마다 최대 세 키

설정 lexer `4a19d0`은 172개 토큰 이름을 구분한다. 실제 배치 적용 `4a1890`은 행동 토큰 13~47의 35개 행동과 키 토큰 62~170을 허용한다. 내부 변환은 `행동 인덱스=토큰−13`, `키 인덱스=토큰−61`이며 행동마다 최대 3개의 키를 `config+0x40` 행렬에 기록한다. 물리 키 변환표와 설정 키 이름의 연결을 이 산식으로 교차 확인했다.

원본 실행 파일의 compiled 기본 행렬 `0x1408cfa90`과 원작 프로그램이 생성한 `config.txt`의 35개 키 배치를 비교하여 모두 일치했다. 관찰 파일 SHA256은 `663b43d647bfa7685b4110f3d4714b626e8e508f9e5317f4df15dbfb4dec560b`이며 비교 결과는 외부 `native/input_config_comparison.json`이다. 이후 사용자가 바꾼 설정까지 이 기본 배치와 동일하다고 가정하지 않는다.

## config 파싱 값에서 실제 입력 배치까지

`4a1890`이 config `+40`에 쓴 배열과 실제 키 조회 `3c0aa0`이 읽는 `1408cfa90`은 처음에는 별도다. 그러나 적용 `4a1470`은 검증 `4a2510`을 통과한 뒤 `4a29d0`을 호출한다. 이 함수는 35개 행동 각각의 3개 slot을 `3c0ef0`에 전달한다. 원시 leaf `3c0ef0..3c0f0e`는 slot 0~2를 허용하고 `1408cfa90[(action×3+slot)]`에 전달 키 번호를 쓴다. 따라서 이 배열은 compiled 기본값이면서 **로드 후 재지정 가능한 실제 입력 행렬**이다. 기본 config 35/35 일치만으로 사용자 변경 적용까지 주장한 것이 아니라 이 복사 소비를 추가로 닫았다.

같은 `4a29d0`은 config `mouse_speed +38`이 양수일 때 입력 manager `+14`로 복사한다. 최종 X/Y 시점 축은 mouse delta에 이 배율을 곱하고, 뒤에 게임 내 반전 옵션을 반영한다. 이는 `09_시스템.md`의 조사 조준점 속도 `permanent+66`과 다르다. config 적용 호출은 공통 초기화 `49e9f0 → 3bbfa0 → 4a1470`에서 확인했으며 실행 중 파일의 자동 재로드·실시간 변경을 선언하지 않는다.

외부 `native/options_findings.json`·`options_disassembly.json`에 적용과 반증을 보존했다. config를 파싱했다는 사실과 실제 입력 배열을 바꿨다는 사실, RAM 배치와 disk 파일 쓰기를 구분한다. `4a1470/4a29d0`은 입력 적용이며 config 파일 쓰기 함수가 아니다. 근거는 `ev_6c35cef46968648cad184d1daf2f3a57fcfa76b2fff24b6d62393c25d99e33e7`, `ev_85515489faa6a04fde29d2f22ab0800609909bd85f125b6693f25ab4dd4d6202`, `ev_fc8b93244c69a2360791cb7b6ee6a9ea6df3a36b633fe61f4d26ab4526392655`와 위 원시 leaf다.

## 패드는 원시 XInput 비트를 다시 변환한다

`SpPadServer`의 `570aa0`은 XInput 또는 DirectInput 상태를 읽고 등록된 패드 객체에 전달한다. 실제 디지털 변환 `56f540`은 장치 종류에 따라 분기한다. XInput 분기는 `wButtons`를 그대로 게임에 넘기지 않고 다음 논리 비트로 바꾼다. 물리 버튼의 원시 비트 의미는 [Microsoft의 XINPUT_GAMEPAD 문서](https://learn.microsoft.com/en-us/windows/win32/api/xinput/ns-xinput-xinput_gamepad)를 기준으로 대조했다.

| XInput 물리 버튼 | 게임 내부 비트 | 기본 키보드 대응 |
|---|---:|---|
| A | 0x40 | Z |
| B | 0x20 | Escape/R/X |
| X | 0x80 | F1 |
| Y | 0x10 | Enter |
| 왼쪽/오른쪽 Shoulder | 0x100 / 0x200 | Q / E·Space |
| 왼쪽/오른쪽 Stick 누름 | 0x100000 / 0x200000 | 기본 키 없음 |
| Start | 0x400000 | F3 |
| Back | 0x800000 | 별도 기본 배치 없음 |

스틱 축은 32767로, 트리거는 255로 나누며 두 Y축에는 부호 반전이 있다. 이 단계 뒤 `56fac0`이 스틱 dead zone·방향 임계·트리거 임계를 처리하고 방향/트리거 논리 비트와 새 누름·해제·반복 상태를 만든다. DirectInput 분기는 두 GUID의 특례 레이아웃과 일반 레이아웃도 구분한다. 이를 모든 제조사 패드의 동일한 물리 배치라고 일반화하지 않는다.

## 마우스의 물리 버튼·휠·새 누름

## 표시 자료와 실제 입력 자료를 혼동하지 않는다

Brain Drive의 실제 소비에서는 같은 논리층이 다른 기능으로 쓰인다. `3c11b0`은 bit 4/8, 즉 기본 A·왼쪽 화살표 / D·오른쪽 화살표와 패드 D-pad 좌우를 −1/+1로 만든다. 둘 다 누르면 왼쪽 분기가 먼저다. 다음으로 패드 왼쪽 스틱 X를 dead zone 0.125로 재매핑하며, 그 값이 없을 때 허용된 마우스 X 변화량도 조건부로 받는다. `3c3ce0`은 마우스 버튼 1(오른쪽 버튼) 또는 bit 1(W·위쪽 화살표/D-pad 위) 또는 선택된 결정 비트의 누르고 있음을 검사하고, `3c3de0`은 같은 조합의 새 누름을 검사한다. 따라서 이 미니게임의 가속 입력을 E/Space 또는 고정 Enter라고 정하면 실제 default 배치와 맞지 않는다. 부모 소비 `106e00`은 이 판정에 따라 throttle 경로를 나눈다.

근거: `ev_cb18bbd81f3f6bb6418a1a06541db816cdf59916448a512860ee5299fef77351`, `ev_762ce7845d3628a15c2143d49d4158ed58c4b4f63819b6cd26b3d8cd59d92986`, `ev_96aa4a2eaf54e22b9c2a4d6e32fcf6a6641d47937e117555a5fa3019f9f94d80`.

## 도움말의 모달·소리·페이지 입력

공통 도움말 wrapper `3a07d0`은 안내 창·상세 보기·배경/정지 처리 객체를 따로 만든다. `3a0b20`은 요청한 도움말 라벨을 기록하고 `3bc0f0(1)`로 전역 모달 상태를 세운 뒤 일반 SE32개 플레이어에 `5433f0(1)`의 pause 요청을 전달한다. 이 함수가 pause하는 대상은 BGM2개·음성8개와 별개의 SE 목록이다. 모든 소리를 하나의 정지 스위치로 취급하지 않는다.

모달 getter `3bc050`은 전역 값을 반환한다. 실제 탈출 main은 도움말 wrapper를 갱신한 뒤 이 값이 켜져 있으면 구성요소의 진행 대신 다음 scheduler 호출로 돌아간다(17). 그러므로 도움말 표시와 해당 모드의 시간·이동 정지는 호출자가 어떻게 모달 상태를 소비하는지까지 확인해야 한다. 이 사례를 다른 모든 게임 모드의 같은 pause 정책으로 일반화하지 않는다.

`3a09a0`은 준비 대기→안내 진입→선택 결과→상세 보기→복귀/전체 퇴장이라는 상태를 가진다. 안내 입력 `3a1ae0`은 취소와 상세 보기 요청을 구분하며, 실제 자료가 상세 보기를 허용할 때만 그쪽 결과를 낸다. 상세 입력 `3a3d10`은 현재 하위 상태에서 페이지 전환이 허용되고 페이지 수가2 이상일 때 좌우 인덱스를 순환시키고 전환 중 flag를 세워 중복 입력을 막는다. 닫기 결과와 안내로 돌아가기 결과도 다르다.

최종 퇴장은 연출·배경 정리를 거친 뒤 `3bc0f0(0)`과 `5433f0(0)`을 호출하고 다음 상태에서 idle로 돌아간다. 취소 키를 받은 바로 그 순간에 모든 객체가 정리되고 게임 입력이 재개된다고 축약하지 않는다. 실제 페이지 그림·키 표시 전환·소리의 재개는 실행 관찰이 남는다.

## 마우스 좌표 → display target → 상대 조준 → 실제 hit

이 절은 원본 입력을 조작하거나 새로운 Win32 UI 함수를 호출한 실험이 아니다. 복원 PE의 정적 REA·원시 명령과 독립 float32 계산을 대조했다. 외부 원장은 `native/mouse_coordinate_findings.json`, 재현 helper는 `native/analyze_mouse_coordinates.py`다. HWND·프로세스 입력·설정·저장 자료에 쓰지 않았다.

### 화면 좌표 변환은 두 실제 target 크기 사이의 aspect 보정

`57c230`은 `GetCursorPos → ScreenToClient`로 창 client 기준 정수 위치를 얻는다. API의 screen→client 기준은 [GetCursorPos](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getcursorpos)와 [ScreenToClient](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-screentoclient)의 공식 계약과 대조했다. 이 분기에서 DirectInput의 상대 X/Y를 그대로 조준 값으로 사용하지 않으므로, 뒤의 delta를 hardware RawInput 단위라고 부르지 않는다.

`5af060 → 5b0dc0`은 `SpGraphicServer` 전역 `0x140d20aa8`의 두 target을 사용한다.

| 객체 | 실제 생성·선택 근거 | 변환에서의 역할 |
|---|---|---|
| graphics+0x88 | `5b0600 → 5b0f50`, swap-chain GetBuffer/GetDesc, `swap chain back buffer` | source 크기 Ws/Hs. 각 target+0x38/+0x3c |
| graphics+0x68 | `5b10d0`, `display color`, graphics+0x18/+0x1c로 생성한 배열에서 `54b940`의 index0 선택 | destination display 크기 Wd/Hd |
| graphics+0x78 | `5b10d0`, `render color`, graphics+0x20/+0x24로 별도 생성 | 위 마우스 변환의 destination으로 사용하지 않음 |

따라서 내부 render resolution과 display resolution을 하나의 값이라고 합치지 않는다. constructor `5b1870`도 두 크기를 별도 설정한다. 실제 모든 설정의 destination이 항상1920×1080이라는 함수 계약은 아니다.

양의 target 크기에서 native 식은 다음과 같다. source는 swap-chain buffer, destination은 display target이다.

```text
sx=Wd/Ws, sy=Hd/Hs
gx=max(0, 1-sx/sy), gy=max(0, 1-sy/sx)
X=(sx*clientX - gx*Wd/2)/(1-gx)
Y=(sy*clientY - gy*Hd/2)/(1-gy)
정수화 = signed trunc(float32(value+0.5))
```

이는 화면에 맞춰 들어간 중앙 content 영역을 역변환하는 식이다. **조건부 계산 예**로 destination1920×1080, source1280×720이면 위치를1.5배 한다. source2560×1080이면 좌우 content 여백은 각각320, source1280×1024이면 위아래 여백은 각각152다. 각 client 중심은 destination(960,540)으로 옮겨진다. 이 사례들을 실제 원작 창 크기를 바꾸어 관찰한 것으로 세지 않는다.4개 크기 조합·정수 좌표 grid의 forward/inverse 수치 검사에서 roundtrip 오차0을 확인했다. 일반 정수화에는 양자화가 있으며 음수의 `+0.5 후 절삭`은 대칭 반올림과 다르다. 창 밖 좌표·여백의 값은 뒤 SpMouse clamp와도 구별한다.

### 현재 위치·delta·재중앙화와 스무딩 반증

`57c230`이 전달하는 absolute 모드1에서 `57b490`은 이전 current를 저장한 다음 변환 위치를 SpMouse+0xc8/+0xcc에 쓴다. 보정 counter+0x128이 양수인 특수 분기는 pending 보정을 먼저 소비한다. X는 `[marginX, serverWidth-marginX-1]`, Y는 `[marginY, serverHeight-marginY-1]`로 제한하며 margin은 SpMouse+0xf8/+0xfc다. **clamp한 current−직전 current**가 +0xb4/+0xb8의 delta다. server 크기는 constructor에서1920×1080으로 시작하지만 `670360`이 매 poll graphics+0x18/+0x1c를 `57c030/57c020`으로 복사한다. 초기값을 영구 크기로 읽지 않는다.

raw leaf `57a100`과 `57a1a0`은 둘 다 이 **같은 +0xb4/+0xb8 두 float**를 그대로 복사한다. 하나가 원본이고 다른 하나가 smoothed buffer라는 가설은 반증됐다. `57a3c0`은 current 두 float를 그대로 읽는다. `57b300`은 버튼 반복 시간, `57b190`은 다중클릭·버튼 이벤트의5단위 거리 조건이어서 좌표 스무딩 함수가 아니다. SpMouse+0xc0/+0xc4는 activity 기준 anchor이며 매 tick previous 위치로 사용하지 않는다. 기본 SpMouse의 virtual update `57b2a0`은 `ret0`이다. 별도 subclass나 OS 전체 입력 정책까지 no-filter라고 일반화하지 않는다.

`3c9420`의 상대 모드 기본값 input+0x20=1은 `3c9cb0`으로 client RECT 중심을 구한다. static 경로 `57c040`은 ClientToScreen/SetCursorPos 뒤 실제 위치를 다시 GetCursorPos/ScreenToClient/5af060으로 읽고 등록된 모든 mouse 객체에 `57b380`을 적용한다. 후자는 current를 동기화·clamp하고 **delta 두 값을0으로 reset**한다. 재중앙화만으로 다음 조준이 자동으로 크게 튄다는 설명은 이 동기화 분기를 빼먹은 것이다. 이 API를 분석 중 호출하지 않았다. 다른 모드 `3c9d50`의 창 밖 검사는 같은 client 위치의 동기화 경로이며, 이 함수에 ClipCursor가 없으므로 OS 포인터를 창 안에 가둔다고 확정하지 않는다.

### delta의 시간 정규화·감도와 대표 미니게임 소비

입력 manager `3c9420`은 두 갱신 사이 microsecond 차이에서 `N=1/(elapsedSeconds*60)`을 만든다. 60Hz와 같은 interval이면 N=1이다. 같은 mouse delta를 두 배열로 읽고 다음 배율을 적용한다.

| input manager 필드 | 소비식 | 생성 기본값 |
|---|---|---|
| +0x2c/+0x30 | mouse deltaXY×N | 뒤 카메라 축 등이 추가 처리 |
| +0x34/+0x38 | mouse deltaXY×N×input+0x10×input+0x14 | +0x10≈0.15, +0x14=1 |
| 카메라 축 `3c2de0/3c3080` | 앞의 +0x2c/+0x30×input+8을 ±input+c로 clamp, input+14 적용, 마지막 X/Y 반전 | +8≈0.05, +c=6 |

이는 시간·감도 배율의 차이이며 이전 위치를 보간하는 시간 스무딩이 아니다. default만으로 저장된 조준 옵션의 모든 값·모든 writer를 확정하지 않는다. 실제 경과 시간·입력 허용·pad 우선순위와 recenter 모드가 결과를 바꿀 수 있다.

대표 `3913e0`은 상태+0xe0=8·+0x98=4일 때 `3c1330/3c13b0`을 읽는다. pad 왼쪽 스틱의 해당 축이 deadzone0.125/재조정0.875 뒤 유효하면 pad가 우선이고, 아니면 +0x34/+0x38을 반환한다. 축×10을 ±40으로 clamp해 커서+0x124/+0x128에 더한 뒤 네 기울어진 경계로 제한한다. default·N=1·유효 mouse deltaX20이면 이 단계의 X 증분은30, deltaX100이면 clamp 후40이라는 **조건부 계산 예**다. 실제 체감 속도 측정이 아니다.

같은 +0x124/+0x128을 `4ab240`에 넘겨 SFL 커서 sprite를 배치하고 `38f530` hover에서도 사용한다. 표시와 hit의 기준 좌표를 따로 늘리지 않는 연결이다. 실제 hit의 polygon·현재 page·미완료 조건은 [05_미니게임.md](05_미니게임.md)의 별도 계약이다. 절대 마우스 후보 `3c1bb0`은 이 설치본에서 `return0` stub이므로 모든 미니게임이 절대 mouseXY를 받는다고 선언하지 않는다. [04_재판.md](04_재판.md)의 상대 조준·투사체 발사 시 좌표 고정도 이 대표 페이지 hit와 구별한다.

팬게임의 기준 좌표를1920×1080으로 정한다면 display target과 실제 content rectangle을 명시하고 같은 역변환의 결과를 sprite·hit에 함께 적용할 수 있다. [06_UI.md](06_UI.md)의 design→NDC→viewport는 그 반대 방향의 표시 계약이며, [08_카메라.md](08_카메라.md)의 수평 전체 FOV는3D ray/투영을 위한 별도 값이다. FOV를2D mouse 배율에 곧바로 곱하지 않는다. 원작의 다른 DPI·window/borderless 조합에서 실제 target 크기·활성 분기를 관찰한 것은 아니다.

주요 근거는 변환 `5b0dc0 ev_44dc55e5e74092a7d53d9a8d292482ecf69d1b694ee52df3067e7b4ece082fdb`, 위치·delta `57b490 ev_666030f6511ceecc5eb2e778c695b0908a372a6cccd4afb458b59cd46d59b032`, manager 갱신 `3c9420 ev_6833c0ad0d50ba115d88e11343830f30c1f05b7444db98dea52d75083deb5127`이다. 원장의22개 REA record 외에 getter·재중앙화 sync·server setter 원시 명령을 보존했다. 초기 writer 후보 `5af480/5afe40`의 RBP 저장은 stack이었다는 반증과 `54b900`은 flag reset뿐이라는 기각도 기록했다. 이를 target 생성 근거로 사용하지 않는다.

### 조사 조준점 속도 옵션은 소비자에서 한 번 더 곱한다

옵션의 조사 조준점 속도는 permanent+0x66의u16이며 기본3이다. 원시 getter53b240과407c80의 실제 XMM0 float 반환을 대조했다. 설정1/2/3/4/5는 각각0.5/0.75/1/1.5/2배이고, 범위 밖은1배다. 이 값은 입력 manager+10/+14에 기록하는 setter가 아니라 탐색 커서40ac40에서 추가로 곱하는 배율이다. 따라서 앞 절의 기본 마우스 gain0.15와 옵션 기본3을 같은 필드라고 해석하지 않는다.

40ac40의 상대 입력은3c2560→3c25d0/3c26a0에서 얻는다. 패드 왼쪽 축이 deadzone0.125를 넘으면 우선하고 나머지 범위는0.875로 정규화한다. 그 외에는 마우스의+34/+38을 쓰지만, 장치 허용 조건에서 mouse button index2가 눌리면0을 반환한다. 이 함수의 절대 입력 helper3c2550은 해당 설치본에서return0이다. 상대 벡터의 크기에10×옵션 배율을 곱하고, 기존 hover ID가 유효하면서 크기가0.7보다 작으면 먼저 크기를6으로 나눈다. 커서는 내부X0..1920/Y0..1080으로 제한한다. 작은 이동의 감속 조건과 대상 붙잡기 후속 분기가 있으므로 일정 배율 하나로 전체 조사 체감을 설명하지 않는다.

이는 탐색 조준점 소비자 한 곳의 규약이다. 모든 미니게임의 감도·최종 픽셀·장치 지연을 확인한 것은 아니다. 앞 절의 실제 target 기반 좌표 변환과, 여기의 탐색 커서 제한은 서로 다른 층이다. 근거: `ev_6b6b86b2ff9cd7d75569f98207592048338eb43806b556f1297c3a3ddec0a381`, `ev_534f3b0bb83e8e917d095f2926e7af5bb8992b61c24728eefdb9f8db24d1aeb5`, `ev_d2895a27113d50d03aa349da81c1906a41b309a2bf403c6a3d2b9410211a57a9`, `ev_ae0e486cd7d8e2041f1e11bc507433ecdc902f6b4b343d07ba7b199c45db57f5`, `ev_d2dfdbae48644caf23163f7226c8c92a144a51bea218d62e52634a61b361033f`, `ev_5e2eab0af3fcf821f6384a839ffaadfaf0ea678a62c376c0baf61ce5ba9cea35`, `ev_ddcd9a9cd75448fdfe15d09fedd28f2b6c8681d606e3b675df6987afc8fd4578`. 외부 `native/aim_option_findings.json`, `native/aim_option_disassembly.json`, 재현 `native/probe_aim_option.py`.

## 고정·궤도 시점 모드0의 조작 소비

직접 실행 없이 정적 REA로 모드별 경로를 분리했다. `409240`은 탐색+90이0이면 `409c50 →409cc0`의 시점 갱신과 `40ac40`의 조준 갱신을 부른다. +90이1이면 수동 보행 `40a120`으로 간다. 후자의 오른쪽 클릭/Enter→+258 토글을 모드0에도 있다고 설명하지 않는다.

모드0의 X축 `3c2110`은 논리 방향 bit4/8, 오른쪽 스틱 axis2, 허용된 마우스 순으로 검사한다. Y축 `3c2330`은 bit1/2와 오른쪽 스틱 axis3을 쓴다. 반대 디지털 방향이 함께 눌리면 먼저 검사한 음의 방향이 우선이다. 스틱은 절댓값0.125를 넘을 때만 `(절댓값−0.125)/0.875`를 원래 부호로 돌린다. X/Y 반전은 최종 축에 적용한다.

마우스로 시점을 바꾸는 분기는 입력 허용 전역·manager+1c·장치 포인터가 유효하고 **mouse button index2가 눌려 있어야** 한다. delta×manager+0을 ±manager+4로 제한한 뒤 manager+14를 곱한다. 같은 가운데 버튼 조건이 조사 조준의 `3c25d0/3c26a0`에서는 마우스 조준 delta를0으로 만든다. 따라서 조사 조준과 시점 회전은 같은 마우스 입력을 무조건 함께 소비하지 않는다. `3c2110`의 decompiler가 만든 `extraout_XMM0` 표기는 원시 명령과 대조했으며, 실제 반환은 XMM6에서 XMM0로 복사한다. 임의의 미초기화 입력값으로 해석하지 않는다.

`409cc0`은 각 축의 목표 증분을 `입력×(상한−하한)/90`으로 만든 뒤 기존 증분에서0.5 비율로 접근한다. 무입력에서 수평 증분은0.25배 후 절댓값0.1 미만이면0, 수직은0.5배 후0.05 미만이면0으로 만든다. 수직은 정렬된 경계로 제한한다. 수평은+ac에 따라 경계 제한 또는0..360도 순환을 쓰므로, 모든 방이 같은 회전 범위라는 뜻이 아니다. 업데이트 기반 식이며 체감 속도·밀리초 실측으로 부르지 않는다.

방향 상태 `40bcf0`는+214가 활성일 때 네 판정의 반전값을+2c4..+2d0에 기록한다. `35e880 →352c00/362a70 →3599d0`은 이를 HUD+2458..+2464와 enable+2454로 전달하고 enable 변경 때 유효 핸들에 `fl_in/fl_out`을 요청한다. 이 함수들에는 클릭 hit나 카메라 회전이 없다. 방향 표시가 보인다는 사실만으로 누를 수 있는 화살표나 화면 가장자리 자동 회전이라고 확정하지 않는다.

## 공통 context의 활성 상태와 입력 동기화 gate

직접 실행 없이 기존 context의 작성 함수를 정적 REA로 좁혔다. 생성자 `492f60`은+1e2c와+1e30을 모두1로 초기화한다. 창 메시지 처리 `496400`은 메시지6에서 wParam의 상위16비트가0이고 하위16비트가0이 아닐 때+1e2c=1, 그 밖에는0을 쓴다. 이 필드를 막연한 게임 모드 준비값으로만 해석하지 않는다.

`49dd30`은 자신의 HWND와 `GetForegroundWindow()`의 일치 여부를 구한 뒤, 그 bool과+1e2c가 **다르면+1e30=1, 같으면0**을 쓴다. `49dde0`은+1e30이 이미 켜져 있을 때 같은 비교를 수행해 일치하면0으로 푼다. 입력 소비자는+1e30==0뿐 아니라+1e2c!=0도 요구하므로, 비활성 상태끼리 일치했다고 입력이 켜지는 것은 아니다. 이전의 '입력 허용 전역 전체 의미 미확정' 중 이 작성 계약을 좁혔으며, 실제 합성 입력 미수신의 원인으로 확정하지 않는다.

## 아직 남은 입력 경계

- 다른 DPI·비기본 display 크기·window/borderless에서 실제 target 크기와 입력 활성 분기, 감도 필드의 모든 writer·설정값. 위의 변환·대표 조준 배율은 정적 근거다.
- 키보드·패드 입력 허용 전역 필드의 모든 작성 원인과 실제 창 포커스/장치 분리 관찰.
- 모든 마우스 모드·개별 미니게임의 추가 필터·hit 정책과 전체 포커스/비활성 상태의 실행 관찰. X/Y 반전과 대표 상대 조준 소비를 전체 공통으로 일반화하지 않는다.
- 논리 버튼을 기능으로 바꾸는 각 모드의 소비 전체. 위 표를 전 모드 공통 단축키 설명으로 사용하지 않는다.
- 실제 원작 화면의 키 입력·패드 조작 검증. 프로그램 생성 config 관찰과 실제 게임 조작 검증을 구분한다.
