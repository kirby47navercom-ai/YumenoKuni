# 07 — 음향 큐·루프·대본 전환

## 전체 설치본의 확인 범위

원본 오디오는 재생/복호화/저장소 편입하지 않고 metadata를 읽었다. `tools/re/audio.py`는 ACB의 UTF 표, AFS2(AWB) 색인, HCA 헤더와 큐 참조 그래프를 직접 해독한다. 원본 데이터와 분석 JSON은 `C:/Users/kirby/Downloads/v3_re/audio_metadata/` 및 `resources/`에 있다.

| 항목 | 실제 개수 | 확인 |
|---|---:|---|
| ACB |20|모든 하위 UTF 표·CueName→Cue 참조|
| 이름 붙은 Cue |31,272|Sequence→Track→Command noteOn→Synth→Waveform 연결|
| 내장 AFS2 stream |1,464|ID·정렬·범위·헤더|
| 외부 AWB |5|BGM93/JINGLE7/MOVIE50/VOICE14,828/VOICE_ENG14,828|
| 외부 HCA |29,806|모든 헤더·sample count·암호 방식 필드|

20개 ACB의31,272큐는 모두 실제 참조 그래프를 따라 하나의 waveform으로 연결됐고, 미해석 참조·누락·다중 연결은0이다. 이 결과는 순서/랜덤/볼륨 명령 전체를 재생해 검증했다는 뜻은 아니다. `cue_graph_summary.json`, `<묶음>.acb.cue_links.json`에 각 연결과 미지원 항목이 남는다.

큐 번호와 AWB ID를 같은 숫자로 가정하면 틀린다. 실제 `V3_BGM_002`는 CueIndex47 → Waveform47 → StreamAwbId2로 연결된다. 002의 LoopStart 979,918 및 LoopEnd 3,952,821은 기존 BGM AWB의 ID2 HCA 헤더와 일치한다. 이 연결에서는 Waveform 인덱스47을 AWB ID로 사용하면 다른 소리가 된다.

추가로31,270개 waveform을 실제 내장/외부 AWB stream과 전부 대조했고, 누락·중복 선택은0이었다. 이름 큐31,272개와 waveform 개수는 서로 다른 분모다. 이 중208개는 ACB의 NumSamples와 HCA 전체 디코드 길이가 다르지만, **208개 전부 ACB 길이가 HCA의 loop end와 정확히 일치**했다. 따라서 이를 파일 손상이나 파서 오류로 분류하지 않는다. 전체 꼬리 길이와 제작자가 지정한 재생/루프 끝을 구분해야 한다. 근거 `audio_metadata/waveform_bank_validation.json`, 잔여 미설명 차이0은 `sample_length_residuals.json`에 기록했다.

## 샘플과 루프

HCA `fmt` 블록에서 샘플레이트, 블록 수, encoder delay/padding을 읽는다. 재생 샘플 수는 `blockCount×1024-delay-padding`이다. 시간은 이 샘플 수를 샘플레이트로 나눈 값이다. 루프는 HCA 안에도 있을 수 있고 ACB WaveformExtensionDataTable에도 있다. HCA loop가 없다고 전체 파일 반복으로 처리하면 안 된다.

BGM의91개 waveform 확장 레코드에는 LoopStart/LoopEnd가 있다. 기술적 예 `V3_BGM_001`은48,000Hz, LoopStart1,934,312, LoopEnd6,871,455다. 정확한 루프 시작은 약40.2981667초다. 양 끝이 포함/배제인지와 런타임 크로스페이드 여부는 소비 규약을 추가 확인한다. 표의 원문 샘플을 보존하고 mp3 길이/곡 제목 추정값으로 대체하지 않는다.

모든 외부 HCA의 현재 헤더 ciph 값은0이었다. 암호 키나 토큰을 추출/기록하지 않았다. 음향 파서가 PCM을 디코드하거나 파일 내용을 게임에 배포하는 기능은 포함하지 않는다.

## 유메노쿠니와 실제 차이

### 전환은 두 플레이어의 상태 변화다

추가 native 대조에서 BGM은 `BgmPlayer0/1` 두 객체로 구성된다(`0x1405409b0`). `0x140541210`은 현재 슬롯과 반대 슬롯에 다음 곡을 준비하고 현재 슬롯을 XOR 1로 바꾼다. 전환 인수가0이면 즉시 볼륨을 적용하고, 양수이면 전환 상태·목표 볼륨·기간·진행 카운터를 기록한다. 따라서 곡 이름을 바꾸고 하나의 재생 객체를 다시 시작하는 것만으로 이 동작을 설명할 수 없다.

`0x140540e40`의 상태1은 새 곡을 올리고, 상태2는 이전 곡을 내리는 동시에 새 곡을 올린다. 상태3은 현재 곡을 내린 뒤 정지하고, 상태4는 현재 볼륨에서 목표 볼륨으로 옮긴다. 전환은 매 호출 카운터 +1과 기간의 비율로 계산되며, pause 필드가 켜져 있으면 이 업데이트 자체가 반환한다. 기간을 곧바로 밀리초라고 부르지 않는다. 이 루틴을 호출하는 상위 `0x1405406e0`도 음성 언어 자료를 전환하는 동안 다른 상태에 있으므로, 명목60Hz만으로 모든 전환의 실제 초를 확정하지 않는다.

볼륨 변경 helper `0x140541960`은 직전 진행률과 직전 실제 볼륨으로 시작점을 역산한 뒤 새 진행률의 볼륨을 계산한다. 페이드 중 다시 목표 볼륨을 바꾸는 경우도 단순히0에서 시작하는 페이드로 대체하지 않는다. 실제 귀로 들은 크로스페이드·버스 출력 검증은 아직 하지 않았다.

같은 곡 유지도 WRD에서 구체 조건이 있다. `0x14045d7b0`은 현재 재생 상태와 이름 비교로 재시작을 생략하는 경로를 갖고, 특정 두 곡 번호5/84 사이에는 별도 분기를 둔다. 이 분기는 일반 이름 비교 생략 경로와 다르므로 모든 동일 곡 요청이 무조건 같은 처리가 된다고 일반화하지 않는다. `BgmPauseOn/Off`는 manager pause 필드와 두 플레이어의 pause 호출을 함께 다룬다. pause와 stop은 저장되는 상태와 재개 동작이 다르다.

징글 `0x1404678a0`은 WRD 볼륨÷100을 전달하되, world의 별도 값이1.0일 때만 재생 요청한다. `0x140541c00`의 플레이어 볼륨에는 manager의 징글 계열 볼륨×0.25×요청 볼륨이 쓰인다. 이 계수 하나를 전체 최종 음량이나 모든 음향의 공통 배율로 쓰지 않는다. 같은 큐가 이미 특정 재생 상태에 있으면 별도 가상 호출로 처리하고, 다른 경우 새 재생 요청을 한다. 가상 호출만으로 실제 음성 출력 결과를 확인했다고 하지 않는다.

옵션의 음량 단계0..10은 콜백에서10으로 나누어 category 값으로 전달한다. 그 뒤 플레이어별 볼륨 요청에는 BGM·징글0.25, 일반 SE 약0.41665, 음성0.6이라는 서로 다른 계수가 곱해진다. BGM은 진행 중인 페이드의 실제 볼륨, SE·음성은 각 슬롯의 요청 볼륨도 함께 곱한다. SE 옵션 콜백이 징글과 일반 SE를 함께 갱신하므로 징글 전용 옵션이 따로 있다고 추정하지 않는다. 이 값은 플레이어 API에 넣는 선형 계수이며 출력 음압·dB·ACF 버스까지 포함한 최종 음량은 아니다. 기본 옵션6도 모든 계열이 같은 최종 볼륨0.6이라는 뜻은 아니다.

## VIS — 재생 위치와 HUD의 움직임

`0x140540a40`은 현재 BGM 슬롯의 VIS 파일 객체가 준비 상태4이고 데이터 포인터가 존재할 때 선두16바이트를 `u32 format/count/loop_start/loop_length`로 읽는다. 출력8개는 먼저0으로 초기화한다. 해당 BGM 플레이어의 상태·재생 위치 질의가 유효해야 값을 채우며, 레코드 범위를 넘으면0을 유지한다. 파일 객체 준비와 음원 플레이어 상태는 다른 층이다.

설치된93개는 모두 format1이다. 선두16바이트 뒤에6바이트 레코드가 총857,879개 있고, **93개 모두 `16+count×6`이 파일 크기와 일치**한다. 각 레코드의 앞뒤3바이트를 각각 little-endian24비트로 읽어 비트18/12/6/0의6비트 값4개씩을 꺼내고63으로 나눈다. 원시 각 채널0..63 전체와 비트 위치를512가지 합성 입력으로 검사했다. format0의 native 분기는32바이트의 float8개를 읽어1/256로 곱하지만, 이 설치본에서 format0 파일을 관찰한 것은 아니다. 자체 `tools/re/vis.py`는 헤더·범위만 반환하며 원본 프레임 배열을 출력하지 않는다.93개 원본의 헤더·SHA·값 범위를 별도 검사와 대조했고, 합성 bit/float/잘린 파일 검사3개를 포함한 도구 회귀41개가 통과했다.

위치 질의 경로는 `01f0c4→0234a0→035464→0377c8`이다. `loop_length!=0`이고 위치가 `start+length` 이상이면 `(position-start)%length+start`로 감싼 뒤, `(position×60)/rate`의 정수 나눗셈으로 레코드를 고른다. 정상적인 비음수 위치에서는 내림과 같다.91개는 VIS의 start/length가 같은 이름 큐의 ACB `LoopStart/(LoopEnd−LoopStart)` 샘플 수와 정확히 일치한다. 나머지2개는 ACB loop extension이 없어 이 비교를 적용하지 않는다. 이60은 음원 위치를 사전 제작 레코드로 바꾸는 배율이며 실제 HUD의 매초 호출 수를 독립적으로 증명하지 않는다.

native 직접 호출자는 본편 HUD `34d8f0`, 별도 일상 HUD `3619b0`, 다른 world HUD `443730`이다. 세 경로는 표시값8개와 목표값8개를 구분한다. 목표가 더 크면 `min(display+0.15,1)`, 더 작으면 `max(display−display/10,0)`, 같으면 유지한다. 목표까지 선형 보간하는 공식이 아니고, 상승 시 목표를 넘을 수도 있다. `443730`은 표시값을 `130−value×130`이라는 UI Y 인자로 전달한다. 이는 최종 화면 픽셀이나 음악 판정 입력이 아니다. 따라서 팬게임에서 음악과 무관한 임의 점멸만 붙이면 이 피드백 연결을 재현하지 못한다. 자체 음원을 위한 자체 반응 자료와 상태별 표시·평활 규칙을 마련해야 한다.

## 미확정

모든 상황에 대한 BGM/효과음의 최종 명칭 대응, 각 대본 분기에서의 실제 재생 순서와 skip 정책, fade 인자 단위, 음성 종료와 자동 진행의 전체 관계, VIS8채널의 물리적 의미와 실제 화면, UI 자체가 호출하는 음향 명령, ACF의 버스·리미터·볼륨 합성은 전부 완료되지 않았다. ACB 참조가 전부 해석됐다는 사실로 이 영역을 덮지 않는다.

## 유메노쿠니에서 바꿀 것

1. `tools/import_audio.py`는 현재 제공 음원의 큐→파일 대응을 실제 ACB CueName→Waveform→AWB ID로 검증하고, 루프 샘플을 metadata로 보존한다. 원본 음원을 새로 저장소에 넣지 않는다.
2. `tools/sound_design.py`의 `score()/scene_bgm()/rappy()/body()/lines()`에서 편집 규칙과 명시적 이벤트 큐를 구분한다. 실측 전환은 WRD IP/기다림과 연결하고 정규식 결과를 덮어쓸 수 있게 한다.
3. `Game/Source/Flow.hpp`의 `music()/playCue()/updateMusic()/sfx()/eventSound()`에 필요한 volume/fade/pause/stop/pan/지속음 제어를 분리한다. 엔진 기능 범위는 HANDOFF의 제약을 따른다.
4. `Game/Source/TrialRunner.hpp`뿐 아니라 탐색·일상·수사·타이틀·갤러리의 음향도 같은 cue metadata로 검증한다. 재판 BGM만 맞춰서는 요청한 게임 전체 분석이 완성되지 않는다.

## 보행·달리기의 실제 SE 요청

탐색의 발걸음은 WRD `SE_` 명령을 매 걸음 배치하는 방식이 아니다. `409010`의 이동 위상 임계/정지 복귀→`40b000`→공통 SE 재생 `543660`으로 이어진다. 위상은 충돌 후 실제 이동 거리가 아니라 입력에서 얻은 유지 속도에 비례하고, 시점 흔들림 옵션과도 별도다. 발생 조건과 표면 분류의 비실행 제한은 [01_탐색.md](01_탐색.md)의 「이동 위상과 실제 발걸음 SE 요청」을 따른다.

`40b000`이 직접 선언한 index0..4의 큐는 `[V3_SE_064,V3_SE_065,V3_SE_066,V3_SE_067,V3_SE_067]`이다. 이름의 인상으로 발걸음을 분류한 것이 아니라 실제 이동 갱신의 호출과 callee 선언을 연결했다. 이 함수는 index의 로컬 범위 검사를 보이지 않지만, 분석한 수동 경로는 앞 절의 solver 조건으로 기본 index0을 전달한다. 다른 index가 존재한다는 것과 현재 수동 보행에서 각 표면 소리가 선택된다는 것은 별개다. 기존 `SE0_0.acb` metadata(SHA `7db8228c8f15ae1e9ed0e0fb836a578f87b6c978b5491437a4a797ac7e39ef6f`)에서 해당 네 이름의 CueIndex는63/66/69/72다. 숫자 접미사를 그대로 AWB/CueIndex로 쓰면 틀린다. 이 대조를 위해 음원을 새로 추출하거나 재생하지 않았다. 근거 `ev_2bf936afcda5a943c56ca4b2a6e76b941699c2f4d2885018ef63bd69cab18f2e`.

요청 gain은 `5d7910(0.2)+0.5`이고 그 순간 달리기 predicate `3c9260`이 참이면0.2를 더한다. unsigned PRNG의 float32 배율식이므로 대략 보행0.5..0.7, 달리기0.7..0.9이며 반올림된 위 끝점도 가능하다. 이동 쪽 강제 달리기+0x378은 cadence 배율에는 쓰이지만 이 gain 분기에서 별도로 검사하지 않는다. 공통 재생 `543660`은 SE bank/큐 이름을 해석하고 재생 슬롯을 요청한 뒤 `category(+0x16c)×0.41665×요청gain`을 플레이어에 전달한다. 유효 bank/슬롯이 없으면0을 반환하는 경로가 있고, 큐 해석이 실패하면 실제 재생 호출도 생략될 수 있다. 따라서 소리 요청을 곧바로 청취 성공으로 세지 않는다. 이 호출은 개별 걸음의 XYZ를 전달하지 않으며 최종 공간 합성·음압·dB·내부 ACB 변주까지 설명하는 증거는 아니다. 근거 `ev_7c12bffa1350a3fdbf91bb6a5c33d3a51588e5f21089bcab3139f40984a0867a`, `ev_a724f6fd3aca43aedc9853078a8d5f70cf4ea26d79de3be074f052dc425105ad`.

외부 원장은 `native/footstep_findings.json`, 재현 helper는 `native/analyze_footsteps.py`다. 이번 범위는 정적 코드·이미 해독한 cue metadata·조건부 위상 계산이며, 실제 원본 보행 청취와 막힘/정지 시 발생 시점·샘플 겹침은 관찰하지 않았다. 유메노쿠니에 옮길 때에도 제목/바닥 이름 추측 대신 이동 상태·발생 위상·정지 꼬리·요청 gain·재생 가능 여부를 분리해야 한다.

## RSC BGM 명령과 공통 음향 엔진의 연결

RSC 442대본의 BGM 354건도 별도 callback `23b5d0`과 대조했다. 로컬 bgm_label 100행·sound_param_label 35행으로 모든 gain·fade 참조와 일반 cue ID를 연결했다. 322건은 gain 1.0/fade 0의 재생 요청이고, 32건은 gain 인자 0/fade 인자 120의 BgmStop이다. 기술 라벨의 시간값 120을 이 명령만 보고 초로 환산하지 않는다.

일반 재생은 기존 공통 `5411b0→541210` 경로로 들어가며 요청한 cue ID를 로컬에 보존한다. 같은 ID면 재생 함수와 gain 저장 전에 반환하므로, 동일 곡 명령을 다시 쓴 것만으로 재시작·볼륨 갱신이 이루어진다고 해석하지 않는다. BgmChangeVolume은 별도 명령 분기로 즉시 또는 공통 state 4의 음량 전환을 요청한다. BgmPauseOn/Off는 두 플레이어의 pause에 전달하고, BgmStop은 공통 state 3 또는 즉시 정지를 요청한 뒤 로컬 ID를 -1로 비운다. 이 callback은 모두 0을 반환해 이번 update를 양보하며 fade 종료까지 기다리는 명령 자체는 아니다.

현재 출현 집합에는 ChangeVolume/Pause 제어 명령이 없으므로 코드상 기능과 실제 대본 사용을 구분한다. 공통 crossfade의 두 플레이어 상태는 앞 절 근거를 재사용했다. 팬게임의 기존 `music/playCue/updateMusic` 구현이 없다고 다시 판단하지 않으며, 최종 믹싱·실제 청취는 여전히 별도다. 원작 음원 신규 추출·재생·게임 코드 수정은 없었다.
