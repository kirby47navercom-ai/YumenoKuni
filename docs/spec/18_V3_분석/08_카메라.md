## 프리셋 표를 읽는 실제 경로

`FUN_1403f8ca0`은 재판 카메라 프리셋, 인물 위치 매핑, 인물 회전 매핑을 함께 불러온다. 각 파일은 `saiban_camera_data.dat`, `saiban_chara_pos.dat`, `saiban_chara_rot.dat`다. 카메라 표 하나만 읽어서는 화자 상대 방향과 높이 보정을 재현할 수 없다.

카메라 행은 76바이트다. 앞의 실수 16개가 `Speed`, `Frame`, 시작 7개와 끝 7개이고, 이어서 `Loop`, `Type`, `DOF`, ID·패턴 이름 관련 열이 있다. 코드의 열 번호는 파일 순서와 다르다. 네이티브 열 번호 1은 `Speed`, 2는 `Frame`, 3~9는 시작값, 10~16은 끝값, 18은 `Type`, 19는 `DOF`다. 파일의 마지막에 같은 이름의 ID 열이 하나 더 있으므로 이름만 키로 하는 사전으로 바꾸면 정보가 사라진다.

## 시간과 연결

`FUN_1403de300`은 호출 시 받은 속도 인자가 양수일 때 다음 값을 계산한다.

```text
duration = DAT.Frame / (호출 속도 × DAT.Speed)
호출 속도 ≤ 0이면 duration = 0
```

따라서 `Frame`을 곧바로 초로 읽거나 `Speed`만 이동 속도로 읽으면 안 된다. 예를 들어 `Frame=180`, `Speed=0.5`, 호출 속도 1이라면 애니메이션 길이는 내부 시간 360이다. 이 값을 6초·12초라고 부르려면 업데이트 시간 단위가 추가로 확인되어야 한다.

`FUN_1403de000`은 시작·끝 상태를 저장하고 `+0x184`의 경과값을 0으로, `+0x188`의 길이를 위 `duration`으로 설정한다. 일부 모드에서는 길이가 1 미만이면 1로 올린다. 위치·회전·FOV 등의 변화량은 `(끝-현재)/duration`으로 준비된다. 디컴파일러가 구조체 전체를 `int*`로 추정하여 실수의 이동을 `(int)`로 표시한 부분이 있다. 실제 `movss` 명령과 교차 확인했으므로 정수로 반올림하는 동작으로 구현하면 안 된다.

`FUN_1403de930`의 경과값 갱신은 다음과 같다.

```text
elapsed += float[+0x18c] × float[+0x190]
```

`FUN_1403dcd70`은 네 번째 호출 인자의 실수 비트를 `+0x18c`에 저장한다. 디컴파일러의 `param_1[99]=param_4`는 같은 저장을 정수 구조체로 표현한 것이다. 실제 저장 명령 `0x1403dce26`은 `movss`다. 생성자의 `0x1403dda09`는 `+0x190`을 1.0으로 초기화한다. 따라서 기본 설정에서는 이 인자가 길이 계산과 경과값 증가 양쪽에 관여한다. 호출 인자를 무조건 1로 고정하거나 이를 초라고 해석하지 않는다.

끝에 도달하면 다음 프리셋으로 넘기고 초과 경과값을 넘겨받는다. 프리셋 목록은 최대 10칸을 검사하며 `-1`을 종료 표식으로 사용한다. 반복 조건에서는 경과값을 길이 구간 안으로 감싼다. 단순히 매 프리셋마다 시계를 0으로 초기화하는 연결과 다르다. DAT `Loop=1`은 다음 행을 연결하고 `Loop=-1`은 반복 모드를 켜는 경로가 있다. `+0x190`의 이후 변경과 전체 업데이트 호출 간격은 후속 확인 항목이다.

근거: `ev_4923109583ed65008ea629d31f0f5ecb5d7f614f819a998c0bfe78ff4a0c466a`, `ev_c3cf7f3f25a4ff27e226a1afdccdd1033eed931895d66c98aba03ba55e37750d`, `ev_030de101481cd21b2233495a25ccae314dfba4cf490f92b3dedef8a6d9aee7fb`, `ev_db4eb6429fbecc81664d7d2a9d8678a246f6541782cebb2ffafb504194a565ff`. `+0x18c`의 실수 저장은 코드 복원본의 위 명령과 추가 교차 확인했다.

## WRD의 CAM 명령과 연결

실행 파일의 WRD `CAM` 처리기는 `0x14045e090`이다. 단일한 카메라 이동이 아니라 문자열 하위 모드에 따라 다른 경로를 선택한다. `CamSetModeCamera`는 카메라 라벨을 해석하고 재판 프리셋 제어기 `FUN_1403dcd70`을 호출한다. `CamSetModeChara`, `CamSetModeCharaPos`, `CamSetModeObj`, `CamSetModeDoor`, `CamSetModeMovePos`, `CamSetModeAutoMove`는 인물·오브젝트·문·지점·자동 이동 경로로 분기한다.

처리기는 WRD 숫자 인자를 전역 상태의 실수로 저장하고, 일부 이동 길이는 전역값으로 나눈 뒤 최소 1로 올린다. 따라서 WRD 인자 개수나 `CAM` 명령 빈도만 보고 모든 장면의 초 단위 길이를 정할 수 없다. `CamSetModePad`, `CamSetModeCharaMove`, `CamSetModeCharaStop`는 별도 게임 모드 분기에서 다른 제어기를 사용한다. 이를 일반 탐색 카메라와 같은 동작이라고 단정하지 않는다.

근거: `ev_e690fca4aa44a3ad96bb345b9ce55bf8a23807fb6f12523197e3cc5bd7f74b06`. 실제 opcode→함수 대응은 저장소 밖 `native/wrd_dispatch.json`과 교차 확인했다.

## 각도와 화자 상대 회전

재판 프리셋의 회전은 화자 상대일 수 있다. `Type=0` 경로는 화자 인덱스가 주어지면 `FUN_1403dd880`에서 계산한 방향을 시작·끝 `ROT`에 더한다. 화자가 지정되지 않으면 현재 회전을 기준으로 프리셋의 시작과 끝 차이를 유지한다.

`FUN_1403dd880`은 재판 인물 위치 자료 또는 인물 모델의 X/Z 위치에서 방향을 계산하고 `180-angle`을 0~360 범위로 감싼다. 시작·끝 프리셋 자체를 읽는 것만으로 재판장 전체의 절대 카메라 방향을 정할 수 없다.

일반 `CameraTask::update`에 해당하는 `FUN_14037d760`은 기본 Euler 값과 추가 Euler 값을 더하고 `π/180`을 곱한다. 따라서 이 최종 작업 객체의 각도 단위는 도다. 이 함수는 위치에서 100단위 앞의 방향점을 만들어 시선 벡터를 구성한다. 이 100은 시선 방향점을 만들기 위한 길이이며 증언대 반지름이나 물리 단위가 아니다.

근거: `ev_4923109583ed65008ea629d31f0f5ecb5d7f614f819a998c0bfe78ff4a0c466a`, `ev_99b9d58ed2a534ca767decda1d69d176d23c271f4bd0b0dca2d915e45b92a06b`, `ev_18387806486d4bcde06684387d36961211e2103e11e223533800b8a0d34eb238`.

## 높이·거리·FOV를 그대로 복사하면 안 되는 이유

시작과 끝은 각각 같은 보정 함수를 거친다. 아래 식은 함수 인수 구조체의 오프셋과 DAT 열의 연결을 코드에서 확인한 것이다.

| 값 | `Type=0`, `FUN_1403dd0f0` | `Type=1`, `FUN_1403dd2a0` |
|---|---|---|
| FOVY | `FOVY × 1.2` | `FOVY × 1.2` |
| HEIGHT | `HEIGHT × 0.01 × (인물 모델 +0x204 / 0.14)` 및 회전 보정 | `HEIGHT × 0.01 - 0.12`를 인물 높이·Y 위치에 더함 |
| LEN | `5 - LEN × 0.1` | `LEN × 0.1` |
| UP | 아래 각도 보정과 함께 사용 | 부호를 뒤집음 |

`Type=0`에서는 특정 화자 슬롯 16 및 17~21에 대해 추가 높이·거리 오프셋도 더한다. `ROT_Z`가 0이 아니면 삼각함수와 인물 높이를 사용해 높이를 더 보정한다. `Type=1`은 인물 모델의 위치·회전과 보정한 거리로 명시적인 위치/주시점 좌표를 만든다.

예를 들어 표의 `ST_FOVY=20`은 이 단계에서 24가 된다. 이후 `FUN_1403df640`이 최종 카메라 상태 설정기 `FUN_14037bd70`으로 넘길 때 다시 1.5를 곱하므로 설정값은 36이다. 즉 두 보정을 모두 거치는 경로의 총배율은 1.8이다. 표의 `ST_LEN=30`은 Type=0에서 2, Type=1에서 3이 된다. 표의 수치를 그대로 HBEngine FOV나 카메라 거리로 대입하면 원작과 달라진다. 아래 최종 투영 경로에서 이 36은 **가로 전체 시야각 36도**로 쓰이는 것을 확인했다. 원본 열 이름 `FOVY`는 자료의 이름으로 보존하되 세로 FOV라고 해석하지 않는다. 물리적 미터 단위는 별도로 미확정이다.

`FUN_1403df640`은 Type=0에서 회전과 거리를 이용한 원형 위치를 만들고 필요하면 화자 위치를 더한다. Type=1은 시작/끝 보간 결과의 명시적 위치·주시점에서 방향을 다시 구한다. 추가 위치 편차, 흔들림, 화자 옆으로 비키는 `POS × 0.01` 보정도 존재한다. 거리·높이 두 값만으로 같은 화면이 나오는 구조가 아니다.

`FUN_14037bd70`은 전달된 FOV 실수를 목표 상태 `+0x130`에 기록하고, 전달된 전환 길이가 0이면 현재 상태 `+0x50`에도 즉시 기록한다. 위 최종 배율은 이름만 보고 추정한 값이 아니라 이 설정기 호출 인자까지 확인한 값이다. 이 상태값이 실제 투영 행렬로 이어지는 경로는 다음 절에서 확인했다.

## 상태 전달과 실제 view 행렬

`379ec0`은 현재 상태를 0xa0바이트 메시지로 만들고 `495170`을 통해 작업 큐에 보낸다. 수신기 `37bb50`은 원시 명령 209바이트 전체에서 위치·회전·FOV·near/far를 `CameraTask`로 복사한다. 상태 객체의 FOV `+0x50`은 메시지 `+0x30`을 거쳐 작업 객체 `+0x70`에 도착한다. 상태 near/far `+0x14/+0x18`은 작업 객체 `+0x74/+0x78`이 된다. **두 객체의 오프셋을 섞으면 안 된다.** 작업 객체 `+0x50`은 위치 X다. 이 수신기는 REA에 함수가 등록되지 않아 복원본의 원시 명령으로 보완했다.

`37d760`은 작업 객체 안의 `SpCameraLookAt`을 갱신하고 `572170 → 5d7cc0`이 view 행렬을 만든다. 최종 Euler의 pitch/yaw를 라디안으로 변환한 뒤 기본 시선 방향은 다음 식이다.

```text
direction = 100 × (cos(pitch) sin(yaw), -sin(pitch), cos(pitch) cos(yaw))
viewZ = normalize(target - eye)
viewX = normalize(up × viewZ)
viewY = viewZ × viewX
```

따라서 이 기본 시선에서 world yaw 0도는 +Z, 180도는 −Z다. view 공간은 앞쪽이 +Z인 왼손 규약이다. roll·추가 위치/회전·흔들림은 별도 보정이다. `572170`은 view를 만들고 `0e5170`은 이를 렌더 상태로 복사한다. 이 함수들이 원근 투영까지 만드는 것은 아니다.

## 실제 원근 투영 — 가로 전체 FOV

`37d760 → 49a190`은 FOV·near·far를 렌더 컨텍스트에 기록하고 다시 읽어 `0e4a00`에 넘긴다. `0e4a00` 자체는 수치와 변경 표시만 저장한다. 실제 소비는 `549e60 → 5d8040`이다. 이 경로에서 두 추가 스케일 인자는 모두 1.0이다. `5d8040`의 삼각함수는 `6af830`이며, 작은 입력의 `x+x³/3`, π/2 범위 축소와 홀수 사분면의 `−1/t` 분기까지 대조해 tangent임을 확인했다.

```text
Fh = 전달된 FOV (도 단위 전체각)
C = tan(π/2 - Fh × π/180 × 0.5) = cot(Fh × π/360)
r = 세로 종횡비 인자
K = far / (far - near)

P = [ C   0     0        0 ]
    [ 0   C/r   0        0 ]
    [ 0   0     K        1 ]
    [ 0   0    -near×K   0 ]
```

위 배열은 메모리의 행 순서이며 행 벡터를 곱하는 표기다. `clipW=viewZ`, near는 깊이 0, far는 깊이 1로 간다. FOV는 전체각이고 함수 내부에서만 반으로 나눈다. 가로 계수는 C, 세로 계수는 C/r이므로 이 카메라 경로에서 **Fh는 가로 전체 FOV**다. `FOVY`라는 표 이름으로 세로각이라고 추정하는 것은 반증됐다.

종횡비는 `0e4b00 → 0e5de0`이 타깃에서 가져온다. `547cc0`의 가로 인자는 항상 1.0이다. `547cd0`의 세로 인자는 타깃 `+0x88`의 bit 0이 꺼져 있으면 실제 픽셀 `height/width`다. 켜져 있으면 표시 모드 1은 0.75, 모드 2는 0.5625, 그 밖은 디스플레이 타깃의 `height/width`를 사용한다. 이는 정적 분기이며 모든 장면에서 어떤 모드가 선택되는지 실측한 것은 아니다.

세로 전체 FOV를 받는 엔진에는 다음 변환이 필요하다.

```text
Fv = 2 × atan(tan(Fh/2) × r)  # 삼각함수에는 라디안 사용
```

## 1920×1080 합성과 실제 해상도

`37d360`의 카메라 합성 사각형은 1920×1080 기준이며 중심은 960,540이다. `0f1e00`은 기준 크기와 반크기를 저장하고 `0f1a80`은 `[1920,1080,1/1920,1/1080]`을 셰이더 uniform으로 등록한다. 이 두 함수는 원근 투영 생성기가 아니다.

원시 helper `546910`은 좌상단 기준 입력을 `(x/960−1, 1−y/540)`으로 바꾼다. 중심 기준 합성 좌표로는 `NDC=(x/960,−y/540)`이고 텍스처 좌표는 `((x+960)/1920,(y+540)/1080)`이다. 유메노쿠니의 1280×720으로 옮길 때 정적 화면 좌표 배율은 2/3이다. 같은 16:9 타깃이면 위 투영 종횡비는 같지만, 기준 합성 좌표와 실제 타깃 픽셀 크기는 별개다. 이 경로가 모든 UI 위젯의 배치나 모든 셰이더 패스를 증명하는 것은 아니다.

## 재현에 아직 필요한 근거
