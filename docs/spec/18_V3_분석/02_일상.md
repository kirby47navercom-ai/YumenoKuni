# 02 — 일상·대화·자유행동

## 확인 범위

### 기본 대화 입력의 추가 연결

실행 관찰은 현재 도입 대화·CG·일반 공간 배경/대화창·인물 패널의 일부 전환까지 진행했다(14). 아래 모든 장/인물/특수 라벨의 실행 검증을 마쳤다는 뜻은 아니다.

기본 바인딩에서 Auto는 E/Space의 새 누름, 이력은 F2의 새 누름, 빠른 재생은 왼쪽 Ctrl/Esc/X의 누르고 있는 상태다. 현재 실행의 키 설정을 직접 읽은 결과는 아니다. `3c8550→357880→47ab50`은 Auto를 working+6c0 bit0으로 토글한다. message_skip 키 또는 패드 확인 버튼을 누르고 있으면 거부하며, world+b574/ab50/ab60과 대화 자원·상태 조건도 통과해야 한다. 이 함수에는 마우스 Auto 경로가 없다. keyboard Z를 직접 거부한다고 일반화하지 않는다.

이력은 `3c6e40→478c90→366fa0`과 별도 허용 조건을 거친다. 빠른 재생의 `47d880`은 매 update 기본 속도1을 설정하고 허용된 held 입력이면6으로 올린다. ab6c 또는 working+6d0 bit0x20000000은 이를 막는다. 대사를 무조건 끝내거나 영상 전체를 건너뛰는 명령이 아니며 영상 건너뛰기 F3/Start는 별도 소비자다. Auto와 빠른 재생을 동일한 지속 bool로 구현하면 입력을 놓았을 때의 동작과 대기 조건이 달라진다.

외부 `native/dialog_input_findings.json`·`dialog_input_disassembly.json`·`dialog_input_validation.json`에4개 EV와 원시 범위,8개 검증을 남겼다. 근거: `ev_5014a801a6adbc01f002d614654596834bf69b434d5e71b472bdc0d042c3fe02`, `ev_1e2569f99e90edbee790599afc84e8e6de22010a350f79d0c1963cc3cd1d09ea`, `ev_362f2edd0ebd9416fb57bc47e1cbc7d0246cbd0ffca97a2963990c7cd65cf7ff`, `ev_9b95fccd14abba64df880179942252b137d71b7feee7c7ee9e035e852bc386b0`. 실제 Auto·이력·held 빠른 재생의 수신 성공은 아직 확인하지 못했다.

분석은 실제 설치 파일과 복원한 코드의 정적 REA 근거다. 원작 대사는 저장소에 복사하지 않았다. 모든 장의 일상을 직접 플레이한 기록은 아니다. 대화 화면의 실제 배치/애니메이션 수치는 `06_UI.md`, 공간의 인물 위치는 `01_탐색.md`에 이어진다. 이하 외부 근거 경로의 루트는 `C:/Users/kirby/Downloads/v3_re/`다.

## 대사·화자·넘김은 분리되어 있다

WRD dispatcher `0x14045b310`에서 CHN→`0x14045fc40`, LOC→`0x14046b8e0`, BTN→`0x14045dde0`가 각각 다른 처리기다.

CHN은 라벨표3의 화자 식별자를 해석해 상태+0x184e에 저장하고,1000 미만이면 별도 표시 화자+0x1850도 갱신한다. 일부 모드에서는1000대 sentinel을 별도로 처리한다. 화자 하나를 단순 문자열 이름으로만 표현하면 이 구분을 놓친다.

LOC는 문자열 ID를 기록하고 전처리/참조 해석을 거쳐 STX 문자열을 가져온다. 현재 장면 enum에 따라 일반 대화 wrapper(`0x14035efa0`)와 재판 대화 wrapper(`0x14042f3d0`) 등 서로 다른 출력 경로를 선택한다. UI가 준비되지 않은 분기에서는 명령 위치를 되돌리고 반환0으로 기다린다. 표시 후에는 별도 backlog 함수도 호출한다. 근거 `ev_cf0db6beb5caf42dd8c531a7c18c54a0692897e56843317069d5f580fbb0f370`.

BTN은 대화 UI에 진행 대기 상태를 전달하고 저장된 음성 이름 영역을 초기화한다. 반환0으로 실행을 멈추며 뒤따르는 명령 위치를 다른 대기 처리기에 전달한다. 근거 `ev_e071ff7995a47f2e45be45b329f8270ea3b5169347356a8a1075cd32a47432d5`.

LOC 처리에는 텍스트 속도 관련 필드가0이 아닐 때 `(값×0.2)/100`을 전달하는 분기가 있다. 이 값을 곧바로 '초당 글자 수'로 부를 수는 없다. 실제 글자 누적/타이머 소비 함수를 확인해야 한다. 일반 대화의 최종 setter `0x140358660`은 텍스트 포인터+0x930, 추가 파라미터+0x940를 기록하고 `0x1403594f0`으로 넘긴다. 근거 `ev_188e95e98e5f41347c9915c74f1c7061d9fbf7c9af7ce162fcc13f5d00f1119e`.

### 실제 글자 누적·자동 진행

후속 native `0x1403594f0`과 별도 일상 모드의 `0x140365420`에서 소비식을 확인했다. 속도 단계의 배율 배열은 `[0.3,0.3,0.4,0.5,0.6,0.8,1,2,4,8,20]`이고, 언어 enum2/3 경로는 여기에2를 더 곱한다. 호출 입력×배율을 누산기에 더하고1 이상인 동안1씩 빼며 UTF-16 단위를 진행한다.0종료를 만나면 출력 완료 상태를 켠다. `<...>` 제어 태그는 별도로 건너뛰고 색상 태그에는 누산 예산을 보정하는 분기가 있다. 근거 `ev_25bda95e42af5c626bdb509e0c7cccc7229fd7c483c11f86b0ba4e1587f2b96d`, `ev_d36d0049529a18b98cfb7bf352daf4d662b95ff7ab1b835222b1a7a05b2847bc`.

일반 대화 업데이트 `0x140357880`은 출력 중 누적 입력이12 이상이거나 특정 입력이면1024.0을 전달해 빠르게 글자를 표시하고, 평상시에는 저장한 글자 속도값을 전달한다. 출력이 끝나고 BTN 대기가 활성화된 뒤에야 다음 진행 상태로 넘어간다. 자동 모드에는 별도 타이머, 음향 상태 조회, 확인 효과음 `V3_SE_003`, `fl_auto_in/out`, `fl_ok` 완료 대기가 있다. 자동 진행 임계 카운트는 언어 경로별로 표시 문자 수×2+120 또는×4+120이다. 실제 초 변환은 전체 tick 주기 검증 전까지 보류한다. 근거 `ev_5014a801a6adbc01f002d614654596834bf69b434d5e71b472bdc0d042c3fe02`.

별도 일상 업데이트 `0x1403639f0`도 같은 누적 표시 구조를 가지지만 일부 입력 타이머 조건이30과60으로 다르다. 모든 대화 모드를 하나의 임의 속도로 합치면 이 차이를 잃는다. 근거 `ev_e8c4c85c05feb4ee392e8e941670a35249c7cc3f0714dc533029c6dc28973729`.

### 자동 진행과 음성의 대기 예산

추가 대조로 위의 음향 조회는 `0x140544970`이며, `0x1405441a0`이 만드는 VoicePlayer0..7 중 하나라도 내부 상태3 또는5이면1을 반환한다. 따라서 현재 대사의 음원 파일 길이만 조회하는 함수가 아니다. 일반 대화의 BTN 대기 상태3에서 자동 진행이 켜져 있으면, 조회 결과0일 때 elapsed(+0x94c)를1 올리고, 결과1일 때에는 threshold(+0x970)를1 내리되 최소60을 유지한다. 초기 threshold는 앞 절의 문자 수×언어 배율+120이다. 별도 일상 모드도 대응 필드(+0x9dc/+0x9fc)에 같은 정책을 적용한다.

입력·중단·다른 진행 차단이 없고, 대기 진입 직후부터 음성 조회가 V회 연속1인 뒤 계속0인 단순 조건을 놓으면, 전체 대기 호출 수는 `V + max(60, 초기예산−V)`다. 즉 음성 재생이 끝난 뒤 문자 수 예산 전체를 다시 기다리는 방식이 아니다. 예산120에서 V=30이면 총120, V=150이면 총210회라는 조건부 계산을 얻는다. 이는 native 상태식에서 계산한 예제이며 실제 대사의 초 단위 청취 결과가 아니다. pause 상태·여러 음성 슬롯·자동 모드의 중간 전환·메뉴 차단이 있으면 이 단순 예제를 그대로 적용하지 않는다.

자동 대기 조건을 충족하거나 수동 진행이 들어오면 상태4로 가고, 일반 경로는 `fl_ok`의 완료를 기다린 뒤 다음 출력 상태2로 돌아간다. 그때 `0x140545040`을 호출한다. 이 함수는8개 음성 플레이어 중 상태0/5를 제외한 객체에 정지를 요청하므로, 모든 상태에 무조건 같은 정지를 건다고 축약하지 않는다. 수동 입력은 음성 조회가0이 될 때까지 강제로 기다리는 조건과도 다르다. 실제 UI 전환·소리의 겹침은 아직 실행 대조가 남는다.

## 입상과 대화 레이아웃

CHR은 공간 인물 리소스/동작, POS는 위치 제어, CAM은 카메라, KNM은 카메라·대상·포즈·표시 전환 요청, KWM은 복수 입상의 구성 전환, LOC는 텍스트라는 별도 계층이다. '대사마다 포즈를 교체한다'는 생성 규칙 하나로 원작 연출을 대체할 수 없다.

KWM `0x14046b350`은3개 구성 슬롯을 순회한다. 현재 슬롯 이름이 요청한 구성과 같으면 갱신을 건너뛰고, 다르면 `fl_%s_%s_move` 라벨을 구성해 해당 슬롯의 UI 전환을 요청한 뒤 새 이름을 보존한다. 근거 `ev_e09531127d190212ed81ed7374c398a2ff8f89dbf77e8a4c910ca32c54f01ab7`. 공개 설명의 포괄적인 'UI mode 설정'만으로는 이동 연출을 재현할 수 없다.

일반 대화·주인공 대화·이벤트 대화는 같은 위치의 이미지 교체가 아니라 서로 다른 이름판/바탕/글자 계층과 진입·대기·교체·퇴장 타임라인을 가진다. 로컬 행렬의 사례는06 문서에 실제 파일·라벨·프레임 레코드 번호와 함께 기록했다. 최종 viewport 좌표와 fps는 별도 확인 대상이다.

### 공간 인물 — 요청·모델 준비·표시·퇴장을 나눈다

CHR `0x14045fd60`의 `3d` 경로는32개 스크립트 인물 슬롯을 사용한다. 저장 상태의 인물ID(+0x5e60), 요청/현재 포즈(+0x5ee0/+0x5ee4), place(+0x6060), 표시 요청(+0x6160), 선택 가능 요청(+0x61e0)과 별도 실행 상태의 phase/리소스 핸들이 있다. `pw`는 별도 ProgWorld 경로다. `2d`라는 문자열 분기는 성공을 반환하지만, 이를 본편 입상 구현이라고 간주하지 않는다.

실제 소비 `0x14047c740`은 phase2에서 `0x140384840(actor,pose)`로 준비를 요청하고 phase3에서 준비 상태를 기다린다. phase4에서는 `0x14037f670(place)`를 적용한 후 현재 핸들을 바꾼다. phase7의 새 포즈는 `0x14037ffc0` 요청과 phase8로 이어지며, 요청 포즈가 이미 현재 포즈와 같으면 교체를 생략한다. `swCharaOff`는 표시 요청0, `swCharaStartFadeOut`은 비동기 fade와 pending 상태, `swCharaStartDelete`는 리소스 유지 요청 해제다. 이 세 가지를 '입상 숨김' 하나로 합치지 않는다. 근거 `ev_a0f2fa5827ca7c496cf7f57e899214f9bf919bb038fc91534abeb0823289b112`.

위치·크기도 화면 위 단일 고정 사각형이 아니다. `0x14037f670`은 변환된 place 레코드의 위치·회전·크기·색/부가 필드를 인물 상태에 복사한다. `0x1403807a0`은 두 렌더 part를 순회해 위치/회전의 기본값+오프셋, 크기 곱, RGB 곱, 기본 alpha×fade alpha를0x90바이트 packet에 구성한다. 변경된 packet은 `0x140495170`→`0x140381870`으로 task에 전달되고, `0x1403854c0`은 로드 완료·표시 요청·alpha·각 축 크기를 검사해 entity 가시 비트를 갱신하며 위치/회전/크기를 전달한다. 회전은 이 단계에서 도→라디안으로 변환된다. place 원문 DAT의 수치와 이 변환 후 구조를 동일시하지 않으며, 최종 shader/pixel 외형 복원으로 확대하지 않는다. 근거 `ev_f8d5f1ce3e6a45387b71fd0cd65e0d3240398c0c98f723e61734acef49766f40`, `ev_b2422d9ad2a55126fd792719751f838fa84aa439a9ad75b7e7fd1239360aaf6d`, `ev_3c33c876c7fee51a9c9ac15304589cade46c52615417ac7b2d500f819d52959c`, `ev_3524f0f02d83f90a1839a3a6aabd3bd8174246dcc39768bcc2031e6e8845878e`.

### fade의 시작과 완료는 다르다

`0x14037fbf0`은 진행 중인 fade(+0x270)가0일 때만 새 모드·rate·초기 alpha를 기록한다. 실제 갱신 `0x140380340`의 허용 분기에서 mode1은 `0x140382b50`, mode2/3은 `0x140382bc0`으로 간다. 이들은 `progress=min(60,progress+rate)`를 누적하고, 등장 alpha는 비음수 progress/60, 퇴장 alpha는1−비음수 progress/60으로 만든다. 끝점에서 +0x270을0으로 지운다. CHR 호출 지점 `0x1404615e6/0x14046171d`의 원시 명령은 XMM2에 rate, XMM3에0을 전달한다. 일부 의사코드가 float 인자를 생략하므로 두 인자 함수라고 읽으면 안 된다. 이 경로의 rate는 디코드한 speed가0이면60, 아니면60/speed다. **실제 허용된 update 횟수의 식**이며 pause·모드·프레임 정체와 무관한 실시간 초라고 확정하지 않는다. 근거 `ev_02619c81def81d8eb3e6ae3435fb6e3e9186794d3a533826679d9237774e53f7`, `ev_6504ba862372cbdc034df17f8eeee70b874b9bce78f3e470e94639ddc419d67c`, `ev_3ea9be5cecee11781073f07ccb64e70d83dc3193c7abe4a31a3a60ed8bd7c008`; ABI 원장은 `native/standing_findings.json`의 `fade_call_raw`.

`0x14037f130`은 +0x270==0을 검사한다. CHR의 `0x140477120`은 이 값을 사용하지만 미등록/없는 인물에서도 성공하는 예외가 있으므로 '모든 리소스 로드 완료' 함수라고 부르지 않는다. 전체 manager의 `0x140384170`은40개 manager actor 항목의 fade와 별도 준비 필드(`37f1d0/37f150`), 외부 준비 상태까지 확인한다.32개 스크립트 슬롯과40개 manager 항목은 같은 분모가 아니다. CHR 반환1, fade 종료, 모델 준비 완료는 서로 다른 사건이다. 근거 `ev_db159868e3915de0faf44919f9cb5b27450824a25c187a7cfd531fb84b1e733a`, `ev_0d454c74763d92bb72ce9b09c51dca4d2fce895d5643fdda2179ae72ca9bfeac`.

### KNM — 카메라/대상 요청과 세 표시 슬롯

본편 대화의 분할 구성은 CHR의 포즈 변경만으로 설명되지 않는다. KNM `0x140467cc0`은 camera slot0..2, point, 인물/대상, pose/카메라 종류, `fl_*` 전환 라벨을 별도로 해석한다. 인물 프레이밍 `0x140406bd0`, 물체(`CamSetModeObj`) `0x140407230`, 문(`CamSetModeDoor`) `0x1404067e0`, 이동 위치 `0x140407a80` 등의 카메라 경로와 대화 UI 요청을 함께 건다. 준비 함수 `0x140476f40`이 실패하면 현재 명령 위치를 되돌려 반환0으로 재시도한다. 이 준비 검사는32개 스크립트 슬롯 중 활성 인물과 특정 animation type의 `37f000` 상태를 보며, 모든 조건을 무조건 기다리는 단일 전역 완료 flag가 아니다. 근거 `ev_8fedbffa23435b3542a8797ca7e7b51dfc2f986b5b1a6ab99d416a649649d933`, `ev_fc66b67064e40925df6f130b8b37fc711389c28845b1994a500882742dc9201d`.

UI 전달은 wrapper에서 끝나지 않는다. `35ed30→352ee0→354e60`은 슬롯별 대상 ID(+0x8cc)를 유지하고 새 대상/교체 때 전환 파라미터를 절반으로 나눠 최소1로 기록한다. `35ec00→352e00→354c70`은 별도 pending counter를 요청한다. `35ec40→352e20→354810`은 선택한 슬롯의 재생을 활성화하고 라벨을 보존한 뒤 일반 경로에서 `4ab510`의 speed1 또는16, `4aa820(label,1)`로 SFL 재생을 요청한다. `fl_fadeout`과 `fl_fadeoutModeEnd`는 일반 재생과 다른 상태10/11이다. KNM `fl_fadeout` 자체도 스크립트 대기+0x16aa에0xb를 기록하고 반환0을 한다. **해당 전용 대기의 최종 해제 소비와 pending counter의 전체 상태 전이는 이번 범위에서 미확정**이다. CHR fade 종료만으로 KNM의 모든 분할 전환이 끝났다고 계산하지 않는다. 근거 `ev_584c33bda07846f4229f317a74a166259e1c1242ab3a67c10407e2cdf0026dca`, `ev_d2e337cebae185ae10368ce423d8df232d7a8099bae3b48126c62fe1a4141a18`, `ev_4d77b5a966e15f71fc7870685ec609f23832c4c13973538db3fe093b4cea1a9b`.

### 후속 확인 — 지연 만료·슬롯 준비·다음 대사 허용

앞선 미확정의 첫 경계는 `0x140478c90`에서 닫혔다. +0x16aa는 **상태 enum이 아니라 지연 카운트**다. 활성 script가 있고 실행 차단+0xab50이0인 해당 분기에서, 별도 카운트+0x16ac가0이고 +0x16aa가 양수면1을 빼고 그 갱신에서는 dispatcher를 호출하지 않는다.11→0에는11회의 허용된 감소가 필요하고, 다음 허용 갱신에서야 dispatcher 후보가 된다. +0x16ac가 활성인 다른 분기에서도 +0x16aa는 양수일 때 함께 감소한다. 메뉴/모드의 조기 반환 등이 있으므로 실제 초나 전체 게임의 무조건11프레임이라고 환산하지 않는다. **KNM의 `0xb`와 UI 객체의 상태11은 다른 구조의 다른 값**이다. 근거 `ev_1e2569f99e90edbee790599afc84e8e6de22010a350f79d0c1963cc3cd1d09ea`.

카운트가0이어도 다음 대사는 즉시 허용되지 않는다. 같은 dispatcher 경로에는 UI busy인 저장 상태+0x6b0==0을 비롯한 모드/카메라/다른 UI gate가 있다. 실제 KNM UI 갱신 `0x1403550b0`은 슬롯 fade 상태10/11에서 `alpha -= manager[+0xb898]×0.1`을 계산한다. alpha<=0이면 `fl_stop`을 재생하고 저장 alpha를1로 되돌리며 슬롯 상태7로 바꾼다. 상태10은 이때 +0x6b0도 지우지만 상태11은 해당 로컬 끝점에서 지우지 않는다. 별도의 global 상태11은 필요한 SFL 재생 완료 검사(`4aa8c0`)를 충족하거나 수치 조건 `manager[+0xb898]>=6`이면 +0x6b0을 지우고 global 상태10으로 간다. 이 검사에는 원래 main-slot 상태에 따른 우회 조건이 있어 임의의 '세 슬롯 모두 끝남' 검사로 바꾸지 않는다. 수치 조건을 특정 물리 취소 버튼이라고 부르지 않으며, alpha의 끝점과 라벨 재생 완료도 동일시하지 않는다. 근거 `ev_9b674e0511f0f835529b750cd55f064added13901014df020766a3c15f8b6c45`, `ev_ca9dd7ea1be743e14ee699ac6715f2312ba67fffbad0710011347c2da07be928`.

두 번째 경계인 `354c70`의 실제 필드 소비는 `0x1403563b0`이다. 슬롯별 +0x89c는 요청 phase, +0x8a8은 요청/경과값, +0x8b4는 지연값이다. +0x8c0의 guard가0이고 enable이0이 아니면 setter는 지연을 기존/요청 값의 최댓값으로 두고, 그 밖에는0으로 만든다. 어느 경우든 요청/경과값은0으로 리셋한다. 공통 갱신에서 지연이0에 도달하면 요청/경과값을1로 켜고, 이후 이 값이 증가해16 이상이며 `384040`의 actor fade-idle 검사까지 통과해야 `493c60(slot)`→phase1이 된다. phase1은 `498270(slot)` 준비를 기다려 `493b20(slot)`→phase2로 간다. phase1/2에서 요청/경과값이0이면 `493b50(slot)`과 phase0으로 해제한다. 따라서 새 요청은 기존 단계를 해제한 뒤 지연·준비 조건을 거쳐 다시 시작할 수 있고, disable/guard 분기는 지연도0으로 지워 이 타이머로 재시작하지 않는다. +0x8a8을 단순 '완료 flag', +0x8b4를 단순 화면 이동 시간으로 부르지 않는다. 요청/준비/활성/해제 호출 규약을 닫은 범위이며 `493*/498*`의 render-target/GPU 합성 내부 전체를 재분석한 것은 아니다. 근거 `ev_677527a031dd49bd11283af396c4a0bf73db3a5ffbe566b10212c1d3fc78f8fd`.

대상 선택도 alpha와 별도다. 같은 소비자는 +0x7a0 지연이 끝나면 대상ID와32개 runtime actor를 대조해 `37f460(actor,값,slot)`을 호출한다. 이 함수는 actor+0x268의 `1<<slot` 비트를 켜거나 지우며 slot−1은0..2에 적용한다. 대상−1은 해당 슬롯 비트를 전체 인물에서 지우고, 지정 대상이면 그 인물을 켜고 다른 인물은 지운다. 특정 인물 분류21..25를 유지하는 예외도 보존한다. 이3슬롯 소속 mask는 global 가시성이나 fade alpha가 아니며, 앞의 렌더 packet에도 별도 필드로 전달된다. 근거 `ev_775d4376ec4b19de53f4851248ab65f6acbe3b80ea6cb10bc999f84a65d6ddc5`.

후속 원장은 외부 `native/standing_wait_findings.json`, 재현 helper는 `native/close_standing_wait.py`다. 기존 전체 명령 census를 다시 세지 않고7개 선택 EV와 원시 필드 참조를 대조했다. 해제 조건을 알았다는 것이 모든 특수 KNM 라벨·실제 화면·물리 취소 입력·모든 모드의 동일 동작까지 확인했다는 뜻은 아니다.

### 실제 명령열과 확인 분모

실효 base007에 US007을 우선한2,716개 기술 원장을 다시 세었다. CHR36,734개 중 `3d`33,228개, `pw`3,506개, `2d`0개다. KNM36,738개와 KWM2,240개는 별도 명령이다. **일상만의 실행 횟수가 아니라 여러 모드·테스트·보너스 문맥을 포함한 정적 literal 명령 수**다.3d의 load8,795개, pose change10,218개, fade-in22개, fade-out509개도 같은 한계를 가진다. 경로·SHA·명령 offset/기술 인자는 외부 `native/standing_commands.jsonl`, 재현은 `native/analyze_standing.py`, 수치/EV/미확정은 `native/standing_findings.json`에 있다.

대표 `chap1/c01_023_010`의 실효 US007 원문 WRD를 다시 해독한 기술 ID 열도 보존했다. offset66/78/90의 세 CHR load→102의 PosSetAll은 대사 이전 준비다. 별도 구간1776의 공간 pose change 뒤1858/1876의 두 KNM 요청→1888 KWM→1892 CHN→1896 LOC ID44→1900 BTN이 있다. 퇴장 구간2264 StartAnim→2276 명시적 WAIT20→2284 StartFadeOut→2296 WAIT60→2322 LOC ID56→2326 BTN 역시 전환 요청과 대사 진행이 분리됨을 보여 준다. 대사는 복사하지 않았다. 파일 전체의 분기를 실제로 모두 실행했다는 뜻은 아니다. 탐색 복귀도 fade의 자동 효과가 아니라 명시적 MOD/후속 script 경로와 별도로 대조해야 한다. 정적 사례의 명령 순서와 원래 runtime의 최종 대화 화면을 구분한다.

유메노쿠니의 현재 `Flow.hpp:204` 이후는 매 say마다 speaker/portrait를 비우고 감정 또는 명시 pose로 단일 webp를 고른다. `showLine()`은 한 Portrait의 가시성과 texture를 즉시 바꾸고, `sayOnce()`도 같은 경로다. `create-project.mjs:116`의 Portrait는 `[290,0,700,700]`인 단일 Image다. 따라서 다음 구현은 화자와 지속 인물 상태, 리소스/pose 준비, 공간 transform, 세 대화 구성 슬롯, 등장/교체/퇴장 및 완료 대기를 구분해야 한다. 원작 코드/그림을 편입하거나 새 renderer를 추가했다는 보고가 아니라, 현재 구조와 검증된 동작 사이의 구현 차이 기록이다. 본편 대화의 직접 화면 관찰, 모든 특수 KNM 라벨, 인물별 높이/billboard 예외와 최종 GPU 표현은 남아 있다.

## 자유행동·선물·상점의 실제 모드

`mode_label.dat`의 MODE5는 modPresent,6은 modMonomonoMachine,7은 modPrizeExchange,8은 modVendingMachine이다. `MOD` 처리기 `0x14046cd40`은 이 값을 분기해 서로 다른 상태 객체를 활성화한다. 선물은 `0x1404109c0`으로 상태/인자를 전달하고, 머신·상점은 장면별로 `0x140458f00` 또는 `0x14045a5b0`을 호출한다. 이 함수들은 요청을 기록하는 setter이며 실제 추첨/소모/반응 계산 함수까지 확인한 증거와 구분한다.

## 방송·동기 영상·사건 연출

MOV는 동영상 재생, FLS는 UI/Flash 계열 리소스·라벨 재생, BGM/SE_/JIN/VOI는 별도의 음향 명령이다. 사건 발견의 충격·암전·방송도 이런 명령열로 조합되므로, 제목이나 대사의 정규식만으로 효과를 배정한 규칙과 실제 시점을 구분한다.

## 일반 대화의 출력·이름판·넘김을 하나의 정상 경로로 연결하기

일반 대화의 화면은 한 장의 이미지와 문자열을 동시에 바꾸는 구조가 아니에요. LOC의 일반 wrapper `35efa0→358660`은 `359480`으로 이전 문자열·출력 위치·완료·BTN 대기를 초기화하고 CLT 기본 태그를 만든 뒤 새 문자열과 속도를 보존해요. CHN 화자, 이름판 리소스, CHR/KNM 인물·구성 요청은 각각 별도 상태예요. 일반 업데이트 `357880`은 먼저 저장된 창 모드 변화와 이름 리소스 상태를 처리한 뒤 글자와 넘김 상태를 갱신해요.

이름 리소스 준비 `358790`에는 `9cc`와 `9cc XOR1`로 고르는 두 은행이 있어요. 현재·이전 표시 화자와 주인공 ID `saved+16a2`를 구분해 `fl_hero_nomal`, `fl_nomal_hero`, `fl_change`, `fl_*_base_in/out` 계열을 선택해요. 이름판과 대화 바탕·인물 이름은 같은 텍스처 한 장이 아니에요. 일반 속도의 전환은 `9d0`을 켜고, `357880`이 이름 슬롯 `508`의 `4aa8c0` 완료를 확인한 뒤 새 텍스처를 붙이고 반대 은행의 이전 리소스를 해제해요. 빠른 진행 predicate `4784e0` 분기는 wait/stop 계열과 즉시 교체를 사용해요. 모든 화자 변경을 동일한 느린 진입 애니메이션으로 다시 재생하면 이 경로와 달라져요. 특수 sentinel과 주인공 표시 분기를 이름 없는 화자로 임의 해석하지 않아요.

글자는 `3594f0`의 UTF-16/태그 누적식으로 표시하고, 현재 출력 버퍼 `52c`를 선택된 대화창의 `4aaeb0`으로 전달해요. 출력 중 held 누적 12 또는 허용된 확인 입력은 큰 표시 예산 1024를 추가할 수 있어요. **글자 출력 완료 `944`와 BTN 대기 `954`가 둘 다 켜져야** 상태 3으로 들어가요. 텍스트를 끝까지 표시한 사건 자체가 다음 대본 명령을 바로 실행하는 사건은 아니에요.

## 본편 선택지 — 창 진입·강조·확정 표시를 거친 뒤 분기한다

본편 `MOD modChoice`는 RSC의 CHOICE/SELECT와 별도 경로예요. WRD 처리 `46cd40` case 1이 보기 뒤의 LOC 문자열을 읽고 CR/LF를 언어 2/3에서는 일반 공백, 나머지에서는 전각 공백으로 바꿔요. 저장 화자 `184e/1850`에는 sentinel 998을 쓰고, 일반 일상 모드에서는 `35e940→352c80→34c430`으로 선택 관리자에 전달해요. 별도 일상 모드의 `362ad0`도 같은 등록 함수로 들어가요. 등록은 보기 수 `+8`, 현재 선택 `+a=-1`, 요청 초기 선택 `+c`, 제한 카운터 `+10/+14`, `ChoiceCrossOut` 여부 `+1028`를 구분해 보존해요.

## 모노모노 표시값과 실제 이산 추첨 추가 확인

자원 포인터0x1408bd2e0에 대한 직접 참조가 없더라도, 실제 로더 `0x14015fbe0`는 배열 시작0x1408bd2b0부터0x1408bd2f0까지8개 포인터를 순회한다. `0x14015fda0`는 선물 아이콘·획득 결과와 백분율 숫자를 그리는 경로이며, 반환값 `0x140160160(object)`에100을 곱한 정수를 숫자 UI에 전달한다. 근거: `ev_dcff0449b9a9b8e168d0f2ca41e4f1acf590efc3a369de4fe67d7e2d824f9f5a`, `ev_3a1f39b3451b20de179cdc531d21ed9d02c4f3e2429f492630e3913d72edff9c`.

원시 명령의 전체 범위0x140160160..0x140160295에서 N=object+0x6f8의 후보 개수, U=각 후보에 대해539c50이0을 반환한 개수, C=object+0x704라고 두면 표시 백분율은 아래 식이다. 후속 소비를 대조하면 C는 저장 잔액과 같은 단위의 투입 수이고, U는 기획득 후보 수다.

```text
U == N: 100
그 외 C <= 1: 100 * U / N
그 외 C == 100: 0
그 외: max(0, 100 * U / N - 100 * C / N)
```

연산은 각각 float32다. Ghidra의 `0x140160160` 의사코드 `ev_374df80db2aff57b13cdbc8ed8920153f720955acf8cd1f9a3f21387ec857fb6`는 이 뒤쪽 산술을 누락하고 루프 이후 return만 보여준다. 따라서 해당 식의 근거는 복원 실행 파일의 원시 명령 전체이며 `native/machine_static_findings.json`에 원본 SHA·파일 오프셋·구간 SHA·각 명령을 보존했다. 디컴파일 텍스트만으로 완료 판정하지 않는다.

실제 선택0x14015f390..0x14015f4c8은 후보를539c50==0인 A와 그 밖의 B로 분리한다. p=표시값/100이며 A가 비면0, B가 비면1로 보정하고 float32(p*32768)과 `5d7ba0()`의 하위15비트 정수를 비교한다. 임계값 이상이 아니라 **임계값이 난수 이상일 때** A를 선택하고, 다음 난수%해당 목록 수로 아이템을 선택한다. 등호를 포함하는 이산 비교와 나머지 선택이므로 UI 백분율과 수학적 실수 확률을 동일시하지 않는다. 난수 생성기의 분포·초기화는 아직 별도 검증 대상이다. 후보 목록과 C의 조작·소모는 아래 후속 소비 대조로 확인했다.

실제 난수 루틴 `0x1405d7ba0..0x1405d7beb`는4개 전역 u32 상태에 xor와11/11/8비트 시프트를 적용하고 최상위 비트를 지운31비트 정수를 반환하는 리프다. CRT rand로 해석하지 않는다. 시드 초기화·장면별 상태 공유·분포 검증은 별도이며 원시 구간은 같은 증거 JSON에 보존했다.

기본 추첨 외의 경로도 있다. 입력·진행 함수0x14015eb30은 결과 대기 후 object+0x714가0이 아니면 전체 후보 N에서 난수%N으로 바로 선택하며,0일 때만 앞의 이중 목록 추첨을 사용한다. 선택 직후 Item 비트 결과를+0x720에 기록하고536b50(item)을 호출한 뒤 C를0으로 만든다. 해당 상태를 보너스/추가 회차로 단정하기 전에 setter와 UI 상태를 더 확인해야 한다. 따라서 위 공식을 모든 회차에 무조건 적용하지 않는다.

후보 목록 초기화0x14015e390은 Item.dat의 전체143행 중 열5(u16,행+12)가0이 아닌 항목83개를 넣는다(52db70의 getter, 목록상한200). 추가 선택의 초기 확률은 C==100이면1, 그 외 clamp(float32(0.1+0.009*C),0,1)이며15e5e0에서15비트 난수와 비교한다. 추가 성공마다 확률에0.5를 곱하고 별도 카운터를 올리며, 카운터4 이상이면 더 시도하지 않는다. 이 역시 원시 명령으로 확인한 상태식이며 실제 상태 순환에서 이 한도까지 도달하는지는 아래 재설정 문제와 구분한다.

### 최종 소비 대조와 도달성 정정

입력·진행 `0x14015eb30`의 실제 의사코드 근거는 `ev_a2729923c6f61ab40ca600ae7807c63e1158da4f9d280a02a4d04ee20b291bae`다. 투입 C는0..min(100,현재 잔액) 범위에서 조작한다. 입력 분기에는 ±10과 길게 누르기 누적에 따른 증가량 `(누적+14)/15`가 있다. 잔액 getter `0x14053a090..0x14053a09e`는 저장영역+0x2636의 u16을 읽고, 실행 직후 `0x14053eb20..0x14053eb43`가 이 잔액에서 C를 차감하며 부족하면0으로 포화한다. 따라서 C는 이 잔액과 같은 단위인 모노모노 투입 개수다. 원시 구간은 기계 근거 JSON에 추가했다.

Item 획득 소비 `0x140536b50..0x140536d60`는 Item saveNo별 저장영역+0x2b6c의 u16 보유 수를1 늘리고999로 제한한다. 이어+0x2d6c 비트가1이면 지운다. 이 경로와539c50의 동일 비트 검사를 대조하면1은 미획득,0은 기획득으로 식별할 수 있다. 그러므로 앞의 U는 기획득 후보 수, A 선택은 중복 아이템 선택이다. 이것을 UI의 '새 아이템 확률'로 뒤집어 적지 않는다. getter 근거: `ev_ef2ea30c4953dbb1fc75d2aebc0765a8cbb76e922efaadf6037c80118be48973`.

중요하게, 추가 선택 카운터 한도4와 전체 목록 추첨 분기는 코드에 존재하지만 **실제 최대4회 추가로 이어진다고 확정하지 않는다.** 상태0x11에서 카운터+0x714를 늘리고 확률을 절반으로 줄인 후 상태0xc로 되돌아가며, 상태0xc는 같은 카운터를0으로 다시 쓴다(원시0x14015f2a4/0x14015f2ba/0x14015f05c). 후속 [22_선물추첨.md](22_선물추첨.md)와 외부 `native/monomono_findings.json`의 조건부 상태 추적으로 정상 로컬 순환에서는 다음 추가 판정 전에 카운터가 다시0이 됨을 확인했다. 따라서 이 순환에 최대4회 상한을 적용하는 해석은 맞지 않는다. 이는 실제 추첨 플레이 기록이 아니며 모든 callback 교차·실제 최대 연속 획득·난수 분포는 여전히 미확정이다.

추가 네이티브 ID: 최초 선택 `ev_e050f9f670490da1682a08cbdcd883e81def2c934a8b896e6dff6b73282aef0d`, 후보 초기화 `ev_442b1d2d74105ade11868df99bda801fabfa9573d6ed21653e953f49f360057a`, 추가 판정 `ev_0c3b6d25601dbed2a55ff9a749ce32f8a0e5b63039242320c02a25c4101361d3`, Item 열5 getter `ev_7d54ae7742e4c455ee86f2726ae285a4fd92a0219076c14dc974fc0ef495341c`. 최초 선택 의사코드는5d7ba0의 하위15비트 처리와160160의 산술 전체를 표현하지 못하므로 원시 구간을 함께 읽는다.

## 본편 자유행동: 선택에서 시간·보상까지

이 절은 설치본007의 기본 WRD와 US007의1929개 WRD 우선 적용을 합친2716개 유효 스크립트에서 조사했다. 대사 본문은 저장소에 가져오지 않았다. `native/freetime_findings.json`은 각 스크립트 SHA·명령 오프셋·조건·분기와 반증을 보존한다. 아래 규칙은 정적 제어 흐름과 네이티브 소비의 대조 결과이며 모든 날짜를 실제 플레이한 기록은 아니다.

### 본편과 보너스의 공유 경로

`ainori/` 경로를 보너스 전용으로 제외하면 본편 선물을 놓친다. 예를 들어 본편 `chap1/c01_019_000`은 `wkAinoriDay=999`를 기록하고, 초대 스크립트가 `ainori/a00_101_000`을 SUB 호출한다. 공통 선물 스크립트는 `wkAinoriDay!=999`일 때만 보너스의 일자/UI 전환과 LOV 증가를 수행한다. SSB 변화는 이 조건 바깥에도 있다. 따라서 본편에는 공통 선물 취향 경로를 적용하되 보너스 LOV·날짜 규칙을 함께 가져오지 않는다. `Friendship.dat`의0/10/100/1000/10000/100000은 이 본편 SSB/SIN 임계값의 근거가 아니다.

### 배치와 초대는 서로 다른 조건

WAK 처리 `0x140474af0`는 `wak050_scene` 변경 시 저장영역+0x1706의 하위 scene을0으로 만든 뒤 mode1에서 `0x140472650(chapter,scene,subscene)`를 호출한다. 이 함수가 `mpf_setting.dat`의 상태3키와 대응하는 지도/캐릭터 비트를 갱신한다. 정적으로 초대 wrapper를 호출하는 scene군23개 전부에 대응 상태행이 있다. `c03_007`처럼 같은 상태키의 행이2개인 경우도 보존했다. 지도에 보이는 마커만으로 초대 가능을 확정하지 않는다. 예를 들어 `c02_016`의 후보 마커는13개지만 확인한 서로 다른 초대 wrapper 호출 대상은11개다. 실제 클릭은 맵 스크립트의 CHK·IFF와 배치 상태를 함께 거친다.

| 범위 | 초대 wrapper 파일 | 호출 scene군 |
|---|---:|---:|
| chapter1 |60|4|
| chapter2 |65|5|
| chapter3 |55|5|
| chapter4 |40|5|
| chapter5 |20|4|
| 합계 |240|23|

이는 설치된 스크립트의 정적 군집 수다. 실제 플레이 날짜 수·살아 있는 인원 수·각 캐릭터의 모든 도달 가능한 이벤트 수로 바꿔 부르지 않는다.

### 수락·거절·선물의 결과

표준 초대 wrapper는 선택 취소/거절 경로에서 수락 label을 거치지 않고 RTN한다. 이 경로에는 SSB+15와 `flg220=on`이 없다. 수락 label은 SSB에15를 더하고100을 상한으로 잡은 뒤 공통 선물 SUB를 호출한다. 조사한240개 wrapper 모두 이15/100 설정과 뒤의20 임계 검사가 있다.

선물 취향은 Item/Person의 이름이나 설명에 있는 '좋아함' 텍스트로 계산하지 않는다. 공통 선물 WRD의 `CHK itemNNN → JMP 반응 label`이 실제 분류표다. 본편 전용1개와 공통15개, 총16개 선물 메뉴 스크립트에서 아이템별 목적 label·오프셋을 보존했다. 일반 반응의 SSB 변화는 -5/-3/+3/+5/+10이며0..100으로 제한된다. 특정 아이템에는 주인공/모드 검사와 별도 label 전환이 있어 이 다섯 값의 단일 rarity 표로 치환하지 않는다. 보너스 LOV 변화는 별도 조건으로 분리했다.

선물 선택의 UI 허용은 앞의 Item 열6과 보유 수 검사다. 본편 진행 처리0x140456d80은 메뉴가 닫힌 뒤 `410350→41c330`이 반환한 선택 Item이 null이 아니면 `53eaa0`로 보유 수를1 차감하고 WRD 체크포인트를 재개한다. `53eaa0`의 원시0x14053eaa0..0x14053eb15는 저장영역+0x2b6c의 u16 보유 수를 감소시키며0에서 underflow한ffff는0으로 복원한다. 즉 **반응이 나쁜 선물도 확인해서 건넸으면1개 소모**한다. 메뉴 취소 null은 이 차감이 없다. 뒤에 나오는 취향 반응과 먼저 일어난 아이템 소모를 구분한다.

### 친밀도 진행과 스킬 해금

선물에서 돌아온 wrapper는 누적 SSB>=20이면 SSB를0으로 만들고 현재 SIN 단계에 맞는 이벤트를 SUB 호출한다. 예를 들어 chapter2 표준 경로는 SIN>=6이면 추가 이벤트를 건너뛰고,5/4/3/2/0 이상의 순서로 다음 이벤트를 선택한다. SSB가20 미만이어도 수락을 취소한 것으로 되돌리지 않고 종료 경로로 간다. 그러므로 선물을 주지 않았다고 자동으로 자유행동이 무효가 되는 규칙은 아니다. 반대로 선물 한 번만으로 항상 rank가 오르는 것도 아니다.

SIN은 단순 work 배열을 덮어쓰는 변수가 아니다. `466200`은 현재값 `53af20`보다 요청 SIN이 클 때만 차이만큼 `537040`을 호출한다. 따라서 각 scene의 `sinNNN=1`은 이미 진행한 값을1로 초기화하지 않는다. 저장 group0은 최대3, group1은 최대6이다. 그룹은 현재 주인공과 모드에 따라 선택되며 SSB도 저장영역+0x8fc0의 두16칸 뱅크로 구분된다. 일부 이벤트를 같은 캐릭터의 동일한 하나의 친밀도로 합치면 이 분리가 사라진다.

증가 차이는 `536fd0`에서 저장영역+0x241e의 보상 카운터에도 더해지고999로 제한된다. SIN>=2의 요청은 `shinmitsu_<group>_<character>_<요청단계-2>` 해금 이름을 만들어53e770을 호출한다. 이벤트의 `flgGallertMode==off` 검사는 갤러리 재생 때 이 증가/보상을 반복하지 않도록 하는 별도 경로다. 스킬 보상은 이벤트에서 WAK의 SKIL 라벨에1을 대입하는 경로이며466200→53e230이 Skill saveNo의 저장영역+0xafac 비트를 켠다. 조사한 최종 이벤트의 스킬 후보15개는 이 소비와 대조했다. 장착·FP 구매·슬롯 용량은 이 '획득 비트 켜기'와 구분한다.

### 시간 소비는 장면 전환의 결과

수락 종료나 친밀도 이벤트는 `flg220=on`을 남기고 호출 맵으로 RTN한다. 호출 맵은 `IFF flg220==on`일 때 정리 후 다음 story scene으로 FIL한다. 거절은 이 표시를 남기지 않아 해당 수락 종료 경로를 타지 않는다. 따라서 '분 단위 타이머를 일정량 차감'이라는 추정 대신 **선택 → 보상/반응 → 종료 표시 → 호출 맵의 FIL**을 시간 소비의 근거로 삼는다. 수사도 단순 시계가 임계값에 도달해서 시작한다고 확정하지 않고 다음 story scene의 상태·사건 분기와 연결해 확인한다.

일반화의 반증도 있다. 따라서 대표 정상 일상은 **준비된 공간/대상 선택→초대 반응/선택→수락 또는 거절→선물/관계→활동 완료→호출자 정리→다음 초기화→다음 장면의 준비/조작 허용**으로 재구성할 수 있다. 대안인 개인 공간 checkpoint102의 휴식은 flg201 허용→2개 보기→Choice0의 검은 fadeOutStop/Delete/FIL이며, Choice1과 허용된 취소는 다음 FIL 없이 남는다. 같은019→020→021에서 목적 초기화가 각각 DayTime/Night를 쓴다. 별도 일상20의 숫자 슬롯·날짜 표시 UI나 보편적인2회 카운터를 본편에 가져오지 않는다.

입력·표현·저장도 연결하되 완료 사건을 합치지 않는다. 대화 SE003/문장·이름판/세 KNM 슬롯, 본편 선택지의 설계 좌표·강조/확정 SFL은 앞 절과06의 계약을 재사용한다. 맵 재개는 인물·맵 준비 및 modTansakuWait의 조건을 다시 충족해야 한다. 패드/F1·SystemSave는 [09_시스템.md](09_시스템.md)의 허용 조건, 저장 확인·작업 완료·성공·퇴장 대기와 이어하기의 snapshot/맵/대본 커서 복원을 따른다. 활동 완료220을 디스크 저장 성공이나 모든 입력 잠금 해제로 바꾸지 않는다.

이 정상 한 고리와215개 진입 wrapper의 SSB/rank 경계, 진입을 우회하는25개, 호출자의 완료 gate·초기화 예외를 합치면 본편 일상·자유행동의 **주요 정상 규칙과 표현**을 명세할 근거가 있다. 모든 날짜/특별 이벤트의 전역 도달성·모든 그림·실제 실행 관찰은 별도 한계다. 외부 `main_daily_normal_findings.json`/`main_daily_normal_contract.py`가 기존 근거20개 원장, REA16개 함수, 정확한 대본 연결15곳과 place08을 대조한다. 원작 실행·추출·렌더 및 공용 점수 변경 없이 확인했다.

### 후속 정정 — 240개 파일 중 정상 진입에서 초대 선택지를 건너뛰는 25개

완료 writer가 파일 어딘가에 있다는 것과 정상 진입에서 그 writer를 실행할 수 있다는 것은 달랐다. 실효 US007 wrapper 240개를 SHA·lab_Top 기준으로 다시 검사했다. 215개는 첫 제어 분기가 modChoice 요청이고, 25개는 그 전에 무조건 JMP로 끝의 LAB→RTN에 도착한다. 이 25개 안에도 선택·선물·관계 이벤트·flg220 writer가 남아 있지만 정상 진입의 JMP가 그 본문을 건너뛴다. 파일 존재를 초대 가능성으로 바꾸지 않는다.

앞서 완료 gate가 없었던 15개는 모두 이 25개의 진입 우회에 해당했다. 따라서 성공한 자유행동의 누락된 전환으로 볼 근거가 없어졌다. 예를 들어 기술 파일 `c02_710_050`은 JMP@212→LAB@892→RTN@896이며, 파일에 남은 flg220 writer@882는 이 진입에서 건너뛴다. 대사를 읽거나 실제 선택을 실행해서 얻은 판단이 아니라 제어 명령과 native JMP/RTN의 대조다.

260개 맵 호출 후보를 다시 나누면 선택지 진입 wrapper 뒤 완료 gate가 240곳, 진입 우회 wrapper 뒤 완료 gate가 5곳, 진입 우회 뒤 gate 없이 HUM/파일 끝이 15곳이다. 고유 호출 대상은 231개이며, 그중 진입 우회 wrapper는 20개다. 원래245개 gate·13개 인접 사슬은 구조적 사실로 유지하되 모두 성공 가능 호출이라고 해석하지 않는다. 우회 wrapper가 이번 경로에서220을 쓰지 않는다는 것이지, 호출 전 남아 있던220 값까지 자동으로0이라는 뜻은 아니다.

215개도 실제 자유행동 횟수·날짜별 가용 인원·rank별 수락 수가 아니다. 전역 등장 조건·다른 label로의 직접 진입·입력에 따른 선택·호출자의 플래그 초기화는 별도 잔여다. 외부 `native/freetime_entry_bypass_findings.json`, 재현 `native/close_freetime_entry_bypass.py`는 240개 SHA/진입, 25개 label/RTN·완료 writer 우회, 15개 예외 연결을 검증했다. 근거: JMP `ev_2c47df134ff2ae62fca852536e9ae0374185c691cb363d5be5ed4ec4904c4d61`, RTN `ev_61263c2b819ac1def4aa76faccf68a0c87fce30c19ded42ea12e9deae9e376bd`, HUM `ev_a6212703759f553ab4bc65b12d5c356e2fced0606a963679754be8dcc631b595`.

### 완료 플래그 초기화와 특수 분기 경계

기존 실효 US007 기술 대본 2,716개에서 flg220을 끄는 명령은 302파일의 549곳이다. 선택한 자유행동 source 진입 23개는 모두 lab_Top의 첫 명시적 분기·호출 전에 flg220을 끈다. 이 중 5개는 먼저 modSetScene/modModeOpen을 요청하므로 이 결과만으로 모든 scheduler·직접 label 진입까지 초기값0이라고 증명하지 않는다.

완료 gate 245개 중 참 본문에서 즉시 초기화하는 곳은 231개다. 나머지 14개 중 11개는 다음 장면의 선형 초기화에서 끄고, 3개는 다음 장면의 첫 FIL 전까지도 끄지 않는다. 이 3개 도착 파일은 각각 뒤의 101 파일로 넘어가며, 그 파일들에도 직접 flg220 명령은 없다. 이것만으로 오래된 값 때문에 오작동한다고 판단할 수 없다. 이후 전역 소비·공유 호출·다른 진입은 별도 추적 대상이다.

14개 모두 일반220 gate 앞에 별도 flg500/wak054 조건 분기가 있다. 해당 분기는 공통 helper 호출 후220과500을 끄고 같은 도착 파일로 FIL한다. 이 helper·초기화는 무조건 실행되는 선행 단계가 아니다. FIL로 교체되므로 그 경로가 뒤의 일반220 gate까지 계속 내려온다고 읽지 않는다. 기존 원장의 intervening_helper_calls는 위치상 목록이며 실행 경로 증명이 아니다.

외부 `native/close_freetime_reset_boundaries.py`와 `freetime_reset_boundary_findings.json`이 SHA·23진입·245gate·14특수 분기 순서를 검증한다. 원본 실행·추출·Game 수정은 없으며 기존 native FLG/FIL/SUB/HUM 근거를 재사용한다. 팬게임에서는 성공·취소·특수 이벤트와 다음 장면 초기화를 구분하고, 모든 초대가 같은 초기화 경로를 탄다고 합치지 않는다.

도입부의 대화·연출 파일과 수동 탐색 파일을 하나의 선형 대본으로 읽지 않는다. 캐시 effectiveUS007의 `c00_001_018 FIL@3148 → c00_002_000 FIL@470 → c00_002_018`이 실제 명시적 교체 사슬이고, 마지막 파일의 `modTansakuWait@374`가 첫 시점·대상 선택 대기 후보다.
